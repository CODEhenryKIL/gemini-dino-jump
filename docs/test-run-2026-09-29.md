## 3. 실제 카카오 전송 → 원장 대조

모두 **사용자가 직접 전송**했다. 서버에서 공식 콜백·보상 원장만 읽기 조회했고, 카카오 메시지·수신자·연락처·인증 비밀은 수집하지 않았다. 시간은 KST다.

| 확인 시각 | 목적 / 방 | 서버 확인 | 게임권 변화 | 뽑기권 변화 |
| --- | --- | --- | ---: | ---: |
| 10:10:08 | 게임 재도전 / 친구 | CONFIRMED, BLOCKED_CAP | 0 | 0 |
| 10:18:07 | 일반 홍보 / 친구 | CONFIRMED, NO_REWARD | 0 | 0 |
| 10:18:34 | 추가 뽑기 / 친구 | CONFIRMED, GRANTED | 0 | **+1** |
| 10:18:53 | 상품 자랑 / 친구 | CONFIRMED, NO_REWARD | 0 | 0 |
| 10:23:11 | 게임 재도전 / 단체방 | CONFIRMED, GRANTED | **+1** | 0 |
| 10:28:41 요청 | 수령 접수 / 나에게 | REJECTED, NOT_ELIGIBLE, 접수 미완료 | 0 | 0 |
| 10:32:06 | 수령 접수 / 친구 | CONFIRMED, INFORMATION_RECEIVED | 0 | 0 |

- 첫 GAME 전송자는 초대권 3장 보유 중이었으므로 미지급이 정상이다. 해당 요청의 두 원장 모두 추가 행 0개였다.
- DRAW 전송의 뽑기권 원장은 정확히 1행·delta +1, 게임권 원장 0행이었다. 이후 2회차 `테스트 커피` PRIZE·공개 완료를 확인했다.
- 당첨 자랑 공유는 추가 게임권·뽑기권을 주지 않았다. 사용자는 카드가 잘 나온다고 확인했다. 위치별 수신 카드 전체를 캡처 대조한 것은 아니다.
- Safari 새 참가자의 MultiChat GAME은 기본권 1장과 초대권 1장, SHARE_GRANT 1건으로 확인했다.
- 시크릿 창에서는 사용자에게 카카오 다운로드 안내가 노출됐다. 같은 사용자가 Safari 일반 창에서 단체방 전송에 성공했다. 시크릿 앱 연결 실패의 원인을 서버 오류로 단정하지 않는다.
- 수령 접수는 나에게 보내기 후 2단계에 머물렀고, 친구 전송 후 3단계로 넘어갔다고 사용자가 확인했다. 서버도 처음에는 접수 미완료, 이후 `INFORMATION_RECEIVED`·연락처 제출 시각 존재로 바뀌었다. 두 전송 모두 게임권·뽑기권 추가 0이다. 입력된 개인정보 본문은 조회하지 않았다.
- 여러 방 동시 선택, 공유창 취소 후 전체 초안 복원, 모든 공유 위치의 수신 카드 캡처 대조는 아직 별도 검증 대상이다.

### 점프 버튼 보완 범위

`game_view.js`에서 점프 버튼에만 `selectstart`, `dblclick`, 비수동 touch 이벤트 차단을 추가하고 화면 정리 시 해제한다. `game.css`의 해당 버튼만 `touch-action:none`으로 변경했다. 기존 점프 누르기·떼기와 수퍼 점프 입력은 유지하며 이름·연락처 입력칸에는 적용하지 않는다.

터치 기본 동작과 글자 선택은 별도 제어가 필요하므로 함께 다뤘다. [MDN touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action), [MDN user-select](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/user-select). 이벤트 모의 시험은 Safari의 실제 선택 UI까지 증명하지 않으므로 배포 후 동일 휴대폰으로 재확인해야 한다.

### 분석 누락 재현

1. 혜택 안내에서 공부법 또는 취업사진의 복사 버튼을 누른다.
2. 복사는 성공하지만 콘솔에 `analytics_batch_rejected`가 발생한다.
3. 실제 화면과 같은 payload를 서버 검증 함수에 넣으면 HTTP 202 안에서 `accepted:0, rejected:1, INVALID_DIMENSIONS`가 반환된다. DB INSERT 호출 0회다.
4. 같은 payload에서 `source`만 현재 허용값 `gemini`로 바꾼 대조 실험은 `accepted:1, rejected:0`이다. 이 비교는 모의 DB 호출로 수행했으며 원격 기록을 조작하지 않았다.

따라서 일반 HTTP 오류율만 확인하면 이 누락을 놓친다. 분석 배치의 `accepted/rejected`를 함께 검사해야 한다.
