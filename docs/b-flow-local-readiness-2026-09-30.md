스냅샷과 검증 자료는 Git 및 배포 대상에서 제외된 `.local/b-flow/`에 접근 제한 파일로 저장했다. 개인정보가 포함되므로 공개하거나 저장소에 추가하면 안 된다. 별도 스냅샷은 단발성 로컬 백업이며, 자동 외부 보관 서비스가 새로 설정된 것은 아니다. 프로젝트의 Auth·Storage 파일·역할·비밀 설정 전체를 대체하지 않는다.

웹 서버 장애/재배포 자체가 별도 DB를 지우지는 않는다. 다만 오삭제·잘못된 DB 변경·DB 장애까지 데이터 손실 가능성이 0이라는 뜻은 아니다. PITR가 꺼져 있으므로 자동 백업 복원 시 마지막 백업 이후 기록은 복구되지 않을 수 있다. Supabase 전체 프로젝트 복구는 다른 스키마에도 영향을 줄 수 있어, 먼저 새 격리 DB로 복원하고 필요한 범위를 확인해야 한다.

근거: [Supabase 공식 백업 문서](https://supabase.com/docs/guides/platform/backups). 실제 보관 목록·PITR 상태는 해당 프로젝트 관리 화면에서 확인했다.

## 최종 승인 후 순서

1. 운영 스냅샷을 새로 생성하고, 코드·DB 버전과 마이그레이션 체크섬을 대조한다.
2. 운영 스키마로 변환한 추가 마이그레이션을 적용한다. 기존 기록 수와 제약 상태를 비교한다.
3. 새 서버와 프론트를 배포한다. 순서는 DB → 서버/프론트다. 기존 클라이언트의 v2 공유도 처리해야 한다.
4. 운영에서 읽기 전용 상태 확인, 기존 당첨/접수 내역 유지, 실제 카카오 새 복합 보상 1회 확인을 진행한다.
5. 문제가 생기면 새 B안 진입을 중지하고 호환 서버로 대응한다. 새 v3 공유가 생성된 뒤에는 DB 컬럼 삭제나 v3 미지원 서버로의 무조건 롤백을 하지 않는다.
