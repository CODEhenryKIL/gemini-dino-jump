- 작성일: 2026-09-29
- 상태: **실행 중 — 코드·운영 준비 진행, 부하 테스트는 사용자 재확인에 따라 계속 보류**
- 목표: 최종 코드·운영 설정·초기 데이터·관측 도구를 검증해, 검토한 릴리스로 본행사를 열 수 있는 상태를 만든다.
- 대상 저장소: `gemini-dino-jump`, 실행 브랜치 `codex/final-launch-preflight` (`codex/phase3-launch`에서 생성)

## 1. 성공 기준

1. 운영 주소가 Vercel 로그인 없이 열리고, 서버·DB·관리자가 정상 연결된다.
2. 본행사 점수·참가자·초대·추첨·수령 기록은 빈 상태에서 시작하며 베타 기록이 섞이지 않는다.
3. 무제한 모드는 꺼지고 최초 게임권 1장, 공유 보상, 환급, 보유 한도와 대기시간이 정상 적용된다.
4. 총 5,000회 추첨에 실제 상품 77개와 Gemini 혜택 4,923자리가 배정되고, 랭킹 경품 3개는 별도로 관리된다.
5. 행사·수령 마감과 동점 순서가 화면·API·DB·관리자에서 일치한다.
6. GA4는 동의한 사용자의 운영 이벤트만 수집하고, Datadog은 운영 서버와 로그 수집 상태를 감시한다.
7. 이상 발생 시 신규 참여를 중단하고 같은 운영 DB를 사용하는 호환 버전으로 복구할 수 있다.
8. GitHub 커밋, 배포 ID, DB 버전, 설정 해시, 실제 검사 결과가 하나의 릴리스 기록으로 연결된다.

## 4. 작업 순서와 완료 조건

### A. 기준 고정 및 준비 절차 보완

**작업**

1. 현재 브랜치·작업 파일·기존 배포·도메인·DB 연결·관리자 역할을 기록한다. 사용자 변경을 보존한 상태로 릴리스용 브랜치 또는 기존 전용 브랜치를 사용한다.
2. 설정·지시서·체크리스트에 최신 결정을 반영한다. Notion 접근은 사용자 확인, 발송일 미정은 비차단 항목, 대학생 증빙은 수동 연락으로 기록한다.
3. 기존 `PRESERVE_BETA_START_NEW` 문구를 ‘본행사는 새 운영 영역으로 시작하고, 베타 참여 기록은 전환 절차에 따라 초기화’로 맞춘다.
4. 현재 `prepare_production.provision()`은 모든 오픈 증거가 있어야 준비 적재를 허용한다. 이 순환 의존을 해소하도록 **준비 검사와 공개 검사**를 구분한다.
   - 준비 검사: 대상·역할·백업·설정·재고 수량이 검증되면 `event_enabled=false`, 캠페인 PAUSED로 준비 가능.
   - 공개 검사: 필수 기능 검사·실제 연결·전환 절차·공개 권한과 미검증 항목 처리를 확인해야 활성화 가능.
   - `server/config.py`의 manifest 승인 검사, `server/db.py`의 guard, 준비 도구, 테스트에 같은 단계 구분을 적용한다.
5. 보류·사용자 확인·자동 검사·실전송 결과를 구분한다. 빈 증거 칸에 임의의 ‘완료’ 문구를 넣어 검사를 통과시키지 않는다.

**완료 조건:** 행사 OFF 상태에서 운영 준비를 진행할 수 있고, OFF 상태에서는 신규 게임·추첨·보상이 허용되지 않는다. 설정 불일치와 권한 오류를 검사가 차단한다.

### C. 운영 영역과 정지 상태 배포 준비

1. 같은 Supabase 프로젝트를 사용한다. 별도 유료 프로젝트를 새로 만들지 않는다.
2. `dino_prod`가 이미 있으면 내용과 역할부터 조사한다. 기존 테이블·기록을 덮어쓰거나 초기화하지 않는다.
3. 고정된 migration 목록과 해시를 확인해 운영 스키마를 준비한다. 최소 권한 역할과 기존 앱/베타에 대한 접근 차단을 검증한다.
4. 실제 운영 관리자 계정의 접근을 확인하고 합성 관리자에게 운영 권한이 이월되지 않게 한다.
5. 최초 적재 후 다음을 대조한다: 추첨판 5,000자리, 상품 77자리, 혜택 4,923자리, 랭킹 전용 3개, 총 재고 80개, 참여·게임·추첨·수령 기록 0개.
6. `PREVIEW_UNLIMITED_PLAY=false`, 테스트 재고/단축 시계 false, `APP_ENV=production`, `VERCEL_ENV=production`, 전용 DB 역할·쿠키·manifest 해시를 적용한다.
7. Vercel **Production 환경의 후보 배포**를 만들되 검증 전 공개 별칭이 자동 이동하지 않도록 지원되는 배포 방식을 먼저 확인한다. Preview 배포에 APP_ENV만 production으로 넣는 방식은 사용하지 않는다.
8. `dino-nanobanana.vercel.app`의 기존 연결도 사전 기록해 뜻하지 않게 바뀌지 않도록 확인한다. 공개 대상 별칭은 `google-korea-team-gemini.vercel.app`이다.

### F. 베타 초기화와 공개 전환 준비

최신 사용자의 베타 초기화 요청을 반영한다. 운영 데이터를 새로 시작하는 작업과 베타 데이터 삭제를 각각 검증한다.

**초기화 범위**

- 공룡 점프 베타의 참가자·점수·게임 세션·게임권/뽑기권 원장·추천/공유 요청·추첨·테스트 재고 배정·수령 정보/임시 입력·참여 분석 기록을 의존 관계에 맞게 정리한다.
- 기존 앱의 테이블, 공용 인증 계정, 운영 관리자 접근, 운영 재고, 실제 본행사 기록은 삭제 대상에서 제외한다. 베타 스키마 구조·migration 이력·환경 guard·관리자 계정도 유지하고 재시드로 참가 기록을 다시 만들지 않는다.
- GA4 테스트 속성과 Datadog 진단 로그는 행사 DB 기록과 구분한다. 운영 통계에 섞이지 않게 분리하며 외부 서비스 전체를 일괄 삭제하지 않는다.
- 초기화 도구는 대상 스키마·캠페인·환경·예상 건수, 외래키와 참조 범위를 먼저 출력하는 계획 모드와 실제 적용 모드를 분리한다. 계획 식별값과 적용 직전 건수를 대조하고 불일치 시 중단한다.

**순서**

1. 운영 후보 배포·재고·관리자·복구 준비 및 마지막 검증을 끝낸다.
2. 현재 베타 배포와 직접 접속 가능한 이전 주소를 조사해, 화면뿐 아니라 API·웹훅 경로까지 베타 신규 쓰기를 막는다. 이미 실행 중인 요청이 종료됐는지 확인한다. 대기 중인 베타 공유 요청은 범위를 확인해 종료·무효화하고, 지연된 콜백은 운영 보상 없이 종료되도록 검증한다. 콜백 만료 시간만 믿고 기존 쓰기 경로를 열어두지 않는다.
3. 비공개 제한 권한의 최종 복구 자료와 초기화 계획을 확보한다. 개인정보가 든 자료는 Git·공개 배포·채팅에 넣지 않고 복구 필요가 끝난 뒤 정리한다.
4. 삭제 계획을 고정하고 적용 준비까지 끝낸다. 물리 삭제는 G 단계의 운영 주소 읽기 확인 직후에 수행해 전환 실패 원인을 조사할 수 있게 한다. 이 짧은 대기 동안 베타는 쓰기 차단 상태를 유지한다.
5. 공개에 사용할 운영 참가자·점수·추첨·수령은 이미 별도 영역에서 0건이고 재고는 준비된 80개인지 다시 확인한다. 따라서 본행사는 베타 물리 삭제 시점과 관계없이 새 기록으로 시작한다.

### G. 공개 전환·GitHub 최신화

1. 검토된 코드·설정·문서를 최종 커밋하고 PR에 변경·검증·미실행 항목을 정리한다. PR을 만들면 현재 작업에 첨부한다. 비밀값·DB dump·개인정보·로컬 로그는 제외한다.
2. Git push·main merge가 자동 배포를 일으키는지 먼저 확인한다. 최종 공개 준비 전 자동으로 주소가 전환되지 않게 순서를 정한다. 검증한 SHA와 실제 배포 SHA가 같아야 한다.
3. 최종 설정 파일 바이트, `PRODUCTION_MANIFEST_SHA256`, DB guard의 해시·행사 플래그를 함께 맞춘다. 행사 플래그를 false→true로 바꾸면 설정 해시가 달라지는 점까지 전환 절차에 포함한다.
4. 활성 설정 파일을 포함한 별도 Production 후보를 준비한다. 아직 연결되지 않은 후보 URL도 외부 쓰기가 불가능하도록 접근을 통제한다. 한 DB 트랜잭션 안에서 캠페인 ACTIVE, guard의 최종 manifest 해시·행사 플래그를 갱신한 뒤 해당 배포로 공개 별칭을 전환한다. 이 사이 구버전의 해시 불일치는 참여 거절로 처리하고, 후보 접근 통제는 공개 전환 시 정상 해제한다.
5. 별칭 전환이 실패하면 신규 참여를 중단하고 현재 DB와 호환되는 정지 상태 빌드·guard 해시/플래그 조합으로 복구한다. DB 트랜잭션과 Vercel 별칭 변경은 하나의 원자적 작업이 아니므로 중간 실패 지점을 각각 검증한다. 실제 시작은 서버 일정·활성 상태·공개 상태가 모두 충족될 때다.
6. 별칭 전환 후 익명 접속으로 홈·API·혜택·랭킹·관리자·공유 설정·GA4/Datadog 환경을 대조한다. 실제 운영 참가자 생성·추첨을 임의의 테스트로 사용하지 않는다. 최초 1장 지급 등 쓰기 검증은 앞선 격리 환경 결과를 사용하고 실제 첫 정상 참여를 관측한다.
7. 오래 열린 베타 화면의 버전 감지·재로드 안내를 확인한다. 이전 화면이 본행사 API에 요청해 베타 게임을 운영 기록으로 제출할 수 없어야 한다.
8. 운영 주소 읽기 검사가 통과하면 F 단계의 베타 삭제 계획을 다시 대조하고 트랜잭션으로 적용한다. 베타 삭제 대상 0건·기존 앱 집계 불변·공개 후 생성된 운영 기록 보존을 확인한다. 삭제 후 지연 콜백이나 이전 URL 요청으로 베타 기록이 재생성되지 않아야 한다. 초기화가 실패하면 오픈 완료로 보고하지 않고 중단된 베타 상태에서 해당 범위만 복구·재처리한다.
9. 공개 URL·커밋 SHA·배포 ID·스키마 버전·설정 해시·공개 시각·검사 결과를 기록한다. 완료된 작업용 브라우저 탭을 닫는다.

**완료 조건:** 로그인을 요구하지 않는 공개 주소에서 운영 설정이 확인되고, 베타 무제한·테스트 상품·기록이 보이지 않는다. 범위를 제한한 베타 초기화가 완료되고 본행사 관측 도구가 실제 운영 환경을 가리킨다.

## 5. 중단·복구 계획

| 상황 | 조치 |
| --- | --- |
| 운영 DB 생성/연결 실패 | 공개 전환 중단. 검증된 기존 화면 또는 점검 화면 유지. 다른 스키마를 대신 연결하지 않음 |
| 초기화 대상/건수 불일치 | 삭제 적용 중단·계획 재생성. 대상 전체를 넓혀서 강제 삭제하지 않음 |
| 설정 해시·역할·캠페인 불일치 | 행사 OFF/PAUSED 유지, 설정과 guard 정합성 복구 후 재검사 |
| 재고 초과·중복 보상·타인 정보 노출 | 신규 참여·보상 중단, 요청/원장 대조 후 수정. 노출된 당첨 결과를 재추첨하지 않음 |
| 코드 배포 오류 | 같은 본행사 DB·캠페인·현재 guard와 호환되는 검증 빌드로 복구. 필요하면 점검 화면으로 전환 |
| 공개 뒤 실제 참여가 생긴 경우 | 베타 DB나 과거 DB dump로 사이트를 되돌리지 않음. 실제 당첨·점수·수령·원장을 보존하며 수정 배포 |
| 분석/로그 연결 실패 | 수집 경로를 복구하고 자체 서버 원장으로 확인. 분석 오류가 게임권·당첨 판단을 바꾸지 않게 유지 |

새 운영 데이터를 쓰기 시작하기 전까지의 복구와 공개 후 복구를 나눠 연습한다. 서비스 전체 데이터베이스 reset이나 이미 지급된 재고의 자동 복원은 복구 방법으로 사용하지 않는다.

## 6. 담당과 사용자 개입

| 담당 | 범위 |
| --- | --- |
| 에이전트 | 문서/설정 일치, 코드 보완, 자동 검사, 운영 연결 준비, 초기화 계획과 검증, 관측 전환, Git/배포/복구 절차 |
| 사용자 | 실제 휴대폰·카카오 조작, 부하 테스트 재개 여부, 최종 공개 판단에 필요한 변경 사항 전달 |
| 행사 운영팀 | 당첨자 연락·대학생/동일인 확인·구매/발송·지급 상태 기록·개인정보 기한 관리 |

새 정보가 꼭 필요한 경우에만 묻는다. Notion 공개 여부, 발송일 미정, 수동 대학생 확인은 재질문하지 않는다. 자동 승인 검사가 실제로 특정 작업을 차단하면 그 작업·이유·영향을 구체적으로 설명한다.

## 7. 최종 완료 보고서에 넣을 내용

- 공개 URL, 코드 SHA·PR, 배포 ID, 운영 캠페인·스키마·설정 해시.
- 실제 적용한 행사/수령 일정과 무제한 OFF 결과.
- 베타 초기화 전후 건수, 다른 앱 데이터 불변 확인, 운영 재고 77＋3 및 5,000자리 대조.
- 기능별 검사 결과와 실기기·카카오 확인 기록. 부하 미실행은 별도 표시.
- GA4 운영 수신·동의와 Datadog 운영 로그·감시·알림 상태.
- 운영 관리자 접근 및 신규 참여 중단/복구 증거.
- 발송일 미정, 개별 증빙 확인, 실제 발송·개인정보 정리 등 행사 운영팀의 후속 업무.

완료 보고서는 `배포 준비 완료`, `공개 전환 완료`, `미검증/보류`를 구분한다. 이 계획 문서 작성만으로 어떤 항목도 실행 완료로 바꾸지 않는다.
