0. 목표와 권한 경계
완성된 서비스를 실제 일주일 경품 행사로 운영할 수 있게 준비한다. 실제 값 검토 → 격리 리허설 → 승인된 운영 설정·도메인 적용 → 최종 점검 → 별도 승인 후 공개 순서다.
이 지시서를 전달하는 것만으로 경품 구매·실제 개인정보 열람/수집·실발송·DNS 전환·본행사 공개를 모두 승인한 것으로 보지 않는다. 아래 승인 단계별로 실행한다. 가능한 코드·문서·격리 검증은 먼저 완료한다.
1. 먼저 미정 정책과 실제 자원 확정
공통 문서 D01–D14을 담당자에게 확인하고 승인 기록/설정 버전을 남긴다. 특히 다음을 확정해야 한다.
행사·경품
- 최초 기본 게임권 수량. 최초 지급 1회와 수량 1장을 혼동하지 않는다.
- 행사 시작/종료 정확한 일시, 한국 시간 표시·서버 시간 기준.
- TOP3 각 경품과 전체 예산, 복주머니 상품/수량/확률/소진 처리.
- 랭킹 경품 재고와 즉시 추첨 재고의 구분. 같은 상품이라도 랭킹용 예산/수량을 추첨이 소비하지 않게 한다.
- 실제 경품은 개별 연락·수동 선물 전달. 자동 쿠폰 API나 유료 발송 서비스를 새로 도입하지 않는다.
- 현재 지급 가능한 재고, 예약된 당첨 권리, 실제 지급 기록을 대조할 담당자.
마감·동점·예외
- 동점자 n분할 여부는 원문의 질문이지 확정이 아니다. 임의로 먼저 달성한 사람 승리/추첨/공동 순위/분할을 선택하지 않는다.
- 공동 순위가 TOP3 경계를 넘을 때 수상 대상·지급액·총예산을 어떻게 산정할지 확인한다.
- 행사 종료 전에 시작하고 종료 뒤 완료된 게임, 마감 시점 검증 대기 게임의 인정 기준을 확정한다.
- 부정 기록/재학생 자격 미충족/연락처 미등록·오입력/미응답/수령 기한 경과/차순위·재추첨 여부를 확정한다.
- 복주머니와 랭킹 중복 당첨, 동일 실제 사람이 여러 익명 ID를 가진 경우의 경품 제한을 확정한다. 재학생 인증만으로 중복 당첨 문제가 자동 해결된다고 가정하지 않는다.
- 쿨다운 중·만석 상태의 방문을 다음 사이클에서 어떻게 취급할지와 여러 추천인 간 중복을 확정한다.
- 경품 결과 공유 링크에도 재도전권을 줄지(D14)를 확정한다. 유입 측정과 보상 지급 조건을 별개로 관리한다.
- 게임권 환급과 쿨다운 상태 복구 예외를 확정한다.
자격·개인정보·혜택
- 게임 참여 대상과 경품 수령 대상을 구분한다. ‘국내 대학 재학생’의 정확한 범위와 필요한 확인 방법을 확정한다.
- 학생증/학생 인증 완료 화면/Gemini 가입 캡처 중 무엇을 받을지 확정한다. 재학 확인과 Gemini 등록 확인은 별도 상태다.
- 이름·연락처·학교, 필요시 최소 증빙만 받는다. 계정 비밀번호·주민번호·불필요한 학생증 정보 등을 수집하지 않게 양식/가림 안내를 검토한다.
- 수집 목적·항목·보유기간·열람 권한·처리 근거/필요한 동의·문의/삭제 요청 방법을 운영자가 승인한다. 이 문서는 동의가 불필요하다는 법적 판단을 하지 않는다.
- 증빙을 개별 연락으로 받는지 비공개 업로드로 받는지 정한다. 개별 연락이면 앱에 같은 원본을 다시 복사하지 말고 확인 상태·최소 참조만 보관한다.
- 실제 운영자·대체 담당자·연락 수단·응답 일정·문의처를 확정한다.
- 오픈 시점 공식 Gemini 혜택명·대상·기간·결제수단/갱신 조건 등 안내를 실제 공식 자료와 팀 승인 링크로 재확인한다. 과거 Pro/Plus/1년·금액 문구를 그대로 믿지 않는다.
- Antigravity/Gemini 제작 문구, Google Student Ambassador 운영 표기, 로고·도메인·홍보 카피의 승인 범위를 확인한다.
정책 결정으로 코드가 달라지면 별도 변경으로 남겨 테스트 환경에 먼저 구현한다. ‘3차니까 숫자만 넣으면 된다’고 마감/동점 구현을 생략하지 않는다.
2. 최종 운영 설정 묶음 준비
- 행사·경품·권리·수령·마감·혜택·콘텐츠·개인정보·공유 정책을 하나의 버전 있는 설정 묶음으로 만든다.
- 예시 값/placeholder/미정값이 남으면 오픈 활성화를 막는 점검을 추가한다.
- 예산·수량·확률 합과 소진 처리·랭킹 예산 유보를 검증한다.
- 코드에 테스트 1장/확률/무제한/10시간 단축 시계가 남지 않았는지 확인한다.
- 승인된 캠페인/학교/매체 링크 목록, 공개 Notion 가이드와 CTA, 공식 Gemini 링크를 준비한다.
- 중간 추적 링크가 허용되지 않으면 직접 공식 링크를 사용한다. 측정 편의를 위해 승인 조건을 우회하지 않는다.
- Notion 내용은 사용자의 실제 사례/검증 가능한 사실을 사용한다. 평점과 활용 사례, 취업사진 예시의 사용 허락을 확인한다.
3. 승인 A — 운영 환경 변경 준비
사용자에게 대상 Vercel 팀/프로젝트, Supabase 프로젝트/환경, 도메인, migration·설정 변경 요약, 비용 영향, 복구 방법을 보여주고 운영 설정 적용 범위를 승인받는다.
승인 후:
- 백업/기존 테이블/관리자/정책/재고의 현재 상태를 먼저 확인한다.
- 필요한 migration·환경변수·관리자 권한만 적용한다. Production DB 전체 초기화·삭제·Preview 데이터 복사는 하지 않는다.
- Vercel/Supabase의 실제 사용량·예산 알림·한도 동작과 담당자를 확인한다. 비용 제어를 무작정 해제하지 않는다.
- 관리자 로그인·허용 계정·MFA 등 운영 보안을 사용 가능한 승인 범위에서 설정한다.
- 고정 운영 도메인과 canonical 주소, HTTPS, 쿠키 설정, 인증 리디렉션, 초대 링크, 외부 이동 허용 목록을 점검한다.
- 도메인 구매/DNS 변경은 승인된 도메인·변경 범위 안에서만 수행한다. 도메인이 바뀌면 기존 브라우저 쿠키/참가자가 자동 이전된다고 가정하지 않는다.
- 실경품 이벤트는 여전히 OFF로 둔다. 도메인 준비와 행사 공개는 별도 단계다.
4. 승인 B — 실제 재고·운영 데이터 적용
- 실제 상품·수량·예산·확률·행사 시각 설정을 담당자와 대조한다.
- 승인된 데이터만 적재한다. 수동 전달 방식이면 지급 단위/수량을 관리하고 실제 쿠폰 코드 적재를 필수로 만들지 않는다.
- 랭킹용 재고·예산을 별도 구분하고 실시간/관리자 집계가 일치하는지 확인한다.
- 증빙·연락처는 필요한 운영 과정에서만 수집한다. 에이전트가 참가자를 대신해 개인정보나 수령 사실을 만들어 넣지 않는다.
- 기존 기록이 있다면 유지하며 이관 사유·전후 수량을 기록한다. 테스트 로그가 보이면 필터/격리 여부부터 확인하고 전체 초기화하지 않는다.
- 이후 정책·확률 변경은 승인·변경 시각·버전을 남긴다.
5. 최종 리허설과 QA
격리 환경에서 할 일
- 최종 코드·정책·데이터 구조와 같은 가짜 재고로 전체 동선을 재현한다.
- 1차 부하 결과가 최종 버전에도 유효한지 검토한다. 2차 부활/렌더링/트래킹 변화 또는 3차 마감 계산 변경이 있으면 관련 기능·100~200 VU 대표 부하를 승인된 개발 환경에서 재시험한다.
- Production에는 부하 테스트를 걸지 않는다. 시간·요청·비용 상한은 별도 계획으로 확인한다.
- 새 초대 보상으로 잔액 3장 도달 즉시 10시간 대기/대기 중 사용과 적립 차단/10시간 경계/종료 후 새 방문으로 다시 3장 도달 시 새 대기/누적 3회 제한 없음/장애 환급 시 쿨다운 불변, 복주머니 1회, 재접속, 재고 마지막 1개, 수동 지급 중복을 시험한다.
- 마감 전후·검증 대기·동점·부적격·차순위·미등록 등의 승인된 정책을 시험한다.
- 실제 스마트폰·인앱/외부 브라우저·뒤로가기·네트워크 실패·클립보드·공유·Notion 이동을 확인한다. 접근 불가능한 기기는 미검증으로 남긴다.
- 이벤트·고유 참가자·분모·이탈 추정·직접/Notion 경유 클릭 중복 제거·미연결 관측을 대조한다.
운영 환경에서 할 일
- 승인된 비파괴 스모크 테스트만 실행한다: 정적 페이지·운영 상태·권한·집계·공식 링크·등록/재접속 경로 등.
- 관리자/테스트 계정·행사와 운영 일반 사용자를 구분해 통계 오염을 막는다.
- 운영 경품을 실제 소비하는 지급 시험은 자동 실행하지 않는다. 필요하면 별도 승인된 소액/테스트 대상·금액으로 운영자가 직접 전달하고 비용·실재고 소비를 기록한다.
- 오류 로그·문의 연결·긴급 일시중지·운영자 접근·롤백 절차를 점검한다.
- 앱 롤백이 재고·원장·DB schema를 자동으로 되돌리지는 않는다. 호환성 있는 복구와 수동 조정 절차를 따로 준비한다.
6. 승인 C — 공개 오픈
오픈 전 체크리스트:
- [ ] 모든 필수 운영값 확정, 가짜 쿠폰/무제한/미정 문구 없음
- [ ] 재고·예산·확률·랭킹 분리 확인
- [ ] 마감·동점·자격·수령기한·개인정보 안내 승인
- [ ] 관리자 권한·문의·개별 지급 담당자 확인
- [ ] 재접속·초대·쿨다운·1회 추첨·수동 지급·계측 테스트 통과
- [ ] 최종 버전에 대한 격리 부하·기기 QA 결과 확인
- [ ] 도메인·링크·HTTPS·쿠키·환경 분리 확인
- [ ] 장애 중단·복구·예산 알림·잔여 문제 검토
- [ ] 공개 승인 기록 확보
조건 충족 뒤 사용자에게 Production 배포/승격, 이벤트 ON, 공개 링크·홍보 시작을 별도로 승인받는다. 승인 없으면 ‘오픈 준비 완료·공개 승인 대기’로 종료한다.
소규모 선공개 → 문제 점검 → 홍보 확대는 운영 제안이며 인원·시간을 사용자가 정한다. 임의로 학생회·참가자에게 메시지를 보내거나 외부 채널에 홍보하지 않는다.
7. 오픈 후 종료·수동 지급 운영안
이 문서는 향후 운영 절차를 준비하는 지시다. 에이전트가 백그라운드에서 일주일 내내 감시한다고 약속하지 않는다. 필요 시 실제 앱의 모니터링/서버 작업을 승인된 방식으로 설정한다.
- 오류율·재고·확정된 지급·추천 비정상 패턴·유입/단계별 클릭 집계를 운영자가 확인한다.
- 쿠키/participant 기준 제한만으로 실제 1인 제한을 보장하지 않는다는 한계를 운영팀에 알린다.
- 서버는 마감 이후 요청을 승인 정책대로 차단하고, 지연된 마감 작업도 정확한 cutoff로 최종 후보 스냅샷을 생성하게 한다.
- 최종 랭킹 후보의 기록·동점·자격·연락처를 검토한다. 연락처가 없는 최종 후보는 승인된 미등록 처리 절차로 분류하고 임의 탈락/차순위 지급을 하지 않는다.
- 지급 담당자 지정 → 자격/중복 수령 확인 → 개별 연락 → 선물 수동 전달 → 전달 증빙/결과 확인 → 관리자 지급 완료 순서다.
- 상대에게 선물이 갔는지 불명확하면 ‘확인 대기’로 둔다. 버튼을 재시도했다고 같은 선물을 다시 보내지 않는다.
- 운영자 변경과 실제 지급 상태를 감사 로그에 남긴다. 공개 페이지에 연락처·학교 증빙을 노출하지 않는다.
- 약정된 기간에 연락처·증빙을 삭제/정리하는 실행 절차와 담당자를 정한다. 이미 전달한 경품을 임의로 가용 재고로 되돌리지 않는다.
- 종료 보고는 경품 배정·실지급·보류, 유입/게임/공유/클릭 성과를 분리한다. 외부 가입률·노션 정독률·실제 공유방 수를 측정한 것처럼 쓰지 않는다.
8. 산출물·완료
- 승인된 운영 설정/정책 버전과 실제 재고·예산 대조표.
- 공식 혜택/브랜드/링크 확인 기록, 안내·개인정보·수령 문구.
- 도메인/운영 배포/migration/환경 상태와 승인 기록.
- 최종 기능·정합성·기기·계측·부하/스모크 테스트 결과 및 미검증 목록.
- 관리자 운영·수동 연락/지급·이상 상황·마감·개인정보 정리 매뉴얼.
- docs/phase3-launch-checklist.md, docs/phase3-report.md.
완료 상태는 ‘준비 완료’ / ‘운영 반영 승인 대기’ / ‘공개 승인 대기’ / ‘공개 완료’로 구분한다. 행사 종료·실제 지급 완료는 이후 운영 결과이며, 오픈 당일 미리 완료로 표시하지 않는다.
금지: 원본 Production DB 전체 초기화, 실경품 자동 발송, 승인 없는 구매/확률 변경/동점 결정/공개, 개인정보를 분석/공개 로그로 복사, 운영 제약 해제, 테스트하지 않은 완료 선언.
