- 문서 상태: **수정·개발 계획. 이 문서 저장은 코드 구현, DB 변경, 배포 또는 본행사 오픈 완료를 의미하지 않는다.**

## 0. 목표와 적용 기준

게임 종료 화면을 간결하게 정리하고, 목적별 카카오 공유와 최대 10회 복주머니를 구현한다. 확정 경품·확률을 격리 환경에서 검증한 뒤 실제 운영 설정과 오픈 절차를 진행한다.

진행 순서:

1. 작업 브랜치와 현재 코드·DB 상태 확인.
2. 아래 확정 사항에 따라 화면·공유·추첨 로직 구현.
3. 로컬 및 승인된 Preview에서 기능·재고·권리·모바일 동작 검증.
4. 남은 운영 정책 확정, 운영 설정 묶음과 복구 계획 준비.
5. 승인된 운영 설정·재고·도메인 적용.
6. 최종 검증 후 본행사 공개 승인.

### 문서 간 우선순위

- 이 문서의 최신 확정 사항은 과거의 **참가자당 복주머니 1회**, **친구 방문으로 초대권 지급**, **당첨 자랑 공유에도 게임권 지급**, **랭킹 2등 3만원** 규칙을 대체한다.
- 구현 시 0차 공통 결정표, 1·2차 정책표, 카카오 공유 문서, 사용자 안내와 테스트도 함께 동기화한다. 과거 구현·검증 기록은 당시 기록임을 남긴다.
- 이미 확정된 사항을 미정으로 되돌려 다시 묻지 않는다. 미정인 사항은 7절에 분리했다.
- 베타 무제한 플레이는 현재 사용자 결정대로 유지한다. 본행사 오픈 시 테스트 무제한을 해제하는 운영 설정을 별도로 적용한다.
- 문서 통합만으로 경품 구매, 실제 개인정보 열람·수집, 실발송, DNS 전환, 본행사 공개까지 승인된 것으로 보지 않는다. 기존에 승인된 작업 범위는 유지한다.
- 피그마 화면 렌더러는 이번 작업 범위에서 제외한다.

## 2. 게임 종료 화면과 조작 버튼

### 2.1 게임 종료 화면 정리

- 게임 결과 카드 내부의 `#TeamGemini`, `2026 캠퍼스 챌린지` 배지를 제거한다. 홈 등 다른 화면의 행사 배지를 일괄 삭제하는 요청으로 확대하지 않는다.
- 결과 화면의 랭킹 닉네임 표시·수정 영역을 제거한다. 기존 닉네임 데이터와 랭킹 기록은 보존한다.
- `이번 판` 라벨을 제거하고 점수를 바로 표시한다.
- 점수 글자 크기, 배경 박스 높이, 안쪽 여백, 섹션 간 간격을 줄인다.
- 최고점과 현재 순위는 간결한 한 줄로 정리한다.
- TOP3 안내는 순위와 최종 순위 확정 시점만 간결하게 표시한다. 중복 문구·불필요한 큰 안내 박스를 줄인다.
- 실제 TOP3일 때의 수령 정보 동선은 유지한다. TOP3가 아닌 참가자에게 새 랭킹 수령 정보 입력을 요구하지 않는다.
- 다음 순서의 행동 버튼을 유지한다.
  1. 한 판 더 하기: 게임권 또는 기존 무료 재도전 조건을 충족할 때.
  2. 카카오톡으로 친구에게 공유하고 한 판 더 하기.
  3. 복주머니 확인하기 또는 기존 결과 보기.
- 모바일 카카오 인앱 브라우저의 주소창·하단 메뉴·안전 영역을 고려한다. 작은 화면에서도 스크롤로 모든 버튼에 접근할 수 있어야 하며, 고정 하단 메뉴에 가리지 않아야 한다.

### 2.2 점프 버튼 길게 누르기

- 텍스트 선택, 길게 누르기 메뉴, 이미지 드래그 방지를 **점프 조작 버튼과 그 내부 요소에만** 적용한다.
- 버튼을 누르고 있는 시간으로 동작하는 수퍼 점프, 짧게 탭하는 일반 점프, 손을 뗐을 때의 종료 처리를 유지한다.
- 이름·연락처 등 입력 필드, 다른 화면의 링크·복사·공유 동작에는 전역 차단을 적용하지 않는다.
- 버튼 문구를 이미지로 바꾸는 것은 필수 결정이 아니다. 이미지로 바꾸더라도 메뉴·드래그 방지와 접근성 이름이 필요하다.
- iOS Safari·카카오 인앱, Android Chrome·카카오 인앱에서 탭/꾹 누르기/버튼 밖에서 손 떼기/화면 전환을 확인한다.

## 3. 목적별 공유 문구와 이동 주소

### 3.1 문구 원문과 카드 배치

이미지를 사용하는 카카오 피드 카드의 제목과 설명은 각각 최대 2줄이다. 빈 줄로 표시 공간을 낭비하지 않고, 제목과 설명을 별도 필드로 구성한다. 긴 상품명·참여 인원·큰 글꼴에서도 핵심 내용이 잘리지 않도록 실제 메시지로 확인한다.

현재 문서 기준은 [카카오 텍스트 제약](https://developers.kakao.com/docs/ko/message-template/common#text)이다. 특정 글자 수가 모든 기기에서 노출된다고 보장하지 않는다.

#### A. 일반·경품 홍보·추가 뽑기 공유

사용자 지정 문구:

```text
삼탠바이미 그냥 뿌립니다. 🎁
게임 한 판 하고 꽝 없는 상품 받아가자!
```

- 첫 문장은 제목, 두 번째 문장은 설명에 넣는다.
- 기존 경품 모음 이미지를 사용한다.
- 이동 주소는 공룡 게임 초대 링크다.
- `꽝 없는 상품`과 Gemini 혜택 표현의 실제 제공 조건 검토는 7절의 오픈 전 확인 사항에 포함한다.

#### B. 게임을 더 하기 위한 공유

사용자 지정 원문:

```text
현재 참여자 {N}명, 지금이면 1등 노려볼 만해! 👀 🥇 1등 하면 무신사 5만원권 GET!
```

카드 배치 초안:

```text
제목: 현재 {N}명, 1등 노려볼 만해! 👀
설명: 🥇 행사 종료 1등은 무신사 5만원권!
```

- 문구의 의미는 참여 인원·1등 도전·무신사 5만원권을 유지한다. 짧은 카드 배치안은 시안에서 실제 노출을 확인한다.
- `{N}`은 서버에서 집계한 현재 랭킹 참가 인원을 사용한다. 접속자 수나 뽑기 횟수로 바꾸거나 숫자를 임의로 만들지 않는다.
- 조회 실패 시 숫자 부분을 생략하고 일반적인 1등 도전 문구를 사용한다.
- `주간 1등`, `10만원` 같은 과거 문구를 사용하지 않는다.
- 경품 모음 이미지와 공룡 게임 초대 링크를 사용한다.

#### C. 실제 상품 당첨 자랑

```text
나 {상품명} 뽑았다!
삼텐바이미도 나온대! 너도 해봐!
```

- 첫 문장은 제목, 두 번째 문장은 설명에 넣는다. 불필요한 세 번째 문장·빈 줄은 넣지 않는다.
- `{상품명}`은 서버에서 확인한 본인의 실제 상품 당첨 결과를 사용한다. Gemini 혜택 결과에 실물 상품명을 넣지 않는다.
- 경품 모음 이미지와 공룡 게임 초대 링크를 사용한다.
- 상품 당첨 결과·수령함의 자랑하기에서 사용하며 추가 추첨·게임권 보상은 없다.

### 3.2 버튼별 연결과 보상

| 화면·버튼 | 문구 | 이동 주소 | 공유 보상 |
| --- | --- | --- | --- |
| 게임 종료 후 재도전 공유 | B | 공룡 게임 초대 링크 | 게임권 +1 |
| 랭킹 하단 공유 | B | 공룡 게임 초대 링크 | 게임권 +1 |
| 친구 초대의 재도전 공유 | B | 공룡 게임 초대 링크 | 게임권 +1 |
| Gemini 혜택 결과 후 한 번 더 뽑기 | A | 공룡 게임 초대 링크 | 뽑기권 +1 |
| 실제 상품 당첨 자랑·수령 정보의 당첨 공유 | C | 공룡 게임 초대 링크 | 없음 |
| 일반 경품 홍보·혜택 화면 하단 게임 홍보 공유 | A | 공룡 게임 초대 링크 | 없음 |
| 공식 혜택 링크 옆 공유 | Gemini 혜택 안내 | 승인된 Gemini 공식 혜택 링크 | 없음 |
| 공부법·취업사진 가이드 공유 | 해당 가이드 제목 | 해당 가이드 주소 | 없음 |

- 게임권·뽑기권의 지급 목적은 버튼이 준비될 때 서버에 확정한다. 프론트가 보내는 값만 믿고 보상 종류를 바꾸지 않는다.
- 한 번의 공유로 게임권과 뽑기권을 함께 주지 않는다.
- 혜택·가이드 단독 공유에 공룡 경품 홍보 문구나 게임 이미지를 일괄 적용하지 않는다.
- 기존 수령 정보 임시 저장 → 해당 수령 건에 연결된 전송 확인 → 접수 완료 흐름은 유지한다. 본인 `MemoChat`은 소유 `claim_id`의 `NONE` 접수용 공유에서만 전송 확인에 사용할 수 있고, 접수 확인과 게임권·뽑기권 지급은 별개다.
- 랭킹 수령 정보 공유는 기록 공유로 구분하되, 접수용 공유 자체에 추가 권리를 붙이지 않는 구현안을 사용한다. 재도전용 별도 버튼은 B 규칙을 따른다.

### 3.3 전송 확인 공통 규칙

- 카카오의 인증된 전송 성공 웹훅으로만 공유 보상을 지급한다.
- 일반 1:1 채팅·단톡방을 지원하고, 지원되는 오픈채팅도 기존 정책에 따라 처리한다.
- `MemoChat` 나에게 보내기는 `GAME`·`DRAW` 보상에서 제외한다. 소유 `claim_id`가 결합된 `NONE` 수령 접수 공유만 전송 확인을 허용하며, 추가 권리는 지급하지 않는다.
- 공유창 열기, 링크 복사, 기본 공유창 종료, 친구 방문은 보상 근거가 아니다.
- 같은 공유 요청으로 여러 방에 보내거나 웹훅이 중복 도착해도 보상은 최대 한 번이다.
- 일반 공유창으로 대체된 경우 카카오 전송 확인이 없으면 지급 완료로 표시하지 않는다.
- 게임권은 기존 최대 보유 3장·새 보상으로 잔액 3장 도달 시 10시간 추가 적립 대기를 유지한다. 대기 중 보유 게임권은 사용할 수 있고, 대기 종료 후 새 전송으로 보상받는다.
- 뽑기권에는 게임권의 보유 3장·10시간 대기를 자동 적용하지 않는다. 별도의 행사 전체 10회 상한을 적용한다.
- 한도·대기·실제 상품 당첨 이후에 온 웹훅을 나중에 소급 지급하지 않는다.
- 웹훅 지연, 창 닫힘, 새로고침 후에도 서버의 확인·지급 결과를 다시 조회한다.

## 4. 복주머니 최대 10회 개편

### 4.1 권리와 종료 조건

- 기존 첫 정상 게임 완료 후 첫 복주머니 기회 1회가 열린다.
- 첫 무료 뽑기 포함 행사 전체 최대 10회다. 공유로 추가 가능한 기회는 최대 9회다.
- 게임을 다시 했다는 이유만으로 추가 뽑기권을 주지 않는다.
- 추가 기회 1회는 추가 뽑기용 카카오 공유 전송 성공 1건과 연결한다.
- **Gemini 혜택 결과:** 화면에는 당첨 표현을 사용하지만 내부에서는 혜택 결과로 저장한다. 실제 상품 당첨·재고 소진·수령권 생성으로 계산하지 않는다. 남은 횟수가 있으면 추가 뽑기가 가능하다.
- **실제 상품 당첨:** 해당 참가자의 복주머니 추첨을 종료한다. 추가 뽑기 버튼을 없애고 결과 확인·수령 정보·자랑하기를 제공한다.
- 실제 상품 당첨 이후에는 이미 받은 미사용 추가 기회가 있더라도 다시 뽑을 수 없다.
- 10회 사용 또는 실제 상품 당첨 시, 미리 열어둔 공유창·다른 탭·직접 API 호출로 추가 권리를 만들 수 없어야 한다.
- 참가자당 제한은 쿠키로 복원되는 `participant` 기준이다. 다른 기기·쿠키 삭제까지 포함한 실제 사람 1명의 횟수를 완벽하게 식별한다고 설명하지 않는다.

### 4.2 화면 흐름

```text
게임 완료 → 첫 복주머니 선택 → 복권 긁기 → 결과 저장·확인
  ├─ 실제 상품: 수령 정보 + 자랑하기 / 복주머니 추가 추첨 종료
  └─ Gemini 혜택:
       ├─ 10회 사용: 혜택 적용·기존 결과 확인
       └─ 10회 미만:
            카카오톡으로 공유하고 한 번 더 뽑기
            → 전송 확인 → 뽑기권 1회 적립
            → 새 복주머니 선택 → 다음 회차 결과 확인
```

- 공유 취소·실패는 뽑기 횟수를 사용하지 않는다.
- 공유 보상 후 화면을 나갔다 돌아와도 미사용 뽑기권을 유지한다.
- 새 뽑기권이 있으면 같은 회차를 새로 추첨하지 않고 다음 회차를 생성한다.
- `사용 3/10회`, `남은 뽑기권` 등을 구분해 보여 준다. 아직 공유하지 않은 최대 가능 횟수를 보유권으로 표시하지 않는다.

### 4.3 서버·DB 변경 계획

- 기존 행사·참가자당 단일 추첨 구조를 **행사·참가자·추첨 회차별 결과**로 확장한다.
- 기존 결과·당첨 권리·수령 정보·지급 기록은 보존하며 첫 회차로 연결한다. 배포 때 데이터를 초기화하지 않는다.
- 뽑기권 원장을 게임권 원장과 구분하고, 최초 지급·공유 지급·사용·필요한 오류 복구를 추적한다.
- `사용한 횟수 + 진행 중 예약한 횟수 + 미사용 권리`가 10회를 넘지 않도록 트랜잭션에서 검사한다. 결과 확정 시 예약을 사용으로 한 번만 전환한다.
- 동일 요청 재시도는 같은 회차·같은 결과를 반환한다. 통신 오류로 새 상품을 다시 뽑지 않는다.
- 참가자 상태, 공유 목적·소유권·만료, 실제 상품 당첨 여부, 횟수 상한, 상품 재고를 서버에서 검증한다.
- 상품 예약과 추첨 결과 저장, 추첨 자리 차감은 한 트랜잭션으로 처리한다. 재고 마지막 1개에 동시 요청이 와도 한 참가자에게만 배정한다.
- 실제 상품 당첨 기록과 `claim`을 연결하고, Gemini 혜택 회차에는 실제 상품 수령 요청을 만들지 않는다.
- 수령함·관리자·분석에서 여러 회차를 조회할 수 있게 하며, 참가자 수·추첨 횟수·실제 상품 당첨자 수·Gemini 혜택 결과 수를 구분한다.

### 5.3 추첨 구현안: 5,000회분 비복원 방식

- 63개의 실제 상품 결과와 4,937개의 Gemini 혜택 결과로 구성된 한 묶음을 사용한다.
- 서버의 안전한 난수로 남은 자리 중 하나를 공정하게 선택한다. 결과를 사용한 뒤에는 해당 자리와 수량을 되돌려 넣지 않는다.
- 위 확률표는 **시작 시점 확률**이다. 진행 중에는 `해당 상품 남은 자리 / 전체 남은 자리`로 변한다. 매회 고정 1.26%를 유지한다고 안내하지 않는다.
- 모든 확정 추첨은 상품 또는 Gemini 혜택 자리 한 개를 소비한다. 실패·중복 요청·새로고침은 자리를 추가로 소비하지 않는다.
- 상품별 수량은 상한을 넘을 수 없다. 총 5,000회가 정상 소진되면 실제 상품 배정은 63개이며, 수령 정보 미등록·자격 미충족 등으로 실제 지급 수는 달라질 수 있다.
- 행사 종료 전에 5,000회를 다 사용하지 않으면 상품이 남을 수 있다. 미소진 상품을 임의 재추첨하거나 확률을 몰래 올리지 않는다.
- 5,000회 소진 이후에는 새 실제 상품 묶음을 만들지 않고 Gemini 혜택 결과만 계속 제공한다. 개인별 최대 10회는 그대로 유지한다. 이 경로는 구현·회귀 검사가 아직 남아 있어 공개 전 필수 항목이다.
- GS 5천원권 초과 14개는 운영 재고에서 삭제하며 `VOID` 재고나 이력으로 남기지 않는다.
- 이 설정은 실경품 운영 전 승인된 격리 환경에서 검증한다. 테스트와 운영의 추첨 자리·원장·재고를 섞지 않는다.

- 본행사는 별도 `dino_prod`에서 빈 기록으로 시작한다. 사용자 요청에 따라 베타 참여 기록은 쓰기 차단·백업 복원·삭제 계획 검증 후 범위를 제한해 초기화한다. 기존 앱·인증·관리자·guard·스키마는 유지하며 [최종 실행 계획](final-launch-execution-plan.md)의 전환 순서를 따른다.

### 7.2 마감·동점·예외

- 동점 순위는 같은 점수 중 **먼저 달성한 기록 우선**으로 확정했다. 서버가 게임 완료를 검증해 최고점 레코드를 처음 저장한 `achieved_at ASC`를 leaderboard·snapshot·final payout에 통일했다. 게임 중 프레임별 점수 획득 시각을 쓰는 방식은 아니다. 같은 최고점 재도전은 최초 시각을 유지하며, 시각까지 같으면 participant ID로 순서를 고정한다.
- 종료 전 시작·종료 후 완료한 게임과 마감 시점 검증 대기 게임의 인정 기준은 아직 확정하지 않았다. 동일 시각에 달성한 경우에는 participant_id 같은 최종 정렬키가 필요하다.
- 종료 전에 시작하고 종료 후 완료한 게임, 마감 시점 검증 대기 게임의 인정 기준.
- 부정 기록, 재학생 자격 미충족, 연락처 미등록·오기재·미응답, 수령 기한 경과와 차순위·재추첨 여부.
- 복주머니 실제 상품과 랭킹 상품은 같은 사람에게 **둘 다 지급한다**(2026-09-29 확정). 복주머니 내 실제 상품 1회 제한은 유지하고, 두 수령 요청·지급 기록은 별도로 관리한다.
- 동일 실제 사람이 여러 익명 ID를 만든 경우의 경품 제한과 운영자 확인 절차.
- 기존에 정한 오류·미완료·저점수 게임권 복구를 유지하며, 실제 운영 예외가 생기면 승인된 기준으로 기록한다.

### 7.3 자격·개인정보·혜택·브랜드

- 게임 참여와 경품 수령 자격을 구분하고, 국내 대학 재학생의 정확한 범위·확인 방법을 확정한다.
- 대학생 증빙은 운영팀이 당첨자에게 직접 연락해 재학·휴학 여부와 필요한 증빙을 개별 확인한다(사용자 확정). 별도 사이트 증빙 업로드는 오픈 필수 요건으로 두지 않는다. 대학생 자격 확인과 Gemini 등록은 별도 상태다.
- 이름·연락처·학교와 필요한 최소 증빙만 수집한다. 비밀번호·주민번호·불필요한 학생증 정보는 받지 않도록 양식과 가림 안내를 검토한다.
- 운영자가 개인정보 수집 목적·항목·보유기간·접근 권한·처리 근거·동의·문의 및 삭제 요청 절차를 승인한다.
- 증빙을 개별 연락으로 받으면 원본을 앱에 중복 복사하지 않고 확인 상태·최소 참조만 남긴다. 비공개 업로드가 필요하면 접근·보관 정책을 별도 준비한다.
- 운영자·대체 담당자·연락 수단·응답 일정·문의처를 확정한다.
- 오픈 시점의 실제 Gemini 혜택명·대상·기간·결제수단·갱신 조건을 공식 자료 및 팀 승인 링크와 대조한다.
- Gemini 화면의 당첨 표현은 혜택 적용 완료·실제 상품 지급과 구분한다. 사용자 지정 `1년 무료`, `꽝 없는 상품`, 경품 홍보 문구가 실제 제공 조건과 맞는지 오픈 전에 확인한다.
- Antigravity/Gemini 제작 표기, Google Student Ambassador 운영 표기, 로고·도메인·홍보 카피의 승인 범위를 확인한다.
- 사용자가 맡은 Notion 내부 CTA 게시 여부와 실제 링크 동작을 확인한다. 가이드 내용·평점·취업사진 예시는 사용자 자료와 사용 허락에 근거한다.

## 8. 운영 설정과 단계별 반영

### 8.1 최종 운영 설정 묶음

- 행사·경품·확률·게임권·뽑기권·수령·마감·혜택·개인정보·공유를 버전 있는 설정 묶음으로 준비한다.
- 예시 값·placeholder·미정값이 남으면 본행사 활성화를 막는다.
- 베타 무제한·가짜 재고·임시 확률·단축 시계가 운영 설정에 섞이지 않도록 점검한다. 정상 최초 게임권 1장은 유지한다.
- 승인된 캠페인·학교·매체 링크, 공개 Notion 가이드와 CTA, 공식 Gemini 링크를 준비한다.
- 중간 추적 링크의 사용 범위를 승인된 정책에 맞춘다. 직접 링크를 쓰기로 한 경우 측정을 위해 임의 변경하지 않는다.

### 8.2 승인 A — 운영 환경 변경

대상 Vercel 팀/프로젝트, Supabase 프로젝트/환경, 도메인, DB 변경·설정 요약, 비용 영향, 복구 방법을 구체적으로 준비해 승인 범위를 확인한다. 기존 승인이 충족하는 범위를 다시 요청하지 않는다.

승인된 범위에서:

- 백업·기존 테이블·관리자·정책·재고의 현재 상태를 먼저 확인한다.
- 필요한 DB 변경·환경변수·관리자 권한만 적용한다. Production DB 전체 초기화나 Preview 데이터 무단 복사를 하지 않는다.
- 실제 사용량·예산 알림·한도 동작과 담당자를 확인한다. 비용 제어를 임의 해제하지 않는다.
- 관리자 로그인·허용 계정·MFA 등 운영 보안을 확인한다.
- 고정 도메인·canonical·HTTPS·쿠키·인증 리디렉션·초대 링크·외부 이동 허용 목록을 점검한다.
- 도메인 구매·DNS 변경은 승인된 범위에서 수행한다. 도메인 변경으로 쿠키·참가자가 자동 이전된다고 가정하지 않는다.
- 본행사 활성화는 별도 공개 승인 전까지 OFF로 유지한다.

### 8.3 승인 B — 실제 재고·운영 데이터

- 5절의 실제 상품·수량·랭킹 분리·확률과 행사 시각을 운영 담당자와 대조한다.
- 승인된 데이터만 적재한다. 수동 지급이므로 실제 쿠폰 코드 적재·자동 쿠폰 API·유료 발송 서비스를 필수로 만들지 않는다.
- 이미 배정·접수·지급된 기록은 보존한다. 변경 사유·전후 수량·설정 버전을 기록한다.
- 테스트 로그는 필터·격리 상태부터 확인하고 전체 초기화하지 않는다.
- 참가자를 대신해 개인정보·학생 증빙·수령 사실을 만들어 입력하지 않는다.
- 정책·확률 변경 시 승인·변경 시각·버전을 남긴다.

### 8.4 운영 환경 최종 점검

- 승인된 비파괴 스모크 테스트로 공개 페이지·API 상태·권한·집계·공식 링크·재접속을 확인한다.
- 관리자·테스트 계정과 일반 참가자의 집계를 구분한다.
- 실경품을 소비하는 지급 시험은 자동 실행하지 않는다. 필요한 시험은 승인된 대상·금액·재고 범위에서 운영자가 수행한다.
- 오류 로그·문의·긴급 중단·운영자 접근·복구 절차를 점검한다.
- 앱 롤백만으로 DB·권리·재고가 돌아가지 않으므로 호환 가능한 배포 복구와 수동 재고 조정 절차를 준비한다.

## 10. 오픈 이후 마감·수동 지급

- 실제 운영의 오류율·재고·배정·지급·공유·게임·전환 지표를 운영자가 확인한다.
- 필요 시 승인된 모니터링을 설정하며, 에이전트가 자동으로 행사 기간 내내 감시한다고 약속하지 않는다.
- 서버는 승인된 마감 기준으로 신규 요청을 차단하고, 정확한 마감 시각 기준 최종 랭킹 후보를 보존한다.
- 기록·동점·자격·연락처를 검토하고, 미등록자는 확정한 정책대로 처리한다.
- 담당자 지정 → 자격·중복 수령 확인 → 개별 연락 → 선물 수동 전달 → 전달 증거 확인 → 지급 완료 순서로 처리한다.
- 전달 여부가 불명확하면 확인 대기로 유지하고, 버튼 재시도만으로 중복 발송하지 않는다.
- 운영 변경·수동 지급은 감사 기록에 남긴다. 공개 화면과 분석 로그에 연락처·학교 증빙을 노출하지 않는다.
- 정해진 기간에 개인정보·증빙을 정리하고, 이미 전달한 상품을 임의로 가용 재고로 복원하지 않는다.
- 종료 보고에서는 배정·실지급·보류, 참가자·게임·추첨, 공유 전송·방문, 외부 링크 클릭을 구분한다. Google 실제 가입 완료·Notion 정독·측정하지 않은 공유방 수를 성과로 쓰지 않는다.
