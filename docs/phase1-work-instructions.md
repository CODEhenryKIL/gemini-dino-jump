최신 확정: 최초 기본권 정확히 1장; 초대권 최대 보유 3장(기본권 별도); 새 초대 보상으로 잔액이 3장이 되는 순간부터 10시간 동안 추가 적립 대기; 여러 초대자에게 각각 보상 가능; 대기 중 방문 자동 이월 금지; 게임 장애로 정상 진행/완료하지 못한 경우 소비한 권리 환급; 행사·참가자당 복주머니 1회; 관리자 수동 연락·지급; 쿠키 인증.
0. 목표와 범위
Vercel + Supabase 운영 기반을 구축하고, 지금 확정된 서비스 규칙과 측정을 최소한의 실제 화면으로 끝까지 작동시킨다. 누적 방문 5,000명 이상·피크 동시 이용 100~200명을 설계 목표로 한다. 5,000명 동접으로 해석하지 않는다.
1차 흐름:
접속/익명 복원 → 공룡 점프 → 서버 결과 검증 → 복주머니 1회 → 테스트 수령 신청 → 관리자 수동 상태 변경 → 지표 조회.
독립 흐름:
공유 → 친구 유효 방문 → 게임권 +1 적립 → 재접속·랭킹 재도전. 새 초대 보상으로 초대권 잔액이 3장이 되는 순간부터 추가 적립을 10시간 제한한다. 기본권은 제외한다. 쿨다운이 없는 동안 보유량 3장까지 적립할 수 있으며, 기간별 누적 지급 3장 제한은 사용하지 않는다.
원래 1차에서 ‘나중에 정할 정책’으로 남긴 항목 중 공통 문서의 확정 사항은 이번에 구현한다. 디자인 전면 개선·부활 아이템은 2차, 운영 경품값·실개인정보·공개는 3차다.
1. 접근·코드 확인
- 현재 세션의 GitHub/Vercel/Supabase 접근을 실제 읽기로 확인하고 대상 프로젝트 ID·환경·권한을 기록한다. 다른 대화의 연결 완료 주장을 근거로 접근 가능하다고 단정하지 않는다.
- 최신 커밋과 사용자 미커밋 작업을 확인하고 codex/phase1-clean-start에서 진행한다. 출발점은 게이트러너 제거 직후의 f57c3d1이며, 이전 1차 구현을 유지·보완하는 방식으로 시작하지 않는다.
- 구현 착수 전에 기존 1차 구현을 제거한 코드인지 실제 diff로 확인한다. 이번 코드 복구에서는 최신 1/2/3차 지시서와 Python 설정을 보존하고, 나머지 미커밋 변경은 복구용 Git stash에 보관했다. 새로운 사용자 변경을 임의로 덮어쓰지 않는다. 원격 자원 정리는 코드 복구와 별도다.
- 코드 기준 복구와 Supabase/Vercel 원격 자원 정리는 별개다. 기존 원격 스키마·역할·migration·Preview 설정을 먼저 읽고 기록한다. 로컬 코드 복구를 원격 초기화·데이터 삭제 승인으로 해석하지 않는다.
- 게이트러너 제거 직후 기준 코드의 Python API·JS 프론트·게임 엔진을 재사용한다. 이전 1차 구현의 잔존을 전제로 하지 않으며, 이관만을 이유로 다른 프레임워크로 전환하지 않는다.
- 이전 감사에서 지적한 추천 커밋/URL 파싱, 비정상 게임 종료, 검증 실패 보상, 수령 중복, 행사 중단 미적용, 재요청 응답 불일치를 최신 코드에서 재확인한다.
- 비밀값을 채팅·Git·로그에 노출하지 않는다. 기존 리소스를 재사용하고 새 유료 리소스는 승인받는다.
2. 서비스·배포·DB 기반
- 게이트 러너 전용 화면·메뉴·코드·게임 선택 팝업을 제거하고 기존 주소는 공룡 점프 홈으로 이동시킨다. 공용 자산은 보존한다.
- 정적 화면/자산은 Vercel, API는 Vercel Functions, 영구 데이터는 Supabase PostgreSQL로 분리한다.
- SQLite·/tmp·프로세스 메모리 의존 저장소를 제거한다. DB 실패 시 임시 DB나 가짜 성공으로 대체하지 않는다.
- 스키마·인덱스·제약·DB 함수·권한은 migration으로 관리한다. 요청 시 DB 초기화/데모 재고 삽입은 금지한다.
- 사용자는 현재 운영 중인 서비스가 없음을 확인했고 기존 Supabase 프로젝트 재사용을 선택했다. 새 Supabase 프로젝트는 만들지 않는다. 여기서 프로젝트는 로컬 폴더가 아니라 Supabase의 기존 클라우드 프로젝트를 뜻한다. 기존 승인 대상은 igfrnexknwtiljdqjrbp이며 실행 전에 실제 접근·대상·현재 사용 상태를 다시 확인한다.
- 같은 프로젝트의 기본 postgres DB 안에 공룡 점프 테스트용 비공개 스키마(예: dino_dev)와 전용 DB 역할을 두어 기존 테이블·데이터·접근 권한을 나눈다. 기존 dino 등 구 1차 자원이 남아 있으면 읽어 확인하고, 충돌 없는 테스트 영역을 선택한다. 기존 자원을 자동 삭제·덮어쓰기·재초기화하지 않는다.
- 위 방식은 논리적 데이터·권한 분리다. CPU·메모리·연결 풀과 프로젝트 Auth/Storage는 공유한다. 완전히 독립된 DB 서버 또는 무영향 부하 테스트로 보고하지 않는다. Supabase 대시보드·Data API·Auth·Storage 연동의 제약이 있는 수동 추가 database는 이번 기본안으로 사용하지 않는다.
- 로컬 PostgreSQL과 Vercel Preview를 구분하고, Preview는 위 테스트 스키마에만 필요한 권한을 가진 계정으로 접속한다. 기존 public 데이터·Auth 사용자·Storage 객체를 보존하고, 프로젝트 관리자 키를 게임 서버 접속용으로 사용하지 않는다. 운영 데이터·키와의 분리는 실제 공개를 준비하는 3차에서 별도로 확정한다.
- Supabase Branch도 별도 환경·과금 대상이 될 수 있으므로 자동 생성하지 않는다. 새 유료 리소스가 필요해지면 필요성과 비용을 먼저 제시한다. 원격 테스트 접근이 없으면 로컬 작업을 먼저 진행한다.
- 적합한 RPC/API 또는 서버리스용 DB 풀 연결을 선택한다. 연결 수·요청 크기·시간 제한을 관리한다.
- 한국 이용자/API↔DB 지연을 고려해 리전을 검토하되, 기존 프로젝트의 재생성·리전 변경은 승인 없이 하지 않는다.
- 개인 결과·수령·관리자·쿠폰 응답은 공유 캐시 금지. 정적 자산·비개인 집계만 캐시한다.
- 환경변수 예시, 헬스체크, 배포 식별값, 로그·복구 절차를 남긴다. Production 공개는 하지 않는다.
- Vercel Python 런타임은 공식 지원 버전을 확인해 .python-version과 로컬 안내를 일치시킨다. 이번 기준은 Python 3.12이며 구 1차의 3.11 지정으로 발생한 빌드 오류를 반복하지 않는다. 지원 버전·의존성 설치·API import를 검증하고, 로컬 검사 통과와 실제 Preview 배포 성공을 구분해 보고한다. 코드 기준 복구 시 이 버전 수정이 사라지면 새 1차 구성에 다시 적용한다.
3. 익명 참가자와 보안
익명 복원
- 로딩에서 기존 쿠키를 먼저 확인하고 유효하면 기존 participant를 복원한다. 없을 때만 서버에서 새 participant와 예측 불가능한 인증 토큰을 생성한다.
- 참가자 인증은 쿠키 방식으로 구현한다. HTTPS 환경에서 Secure + HttpOnly + SameSite=Lax를 적용하며, 참가자 인증 토큰을 localStorage나 URL에 저장하지 않는다. 영속 재방문 요구에 맞는 Max-Age/Expires와 서버 만료를 설정 가능하게 하고 최종 기간은 D12로 남긴다.
- 서버에는 인증 토큰 원문 대신 안전한 해시를 보관하는 방안을 적용한다. 공개 추천 코드와 인증 토큰을 구분한다.
- 게임권·초대·쿨다운·복주머니·점수·수령 상태는 DB에서 복원한다. 랭킹은 현재 서버 상태를 조회한다.
- DB 장애/통신 오류/동시 초기화 때문에 신규 ID·기본권을 중복 생성하지 않게 한다.
- 시크릿 탐지, fingerprint, IMEI, 기기 고유값 수집을 넣지 않는다. 쿠키 삭제·다른 기기/브라우저에서 동일인 보장은 하지 않는다.
접근 보호
- Supabase Auth는 관리자 로그인에 사용하고, 로그인 여부와 관리자 역할 검사를 분리한다.
- 참가자용 접근은 인증 쿠키로 서버가 확인한다. 클라이언트가 준 participant_id만 믿지 않는다.
- 개인정보·증빙 참조는 게임·랭킹과 분리하고 공개 API/분석 데이터에서 제외한다.
- RLS, 테이블 권한, RPC 실행 권한과 서버의 소유권 검사를 함께 적용한다. 서버 전용 키의 사용으로 접근 검사가 불필요해지지 않는다.
- 사용자 입력 안전 출력, CSRF/Origin/CORS, 세션 폐기·참가자 제한을 적용한다.
- 신규 익명 생성·추천·시작·추첨·수령의 요청을 제한한다. IP는 보조 신호이며 공용 대학망 이용자를 동일인으로 단정하지 않는다.
- 실제 개인정보 대신 합성 데이터로 시험한다. 실제 수집의 고지·동의·기간 등은 3차 승인 항목이다.
기술 참고: MDN 안전한 쿠키, Supabase 데이터 보호.
4. 게임·재도전권·추천
게임의 공통 정합성
- 서버가 시작 승인·게임권 소비·유효 상태를 확정한다. 정상 시작하지 않은 게임의 종료를 인정하지 않는다.
- 클라이언트와 서버는 동일한 게임 버전/seed/입력 규칙으로 결과를 검증한다. 현재 물리·난이도는 이 차수에서 보존한다.
- 검증 실패 기록을 랭킹·보상에 반영하지 않는다. 실패 사유·오류·의심 기록은 구별한다.
- 시작/종료 재전송은 동일 결과를 반환하고 중복 소비·보상을 만들지 않는다.
- ACTIVE 세션 만료/포기/복구, 결과 재전송·조회, 화면 이탈 시 타이머·리스너 정리를 구현한다.
- D09 최신 확정: 게임 중 장애로 정상 진행·완료하지 못하면 그 게임에서 소비한 게임권을 반드시 환급한다. 서버 오류뿐 아니라 통신 단절·클라이언트 실행 오류도 복구/판정 대상으로 기록하며 서버 장애로만 범위를 좁히지 않는다. 연결이 끊겨 즉시 처리할 수 없으면 재접속 후 서버가 미완료 상태와 오류를 확인해 환급한다.
- 소비와 환급은 같은 게임 세션에 연결하고 중복 요청에도 정확히 1장만 되돌린다. 기본권/추천권의 원래 종류를 보존한다. 추천권 환급은 기존 권리 복원이므로 신규 초대 보상 횟수에 더하지 않는다. 장애 환급으로 쿨다운을 다시 시작·취소하지 않는다. 정상 완료 전 소비한 초대권의 환급 가능 자리까지 보유 한도 계산에 예약하여, 진행 중 새 보상과 환급이 경합해 3장을 넘거나 환급권을 잃지 않게 한다. 해당 임시 예약은 정상 종료/환급 확정 시 정리하고 이용자에게 사용 가능 잔액과 진행 중 상태를 구분해 표시한다.
- 정상 결과가 이미 저장됐는데 응답만 유실된 경우는 먼저 기존 결과를 복원한다. 사용자의 의도적 포기·정상 충돌·검증 거절과 실제 장애를 구별한다. 판정 불가능한 비정상 종료는 확인 필요 상태로 보존하고, 클라이언트의 환급 주장만으로 무제한 권리를 만들거나 증거 없이 부정 이용으로 확정하지 않는다. 장애 판별과 환급의 재접속/동시성 테스트를 포함한다.
- 운영의 무제한 게임권 하드코딩과 우회 플래그를 제거한다. 테스트는 별도 데이터와 명시적 테스트 설정으로만 수행한다.
- D01 최신 확정: 기본권은 행사·참가자별 최초 한 번, 정확히 1장을 지급한다. 재접속으로 다시 주지 않는다. 기본권은 초대권 최대 보유량 3장 및 10시간 쿨다운 계산에서 제외한다. “최초 기본권 이후 재도전” 흐름에 맞춰 기본권이 남아 있으면 먼저 소비하고, 그 뒤 초대권을 소비한다.
유효 초대
- 공유용 링크는 공개 초대 코드로 만들고 인증 토큰/연락처를 URL에 넣지 않는다.
- 친구가 초대 링크로 사이트를 열고, 화면이 실제 보이는 상태로 3초 이상 머무르며 페이지에서 클릭 또는 터치 1회 이상을 하면 서버에 방문 인정 요청을 보낸다. 클릭을 먼저 해도 활성 3초가 충족된 후에 요청한다. 숨겨진 탭의 시간은 세지 않는다. 이 신호는 링크 미리보기와 단순 열람을 구분하기 위한 조건이며, 친구가 게임을 끝낼 필요는 없다.
- 안내 예: “친구가 링크를 열고 화면에서 3초 이상 머문 뒤 버튼을 한 번 누르면, 방문 확인 후 초대한 사람에게 게임권 1장이 적립됩니다.” 이는 현재 문서의 방문 조건 설명이며 실제 친구/사람임을 증명하는 수단은 아니다.
- 서버에서 발급한 방문 식별/단기 nonce, 서버 시간, 인증된 참가자, 코드, 중복을 확인한다. 클라이언트 신호는 봇/동일인이 아님을 증명하지 못하므로 보조 방어와 한도를 둔다.
- HTTP GET/미리보기 크롤러/공유창 열기만으로 보상하지 않는다.
- 행사 + 초대자 + 방문자 관계의 중복을 차단한다. 재전송·다른 share_id·쿨다운 종료로 같은 관계를 새 보상으로 만들지 않는다.
- D07 최신 확정: 같은 방문자가 A와 B의 초대 링크에서 각각 유효 방문 조건을 만족하면 A와 B 모두 +1을 받을 수 있다. 방문자 전체에 최초 초대자 1명만 허용하는 전역 제한을 넣지 않는다. 각 행사·초대자·방문자 쌍의 중복 지급은 계속 금지한다.
- D08 최신 확정: 10시간이 지난 뒤 발생한 새 방문부터 인정한다. 한도 도달/쿨다운 중 들어온 방문은 측정 기록만 남기고 지급·예약·자동 이월하지 않는다. 같은 방문 세션이 쿨다운 종료까지 열려 있었다는 이유로 소급 지급하지 않는다. 대기 중 방문했지만 아직 이 관계로 보상받지 않은 친구가 종료 후 다시 새 방문을 하면 자격을 다시 평가한다. 이미 보상한 관계는 쿨다운 종료 후에도 다시 보상하지 않는다.
- 인정·중복·자기초대·대기 중·한도·기타 거절의 상태와 사유를 구분한다.
초대권 보유 한도/쿨다운 — 2026-09-25 추가 답변 확정
- 최초 기본권 1장과 초대권 잔액을 별도로 기록한다. 초대권은 참가자당 최대 3장 보유할 수 있다. 한도는 누적 발급량이 아니라 현재 보유량이다.
- 쿨다운이 없고 초대권 잔액이 3장 미만이면 새 유효 초대마다 +1한다. 지급 후 잔액이 3장이 되는 순간 cooldown_until을 서버 시각 +10시간으로 설정한다. 사용과 적립을 반복해 잔액이 계속 3장 미만이면 누적 지급 횟수만으로 쿨다운을 시작하지 않는다.
- 쿨다운 중에는 초대권 잔액이 0~2장으로 줄어도 새 초대 보상을 지급하지 않는다. 이미 받은 게임권 사용과 미사용 복주머니 열기는 가능하다. 사용·재접속으로 대기 시간을 다시 시작하지 않는다.
- 10시간이 지나도 남아 있는 게임권은 유지한다. 잔액이 3장인 동안은 보유 한도 때문에 더 적립하지 않는다. 1장을 써 2장이 된 뒤 새로운 유효 초대로 1장을 받아 다시 3장이 되면, 그 시점부터 새 10시간을 시작한다. 자동 충전과 대기 중 방문의 자동 이월은 없다.
- 예시: 09:00 잔액 3장 도달 → 19:00까지 추가 적립 대기. 19:00에 여전히 3장이면 그대로 사용 가능. 19:10 게임 1회로 2장 → 19:20 새 친구의 유효 방문으로 3장이 되면 다음날 05:20까지 대기. 게임 장애 환급은 신규 초대 보상이 아니므로 위 재시작 조건에서 제외한다.
- 지급 수·사용 수·환급 수·종류별 잔액·쿨다운 설정 이력과 cooldown_until을 원장에 기록한다. 게임 시작 승인 시 사용을 기록하되, 장애 환급과 경합하는 보유 한도 처리는 D09의 잠정 예약으로 보호한다.
- 10시간은 서버 기준으로 판정한다. 기기 시각 변경으로 해제되지 않게 한다.
- 방문 인정·참가자/잔액 잠금·중복/쿨다운/보유 한도 검사·원장 +1·확정 이벤트·잔액 3장 도달 시 cooldown_until 설정을 한 DB 트랜잭션으로 처리한다. 마지막 게임권 사용 시각을 쿨다운 시작 시각으로 사용하지 않는다.
- 쿨다운 안내는 새 쿨다운 설정마다 한 번 표시할 수 있도록 서버 상태를 제공한다. 타이머 때문에 화면 전체가 불필요하게 갱신되지 않게 한다.
5. 복주머니·랭킹·수동 지급
복주머니 1회
- 첫 정상 게임 완료 후 행사·참가자 단위로 1회 권한을 생성한다. game_session_id UNIQUE만으로 끝내지 않는다. 여러 게임을 해도 같은 권리를 참조해야 한다.
- 공유와 복주머니는 독립이다. 공유 안 함/친구 미방문/쿨다운 상태에서도 미사용 복주머니를 열 수 있다.
- 추첨 자격·기존 결과·재고 확인 → 결과 확정 → 재고 예약 → 수령 권한을 하나의 짧은 트랜잭션으로 처리한다.
- 상품 종류와 개별/수량형 실제 지급 재고를 분리하고, 가용/예약/지급/만료·무효 이력을 관리한다. 수동 선물 방식이므로 실제 쿠폰 코드 필드를 필수로 만들 필요는 없다.
- CSPRNG 등 적절한 서버 추첨 방식을 검토하고, 확률 정책 버전·결과를 재현이 아닌 감사 가능한 형태로 기록한다. 변경 요청 때 재추첨하지 않는다.
- 긁기는 이미 확정된 결과를 공개하는 연출이다. 재접속·새로고침·다른 주머니 선택 시도에도 결과가 바뀌지 않아야 한다.
- 잠금 충돌과 실제 재고 소진을 구분한다. 초과 배정·음수 재고·동일 수령 중복 처리를 막는다.
랭킹
- 정상 검증된 최고점과 현재 순위를 제공하고, TOP3 진입을 서버에서 판정한다.
- TOP3 진입 시 정보 요청 상태를 남겨 재접속 때도 등록할 수 있게 한다. 이미 입력한 사람은 반복 요구하지 않는다.
- 이름·연락처·학교 입력과 랭킹 기록을 별도로 저장한다. 잠정 TOP3와 최종 수상자를 구분한다.
- 기간·마감·최고점·동점 그룹·최종 스냅샷을 다룰 구조를 마련한다. 동점 정책 미정 상태에서 임의 ID 정렬로 수상자를 확정하지 않는다.
- D03/D04/D10은 테스트값으로 검증하고 운영 마감은 미설정 상태로 둔다.
수동 지급
- 복주머니와 랭킹 수령 건을 유형으로 구분하되 개인정보를 불필요하게 중복 수집하지 않는다.
- 최소 상태: 정보 접수 → 확인 대기 → 연락 완료 → 지급 완료. 보류/부적격/미응답은 별도 기록 가능하게 한다.
- 관리자 담당자·변경 시각·사유·외부 전달 여부를 기록한다. 동일 건을 두 운영자가 중복 처리하지 않도록 처리 중 담당 표시/잠금을 둔다.
- 연락했다는 사실과 선물을 실제 전달했다는 사실을 분리한다. 상태 변경 재요청은 재고·지급 집계를 다시 늘리지 않는다.
- 가짜 쿠폰 자동 생성·자동 문자·자동 카카오 선물 발송·발송 업체 연동은 제거하거나 범위에서 제외한다.
- 학생증/가입 인증 캡처 종류는 D05다. 확인 상태 구조만 마련하고 승인 전 실제 자료를 받지 않는다.
6. 전 단계 트래킹과 관리자 조회
1차에서 수집·저장·집계·최소 화면 표시까지 구현한다. 2차는 새 화면의 노출/클릭 위치를 연결하고 재검증한다.
6-1. 공통 데이터 계약 — 기술 설계 제안
- 이벤트 ID·행사·환경·배포/이벤트 버전·서버 수신 시각·논리 화면·방문 세션·게임 세션을 구분한다.
- 참가자 ID 연결은 서버 인증 정보로 처리한다. 참여자 ID는 가명 식별값이며 완전 익명이라고 단정하지 않는다.
- 유입은 최초 유입과 이번 방문 유입을 분리한다. 초대 보상 귀속과 마케팅 유입 집계를 혼동하지 않는다.
- link_kind: 초기 홍보 / 재도전 초대 / 경품 결과 공유 / 직접·기타. 학교·제휴·매체는 별도 차원으로 둔다.
- 공유 시도는 share_id와 선택 버튼(카카오톡/복사/일반 공유)을 기록할 수 있게 한다. 보상 중복 기준은 share_id가 아니라 초대자–방문자 관계다.
- 알려지지 않은 채널은 ‘알 수 없음’으로 둔다. referrer가 없다고 특정 앱/대화방을 추정하지 않는다.
- 게임·추첨·지급 확정은 서버 이벤트, 클릭·노출은 클라이언트 관측으로 분리한다. 재전송은 중복 제거한다.
- 민감 정보·인증 토큰·학생증·쿠폰·전체 임의 URL/query를 분석 payload에 넣지 않는다.
- Vercel에는 집계용 값만 보낸다. 참가자·개인 추천 코드·개인 결과 경로는 마스킹한다.
- 테스트 환경·합성 계정은 운영 지표에서 제외한다.

6-3. 이탈·시간 정의 — 기술 보완
- 논리 화면 진입과 활성 체류를 기록한다. 백그라운드 시간은 제외한다.
- 로딩 계측은 참가자 API 완료를 기다리지 않고 가벼운 초기 관측 ID로 시작한다. 이후 안전하게 연결하며 미연결 관측은 따로 집계한다.
- 실제 로딩 준비 완료 시각도 진단용으로 남긴다. 사용자의 우선 분석은 성능 순위가 아니라 로딩 중 이탈 시간이다.
- visibilitychange/pagehide/화면 전환 및 제한된 체크포인트를 사용한다. 매 프레임·매초 서버 전송으로 게임을 무겁게 만들지 않는다.
- 브라우저 강제 종료에서 마지막 신호가 누락될 수 있으므로 정확한 종료시각을 보장하지 않는다. 관측/추정/알 수 없음을 구분한다.
- 진행 중 세션과 관측 기간이 끝나지 않은 사용자를 바로 이탈로 세지 않는다. 세션 만료·분석 관측창은 설정과 지표 사전에 명시한다.
- 재도전/공유 미선택은 선택 기능을 건너뛴 것이지 전체 퍼널 이탈이 아니다. 정상 충돌은 게임 완료이고, 미당첨자는 수령 분모에서 제외한다.
- 서버에서 추첨이 확정된 시각과 브라우저에서 결과가 실제 보인 시각을 구분한다.
6-4. Gemini·Notion 집계 — 원문 수치 보완
- CTA 노출 집합 V와 그 노출 이후 관측 기간 내 클릭한 집합 C를 같은 행사/참가자/위치 기준으로 비교한다.
- 클릭률 = |V∩C| / |V|, 미클릭 = |V| - |V∩C|. V가 0이면 0% 대신 계산 대상 없음으로 표시한다.
- 직접 Gemini 클릭과 Notion 경유 클릭을 합칠 때는 합집합으로 중복 제거한다. 가이드 클릭 자체는 Gemini 전환으로 세지 않는다.
- Notion으로 나가는 클릭을 Notion 페이지 열람·체류로 이름 붙이지 않는다. 별도 분석 연동 없이 원격 페이지 내부 이벤트를 관측한다고 가정하지 않는다.
- Notion → 우리 도메인 → Gemini 경유는 원문처럼 ‘가능하면’ 구현한다. 공식 링크에 임의 파라미터 삽입 금지; 프로그램이 중간 링크를 허용하는지 확인하고 승인 전에는 비활성화한다.
- 단순 리디렉션 GET만 관측 가능한 경우는 ‘경유 요청/추정 방문’으로 기록한다. 확인된 버튼 클릭과 같은 지표로 합치지 않는다.
- 승인될 경우 목적지는 허용 목록으로 고정한다. 공개 GET/미리보기 기록과 실제 클릭 신호를 구분하고, 인증 토큰이나 개인 식별값을 Notion URL에 넣지 않는다.
- 같은 도메인·브라우저 쿠키를 안전하게 이어갈 수 있을 때만 참가자 연결을 시도한다. 인앱→외부 브라우저 전환 등 미연결 건을 임의로 합치지 않는다.
- Gemini 링크 클릭은 도착/학생 인증/혜택 등록 성공이 아니다.
기술 참고: MDN pagehide, MDN share, Vercel 분석 개인정보, Notion 페이지 분석.
6-5. 최소 관리자 화면
- 기간·유입 유형·채널·환경·콘텐츠·당첨 여부로 조회한다.
- 각 지표에 분모·고유 참가자/이벤트 건수·관측기간·갱신 시각·추정 여부를 표시한다.
- 업무 원장과 집계가 일치하는지 합성 데이터로 대조한다.
- 연락처/증빙 관리와 분석 화면은 권한·표시를 분리한다.
- Realtime은 필요할 때 관리자 집계에만 제한한다. 일반 참가자에게 개인정보/재고 테이블 구독을 열지 않는다.
7. 기능·정합성·보안 테스트
최소 자동 테스트:
1. 빈 DB migration, 기존 DB 업데이트, 테스트 데이터 분리.
2. 쿠키 기반 익명 생성/복원, 최초 기본권 정확히 1장·중복 지급 방지, 장애 후 새 ID 발급 방지. 기본권이 초대권 보유 한도 3장 계산에 포함되지 않음.
3. 시작 승인/검증/랭킹, 잘못된 상태·타인 ID·검증 실패 보상 거부.
4. 같은 관계 반복 방문은 1회만 보상. 같은 친구의 A/B 링크 유효 방문은 각 초대자에게 +1 가능. 동시 100개 유효 방문에서도 초대권 보유 3장 이하 및 새 쿨다운 중 추가 적립 없음.
5. 적립 후 잔액이 3장이 되는 순간 쿨다운 1회 설정. 대기 중 사용은 가능하나 잔액 0~2장이어도 적립 금지. 종료 후 3장 유지 → 1장 사용 → 새 초대 +1로 3장 도달 시 새 10시간 설정. 잔액 3장 미만으로 사용/적립을 반복할 때 누적 지급 3장만으로 차단하지 않음.
6. 10시간 경계 전/후, 대기 중 방문의 지급/예약/자동 이월 없음, 종료 후 새 방문 자격 확인, 이미 보상한 관계 재보상 없음. 자동 충전 없음. 제어된 테스트 시계로 검사하되 운영 시간 조작 경로를 노출하지 않음.
7. 복주머니를 먼저 열고 이후 재도전 가능, 여러 세션/새로고침에도 행사·참가자당 추첨 1개.
8. 마지막 경품 1개 경쟁, 재고 초과/중복 수령 방지, 결과 재조회 일관성.
9. TOP3 등록·재등록·순위 하락, 동점 미정 상태에서 임의 수상 확정 없음.
10. 관리자 인증/소유권/개인정보/RLS, 수동 연락·지급 상태 중복 변경.
11. 로딩·게임·긁기 중 이탈 및 복구, 이벤트 중복/분기/CTR 집합 대조.
12. 게이트 러너 제거, 기본 브라우저 E2E.
13. 서버/통신/클라이언트 장애로 게임 미완료 시 원래 종류의 게임권 1장 환급, 재접속 처리, 중복 환급 방지, 결과 응답 유실 복원, 환급 시 신규 초대 보상 횟수·쿨다운 불변. 진행 중 신규 초대/환급 경합에서도 보유 3장 상한·환급 보장 및 잠정 예약 정리 확인.
14. Python 3.12 의존성 설치/API import/기본 회귀 검사. 이후 승인된 Preview에서 빌드·실행 확인; 로컬 검사를 배포 성공으로 보고하지 않음.
8. 원격 부하 테스트
- k6 등 로컬 부하 도구로 승인된 Vercel Preview와 기존 Supabase 프로젝트 안의 공룡 점프 전용 테스트 스키마·제한된 계정에 대해 실제 실행한다. 새 프로젝트나 유료 Branch를 만들지 않는다. 기존 데이터·실경품·실개인정보를 테스트 대상으로 사용하지 않는다. 같은 프로젝트의 DB 자원과 연결 풀을 공유하므로 기존 프로젝트 전체 부하도 관측하고, 실행 전 운영 서비스가 새로 생기지 않았는지 확인한다.
- 초기 안전 제안 상한은 이 차수 원격 실행 합계 30분·API 30,000회다. 사전 요청수·쓰기·분석 이벤트·기본 포함량/추가비 영향을 계산한다. 유료 리소스와 상한 증가는 승인받는다.
- 5,000명 합성 참가자와 적절한 게임 기록으로 조회·집계를 검증한다.
- 10 VU 1분 → 50 VU 2분 → 100 VU 3분 → 200 VU 5분, 별도 0→200 VU 순간 부하 30초를 상한 안에서 수행한다.
- 플레이 대기시간과 유효 로그를 포함한다. 200 VU는 200 RPS가 아니다. 검증을 대부분 실패시키거나 캐시된 조회만 요청해 성공을 주장하지 않는다.
- 한 참가자당 복주머니 1회·재도전 한도를 유지한다. 부하를 위해 테스트 보상/검증 로직을 우회하지 않는다.
- 입장, 게임 종료·추첨 집중, 중복 요청·재고 경쟁을 분리한다.
- p50/p95/p99, 실제 처리량, 예상 밖 오류·타임아웃, 접근 가능한 DB 연결/잠금/쿼리·함수 상태와 비용 영향을 보고한다.
- 초기 제안 목표: 일반 API p95 1초 이하, 결과 검증/추첨 p95 2초 이하, 예상 밖 실패율 1% 미만, 중복 지급/초과 재고 0건. 목표 미달 시 원인과 재시험을 보고한다.
- 재고/권한 오류 발견 시 중단한다. 요청 제한으로 의도적으로 거부한 부정 요청은 정상 시나리오 오류와 분리해 보고한다.
- 원격 권한이 없으면 로컬 결과와 스크립트만 납품하고 원격 미검증으로 표시한다. 1차 완전 검증 완료라고 쓰지 않는다.
- API 부하와 실제 기기 FPS는 별도다. 이번은 기준 성능이며 2차 변경 후 다시 검증한다.
기술 참고: Grafana k6 테스트 유형.

10. 최신 결정과 참고 근거
- 이 개정은 사용자 주석의 확정 내용을 반영한 지시서 수정이다. 코드 기준 복구는 위 시작 기준에 기록한 대로 완료됐지만, Supabase 테스트 영역 생성·서비스 규칙 구현·배포는 아직 실행하지 않았다.
- D01(기본권 1장), D07(여러 초대자 각각 보상), D08(쿨다운 종료 후 새 방문 인정), D09(게임 장애 환급)의 이전 미정 표시는 위 최신 결정으로 대체한다. D09의 장애 판별/복구 기술 설계는 검증 결과와 함께 기록한다. 추가 잔액 정책 질문은 최대 보유 3장·새 초대 보상으로 3장 도달 시 재대기 규칙으로 확정됐다.
- 공통 결정표와 2/3차 문서의 “3장 모두 사용 후 쿨다운”, “한 사이클 누적 지급 3장 제한”, “기본권 수량 미정”, “기존 1차 구현 보완”, “별도 원격 프로젝트 필수” 문구는 이번 사용자 확정과 충돌하는 범위에서 적용하지 않는다. 해당 차수 착수 시 문서 간 일치를 재확인한다.
