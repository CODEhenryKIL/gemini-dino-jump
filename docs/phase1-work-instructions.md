# 1차 작업: 공룡 점프의 Vercel + Supabase 운영 기반 구축

첨부된 상세 작업 지시서를 기준으로 아래 작업을 실제 수행해줘.
설명·설계·스크립트 작성으로 끝내지 말고, 가능한 계정 연결과 설정,
코드 수정, DB migration, Preview 배포, 테스트 실행, 결과 보고까지 진행해줘.

대상 저장소:
https://github.com/CODEhenryKIL/gemini-dino-jump

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 목표와 작업 범위
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

이 서비스는 공룡 점프 게임을 통해 경품과 친구 초대,
Gemini 학생 혜택 안내를 제공하는 이벤트 사이트다.

목표:
- 누적 방문자 5,000명 이상
- 피크 동시 이용자 100~200명
- 게임 중 서버 통신 때문에 조작이나 화면 진행이 멈추지 않는 구조
- 실제 경품 운영에 필요한 재고·보안·기록 구조
- 사용자 행동 지표를 운영자가 확인할 수 있는 상태

이번 1차의 최종 목표:
격리된 개발/Preview 환경에서
접속 → 게임 → 결과 검증 → 테스트 추첨 → 테스트 수령
→ 관리자 확인 → 지표 확인이 정상 작동하고,
원격 부하 테스트 결과까지 확보하는 것이다.

확정 사항:
- 게이트 러너를 삭제하고 클래식 공룡 점프만 남긴다.
- Vercel에 웹/API를 배포한다.
- 영구 데이터는 Supabase PostgreSQL에 저장한다.
- 기존 Python 백엔드와 JavaScript 프론트엔드를 우선 재사용한다.
- 기존 공룡 점프의 디자인·물리·조작·난이도는 최대한 유지한다.

이번에 임의로 확정하지 않을 사항:
- 기본 게임권 수
- 친구 초대 및 점수 비교 보상
- 최종 경품 확률·수량
- 랭킹 경품과 마감 규칙
- 학생 인증 방법
- Gemini 가입 확인 조건
- 디자인·마케팅 고도화

미정 정책은 설정값으로 분리한다.
개발에 필요한 테스트 값은 명시해 사용하되,
실제 운영 정책으로 확정하거나 실경품 지급을 켜지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. 실제 연결 상태 확인
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- 최신 코드와 기존 사용자 변경을 확인한 뒤 작업 브랜치를 만든다.
- 현재 Codex 세션에서 GitHub·Vercel·Supabase 접근 권한을 확인한다.
- 다른 대화에서 연결됐다는 설명만으로 사용 가능하다고 가정하지 않는다.
- 대상 Vercel 프로젝트와 Supabase 조직·프로젝트 ID를 확인한다.
- 기존 Git 연결, 환경변수, 리전, 요금제, 프로젝트 수를 확인한다.
- 관련 없는 다른 서비스와 프로젝트는 수정하지 않는다.
- 기존 리소스를 우선 활용하고 유료 리소스를 중복 생성하지 않는다.

접근 권한이나 자격증명이 부족하면 가능한 코드 수정·로컬 테스트를
먼저 진행하고, 사용자가 직접 해야 하는 설정만 따로 정리한다.

비밀값을 채팅이나 Git에 남기지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
3. 공룡 점프만 남기기
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- 게이트 러너의 코드·화면·메뉴·전용 라우트·전용 안내를 제거한다.
- 게임 선택 팝업을 제거하고 홈에서 공룡 점프로 바로 연결한다.
- 공룡 점프에서 함께 사용하는 에셋은 보존한다.
- 기존 /gate_runner.html 주소는 공룡 점프 홈으로 이동하게 한다.
- 두 게임 운영을 전제로 한 랭킹·경품 문구를 정리한다.
- 게임권 표시는 서버 잔액을 사용하고 ‘무제한’ 하드코딩을 제거한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
4. SQLite → Supabase 이전 및 Vercel 배포
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

데이터:
- SQLite와 /tmp 파일을 서비스 영구 저장소로 사용하는 구조를 제거한다.
- 참가자·게임 세션·게임권·최고 기록·추천·행사 설정·경품·추첨·수령·
  관리자 로그를 PostgreSQL로 이전한다.
- 스키마·인덱스·외래키·고유 제약·접근 권한·DB 함수를 migration으로 관리한다.
- 서버 요청 중 DB 자동 초기화나 데모 재고 자동 삽입을 하지 않는다.
- DB 장애 시 SQLite·메모리·가짜 성공 응답으로 대체하지 않는다.

환경:
- 로컬 개발은 Supabase CLI의 로컬 PostgreSQL을 우선 사용한다.
- 원격 Preview는 운영과 분리된 승인된 개발 DB에 연결한다.
- Preview에 운영 DB 키를 넣지 않는다.
- 운영 DB에 test=true만 붙여 사용하는 것을 환경 분리로 취급하지 않는다.
- 기존 테스트 기록·가짜 쿠폰을 운영 DB에 자동 복사하지 않는다.
- 추가 유료 개발 프로젝트가 필요하면 생성 전에 승인받는다.

배포:
- 정적 파일은 Vercel 정적 배포, API는 Vercel Functions로 구성한다.
- 기존 스택에 맞는 Supabase API/RPC 또는 PostgreSQL transaction
  pooler 연결을 선택하고, 선택 이유를 문서화한다.
- 서버리스 인스턴스별 과도한 DB 연결을 방지한다.
- 한국 이용자와 API↔DB 지연을 고려해 서울 리전을 우선 검토한다.
- 개인정보·쿠폰·개인 결과 응답은 공용 캐시에 저장하지 않는다.
- 기준 도메인과 초대·혜택 링크는 설정값으로 관리한다.
- 환경변수 예시, 헬스체크, 로그 확인, 배포·복구 절차를 제공한다.
- 앱 롤백과 DB migration 복구는 별개로 설명한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
5. 경품·게임권·추천·수령의 정합성
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- 상품 종류와 실제 지급 가능한 재고를 분리한다.
- 재고의 가용·예약·지급·만료·무효 상태와 변경 이력을 관리한다.
- 추첨 자격 확인 → 결과 확정 → 재고 예약 → 수령 권한 생성을
  하나의 짧은 DB 트랜잭션으로 처리한다.
- 게임권 사용·게임 종료·추천 보상·수령에도 중복 방지를 적용한다.
- 같은 요청을 반복해도 기존 결과를 반환하고 권리·재고는 한 번만 변경한다.
- 기존 결과를 반환할 때도 본인 소유 여부를 먼저 검사한다.
- 재고 1개에 여러 요청이 몰려도 최대 1개만 배정한다.
- 실패하면 전체 롤백하고, DB 확정 뒤에 성공 응답을 보낸다.
- 실제 발송 없이 지급 완료로 처리하지 않는다.

이전에 지적된 아래 문제를 최신 코드에서 재확인하고 수정한다:
- 추천 관계 저장 후 커밋 누락
- 추천 링크 경로와 코드 파싱 불일치
- 저장 성공 여부와 무관한 추천 적용 안내
- 정상 시작·게임권 차감 없이 종료·보상으로 넘어가는 경로
- 검증 실패 게임의 랭킹·추천·추첨 반영
- 반복 수령 요청에 따른 중복 지급 집계
- 응답 쿠폰과 DB 저장 쿠폰 불일치
- 만료·필수 정보·소유권·상태 검사 누락
- 행사 중단·참가자 차단 상태의 API 미적용
- 최초 요청과 재요청 응답 형식의 불일치

테스트 경품:
- 가짜 재고와 가짜 발송 공급자로 전체 흐름을 검증한다.
- 자격 검증·재고 잠금·중복 방지 로직 자체는 우회하지 않는다.
- 실제 쿠폰 구매·적재·발송은 하지 않는다.
- 운영 환경에서 가짜 쿠폰을 발급하지 못하게 한다.
- 실경품 설정과 운영 정책이 미완성이면 실제 지급은 비활성화한다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
6. 개인정보·관리자 보안·오류 복구
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

보안:
- 수령 개인정보와 게임·랭킹 데이터를 분리한다.
- 이번에는 합성 개인정보만 사용한다.
- Supabase Auth 기반 관리자 로그인과 서버 측 관리자 권한 검사를 구현한다.
- 로그인한 모든 사람을 관리자로 취급하지 않는다.
- RLS·테이블 권한·RPC 실행 권한을 함께 설정한다.
- 서버용 키로 DB에 접근해도 소유권·관리자 권한 검사를 생략하지 않는다.
- 이름·연락처·주소·세션 토큰·쿠폰·서버 키를 로그/분석/Git에 넣지 않는다.
- 사용자 입력의 안전한 출력, 요청 크기·로그 길이·숫자 범위 제한,
  세션 관리와 인증 방식에 맞는 CSRF/Origin/CORS 보호를 적용한다.
- 익명 생성·게임 시작·추천·추첨·수령에 요청 제한을 적용한다.
- 관리자 변경에 담당자·시각·대상·변경 내용·사유를 기록한다.

오류 복구:
- 새로고침·이탈 후 ACTIVE 세션이 영구적으로 재참여를 막지 않게 한다.
- 결과 전송 실패 시 같은 세션으로 재전송하거나 기존 결과를 조회한다.
- 미확인 추첨·미완료 수령을 다시 찾을 수 있게 한다.
- 화면 이탈 시 타이머·이벤트·불필요한 요청을 정리한다.
- 오래된 비동기 응답이 현재 화면을 덮어쓰지 못하게 한다.
- 연결 실패·저장 대기를 표시하고 사용자에게 재시도 방법을 제공한다.
- 클라이언트와 서버 검증기의 게임 규칙·버전을 맞춘다.

성능:
- 게임 프레임·점프마다 DB 요청이나 네트워크 대기를 넣지 않는다.
- 명백한 이미지·DOM 병목은 개선하되 게임 디자인·물리는 임의로 바꾸지 않는다.

7. 지표 수집 + 관리자 조회 화면
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

이벤트 코드만 넣지 말고 운영자가 실제 숫자를 볼 수 있게 구현한다.

Vercel Web Analytics:
- 현재 플랜·추가 과금 여부를 확인하고 허용된 범위에서 활성화한다.
- 방문자·페이지뷰·유입·기기 등 제공되는 지표를 연결한다.
- SPA의 주소가 바뀌지 않는 화면 이동도 논리 화면 단위로 측정한다.
- 자동·수동 페이지뷰의 중복 집계를 막는다.
- participant_id·개인 추천 코드·세션 토큰·개인정보는 보내지 않는다.

Supabase 핵심 이벤트:
- page_view
- page_engagement
- game_start
- game_finish_verified / game_finish_rejected
- draw_open / draw_result
- claim_start / claim_submit
- invite_copy / invite_share_open
- referral_qualified / referral_reward_granted
- gemini_link_click
- 개인정보를 제거한 오류 이벤트

이벤트 원칙:
- 서버 확정 결과와 클라이언트 버튼 클릭을 구분한다.
- 참가자 연결은 서버 인증 정보로 확인한다.
- 재전송 이벤트는 중복 제거한다.
- 업무 기록은 DB에 남기고 외부 분석 전송 실패가 게임·수령을 막지 않게 한다.
- 개발·Preview·부하 테스트 데이터는 운영 집계에서 제외한다.
- 매 프레임 이벤트를 보내지 않는다.
- Gemini 외부 링크에 승인되지 않은 추적 파라미터를 추가하지 않는다.

지표 해석:
- 체류시간은 화면이 보이는 동안의 활성 시간을 기준으로 한다.
- 마지막 전송은 유실될 수 있으므로 이탈은 관측 데이터 기반 추정으로 표시한다.
- 공유창 열림은 실제 공유 완료가 아니다.
- Gemini 링크 클릭은 외부 가입 완료가 아니다.
- 정상 충돌은 게임 오류가 아니다.
- 미당첨자의 수령 미진입을 이탈로 계산하지 않는다.
- 익명 참가자 ID와 실제 사람 수를 동일하게 표현하지 않는다.

관리자 화면:
- 기간별 방문/참여와 화면별 조회·활성 체류시간·추정 이탈
- 유입 채널별 참여와 Gemini 클릭
- 게임 시작 → 정상 종료 → 추첨 → 당첨 → 수령 접수 퍼널
- 추천 유입·유효 추천·보상
- 경품별 가용·예약·지급·실패 현황
- 지표 정의·분모·기간·갱신 시각

UTC 저장·한국 시간 표시를 일관되게 적용하고,
알려진 테스트 데이터로 집계값을 대조한다.
모든 플레이어에게 Realtime 연결을 열지 않는다.

8. 기능·보안·브라우저 테스트
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

다음을 실제 실행하고 결과를 남긴다:
- 빈 DB migration 적용과 전체 정상 플로우
- 추천 저장과 보상 1회 지급
- 잘못된 상태·검증 실패·만료·타인 ID 요청 거부
- 동일 요청의 반복·동시 재전송
- 마지막 재고 경쟁과 중복 지급 방지
- 서버 저장 후 응답 유실·재조회·복구
- 게임 중 새로고침·화면 이동·탭 숨김·재개
- 일반 사용자의 관리자/타인 개인정보 접근 차단
- 행사 중단·재고 소진·DB 장애
- 분석 이벤트 중복 제거와 집계 일치
- 게이트 러너 제거와 공룡 점프 정상 동작

Preview 브라우저 E2E도 실행한다.
모바일 화면 에뮬레이션과 실제 휴대폰 검증은 구분한다.

9. 부하 테스트를 실제 실행
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

환경:
- 로컬 실행 k6 등 무료 도구를 우선 사용한다.
- Vercel Preview + 별도 개발 DB + 가짜 경품에서만 실행한다.
- 대상 URL/DB ID를 검사하고 Production에는 실행하지 않는다.
- 테스트용이라는 이유로 정상 검증·재고 로직을 우회하지 않는다.
- 필요한 권한/개발 DB가 없으면 로컬 테스트와 스크립트를 준비하고,
  원격 검증은 미완료로 보고한다.

비용·범위:
- 실행 전 예상 API 호출·DB 쓰기·이벤트 수와 비용 영향을 계산한다.
- 초기 원격 테스트는 누적 30분, API 호출 총 30,000회 이내로 제한한다.
- 무료 도구를 사용한다고 클라우드 비용까지 무료라고 가정하지 않는다.
- 유료 테스트 서비스·무제한 재실행·자동 사양 증설은 하지 않는다.

시나리오:
- 합성 참가자 5,000명 규모 데이터로 조회·집계 점검
- 10 VU 1분
- 50 VU 2분
- 100 VU 3분
- 200 VU 5분
- 별도 0→200 VU 순간 부하 30초

실제 사용자처럼 세션 시작, 플레이 대기, 유효 종료 제출,
테스트 추첨, 일부 수령/랭킹 조회를 구성한다.
200 VU를 200 requests/second로 해석하지 않는다.
입장 집중·종료/추첨 집중·중복 요청·재고 경쟁을 각각 확인한다.

측정:
- API별 p50/p95/p99 응답시간
- 실제 요청률·예상하지 않은 실패율·타임아웃
- 함수/DB 오류·연결·잠금 대기·느린 쿼리
- 재고 초과 배정과 중복 지급
- 지표 수집에 따른 추가 부하
- 실행 지역·기간·데이터 규모·cold/warm 조건

초기 목표:
- 조회·일반 API p95 1초 이하
- 결과 검증·추첨 API p95 2초 이하
- 예상하지 않은 실패율 1% 미만
- 중복 지급·재고 초과 배정 0건

목표는 검증 기준이며 성능 보장이 아니다.
미달하면 원인·수정·재시험 결과를 보고한다.
심각한 정합성·보안 오류가 발생하면 즉시 중단한다.

API 부하 테스트와 게임 FPS 테스트는 별개다.
실기기에서 확인하지 못한 성능은 미검증으로 표시한다.

10. 최종 산출물과 완료 보고
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

5. 관리자 접근과 지표 조회 방법

9. 남은 권한/외부 설정·미검증 항목·2차 정책 결정 목록

docs/phase1-readiness-report.md에 결과를 모은다.

완료 보고는 반드시 구분한다:

- 승인·권한 대기
- 미검증 또는 목표 미달

스크립트만 작성하거나 로컬에서만 시험한 상태를
‘원격 동접 200명 검증 완료’라고 보고하지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- Production DB 삭제·초기화·테스트 데이터 투입

- 실제 도메인/DNS 변경·도메인 구매

나머지 구현과 테스트는 가능한 범위까지 끝내줘.
