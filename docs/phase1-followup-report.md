초대권 규칙은 기존 확정대로 **새 보상으로 잔액이 3장이 되는 순간부터 10시간 추가 적립 대기**다. 기본권은 별도이고 대기 중 이미 가진 권리는 사용할 수 있다. 원문·차수별 문서의 충돌 문구를 정리했으며 서버의 기존 쿨다운 규칙은 변경하지 않았다.

### 수령 데이터 보정

새 migration: `supabase/migrations/20260925125939_add_awaiting_claim_information_status.sql`.

- 기존 `INFORMATION_RECEIVED` 중 제출 시각·연락 정보가 없고 담당자·검증·업무 처리 흔적도 없는 최초 버전 행만 입력 대기로 변경한다.
- 처리 중·종결된 기존 상태는 보존한다. 연락 정보는 있으나 제출 시각이 없었던 행은 연락 정보 생성 시각으로 보정한다.
- 관리자 PATCH는 실제 연락 정보와 제출 시각이 모두 있어야 한다. 누락된 기존 행도 상태값만으로 우회할 수 없다.
- 늦은 정보 제출·반복 제출은 기존 처리 상태를 되돌리지 않는다. 프론트는 `PAID`·`INELIGIBLE`을 제외한 미입력 상태에서 입력 버튼을 제공하므로 기존 보류·미응답·연락 완료 건도 상태 역행 없이 복구할 수 있다.
- 새 코드의 필수 스키마 버전도 같은 값으로 올렸다. 기존 원격 DB에 새 코드만 먼저 배포하지 않는다.

### 지표 해석

- `sharing`의 기존 전체 합계는 호환성을 위해 유지한다. 관리자 초대 영역과 Gemini 영역은 각각의 목적별 합계만 사용한다. 목적을 확인할 근거가 없는 이벤트는 별도 표시한다.
- 공유창 닫힘은 실제 메시지 전송 완료를 의미하지 않으며 `actual_delivery=unknown`을 유지한다.
- CTR의 클릭은 같은 참가자·위치에서 노출 이후 관찰창 이내에 발생해야 한다. 전체 고유 참가자는 여러 위치를 합산하지 않고 다시 중복 제거한다.
- 조회 종료 시각은 제외 구간이므로 노출 관찰창 끝이 조회 종료와 정확히 같으면 pending이다. 종료를 지난 조회에서만 해당 경계 클릭까지 포함해 확정한다.
- pending은 해당 조회 범위에 관찰 완료 노출이 없고 진행 중 노출만 있는 참가자다. 나중의 새 노출이 과거 완료 전환을 지우지 않는다.
- 클릭은 외부 공식 링크를 누른 기록이며 Gemini 인증·혜택 등록 완료로 표시하지 않는다.

## 반영 범위와 남은 작업

- 최초 보완·로컬 검증 단계에서는 원격 Supabase, Vercel 설정·배포, GitHub main과 PR을 변경하지 않았다. 이후 사용자 요청으로 보완 브랜치의 커밋·푸시·PR·main 병합을 진행한다. GitHub 반영이 원격 DB·배포 적용을 뜻하지는 않는다.
- 현재 Preview에는 이전 코드가 남아 있다. 이번 브랜치의 보완은 로컬 코드·migration·검증 완료 상태다.
- 원격 반영 때에는 쓰기 중단·보정 대상 확인, migration 적용, 새 Preview 연결, 실제 수령·관리자 흐름 확인 순서로 진행한다. 구체적인 절차는 [운영 절차](phase1-runbook.md)를 따른다.
- 추가 콘텐츠 분류·카드별 클릭률·1인당 지표, 2차 화면 완성, 실제 재학생 검증 및 지급 조건·운영값 확정은 후속 범위로 남는다.
- 이전 200명 테스트의 0건 오류 기록과 일반 API p95 1초 목표 미달은 그대로 보존한다. 이번 보완으로 원격 성능이 개선됐다고 주장하지 않는다.
