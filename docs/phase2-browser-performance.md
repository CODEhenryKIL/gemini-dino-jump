# Phase 2 로컬 브라우저 성능 확인

측정일: 2026-09-26 KST. 실제 Codex 내장 Chromium 153 / macOS. localhost Python 서버에서 현재 게임 엔진을 직접 import했다. 사용자 지정 Smile/Heart 원본을 적용한 상태다. 실물 휴대폰, 원격 동시 접속, 전체 GameView의 DOM 애니메이션 성능을 대신하지 않는다.

## 방법

`scripts/prepare_phase2_browser_benchmark.py`로 `public/preview-phase2-perf.html`을 생성하고 브라우저에서 버튼을 눌렀다. 생성 HTML은 Git과 Vercel 배포에서 제외한다. 빈 RAF 2초 → 실제 엔진 seed 4 봇 → 엔진 종료 → 생성/시작/중단 10회의 순서다. 봇은 실제 `jumpPress`/`jumpRelease`를 사용하며 충돌·시간·점수 규칙을 바꾸지 않는다.

- 빈 RAF: 60 간격, 평균 33.333ms, p95 33.9ms, 최대 34.2ms.
- 페이지는 전체 측정 동안 visible. 이 환경의 기본 RAF 자체가 약 30Hz였으므로 60 FPS 통과로 표현하지 않는다.
- 게임: 3,618 tick / 60.3초, 723점, 코인 12개(+120), 하트 2개, 부활 2회, 최종 COLLISION.
- 실시간 봇의 입력은 브라우저 RAF 간격에 따라 달라져 오프라인 60tick bot의 68.8초 결과와 직접 비교하지 않는다.

## 실제 경계 전후 프레임

각 실제 `onStageChange`/`onRevive` 콜백의 전후 30tick을 표본으로 사용했다. 마지막 60초 경계는 60.3초 게임 종료로 인해 뒤쪽 표본이 일부만 존재한다.

| 경계 | callback tick | RAF 간격 p95 / 최대(ms) | 엔진 프레임 처리 p95 / 최대(ms) | render p95(ms) |
| --- | ---: | ---: | ---: | ---: |
| 15초 stage 2 | 900 | 34.2 / 34.2 | 1.3 / 7.2 | 0.4 |
| 1차 부활 | 1342 | 34.0 / 34.3 | 1.4 / 2.7 | 0.5 |
| 30초 stage 3 | 1800 | 34.3 / 34.4 | 0.7 / 1.8 | 0.3 |
| 45초 stage 4 | 2700 | 34.1 / 34.1 | 2.5 / 2.6 | 0.8 |
| 2차 부활 | 2966 | 33.5 / 33.6 | 0.6 / 0.6 | 0.4 |
| 60초 stage 5 (뒤쪽 일부) | 3600 | 33.5 / 33.5 | 2.0 / 2.2 | 0.5 |

이 측정에서는 스테이지·부활 경계에서 기본 RAF 간격보다 큰 프레임 정지가 관측되지 않았다. 이전 사용자가 본 멈춤의 원인을 확정하거나 모든 기기의 부드러움을 보장하는 결과는 아니다.

## 반복 생성·중단

10회 모두 resize listener 증가 0, 잔류 RAF 증가 0, stop 이후 resize 호출 없음, stop 이후 tick 진행 없음. 본 게임 엔진 종료 후에도 listener/RAF 잔류는 0이었다.

브라우저의 비표준 `performance.memory` 참고값은 반복 전 9,083,895 bytes, 후 8,533,079 bytes였다. GC 시점을 통제한 heap snapshot 검사가 아니므로 메모리 누수가 전혀 없다고 결론 내리지 않는다. 10회 **완전한 게임 플레이**가 아니라 10회 엔진 시작/중단 수명 주기 검사다. 전체 앱의 반복 화면 전환·이벤트 중복 검사는 별도 회귀 테스트 범위를 따른다.

## 아이콘 시각 확인

별도 로컬 확인 페이지에서 실제 `DinoGameEngine.drawItem`으로 Smile-Light/Heart-Light 원본을 30px에 렌더링했다. 낮·밤 배경 모두 이미지 로드를 확인했고 원본 비율과 충돌 영역을 유지했다. 해당 임시 확인 페이지는 배포하지 않는다.
