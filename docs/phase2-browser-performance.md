# Phase 2 로컬 브라우저 성능 확인

측정일: 2026-09-26 KST. 실제 Codex 내장 Chromium 153 / macOS. 사용자 지정 Smile/Heart 원본을 적용한 상태다. 먼저 엔진 단독으로 측정한 뒤, 아래 별도 절에서 실제 GameView·API·로컬 DB를 연결한 10판 순차 플레이를 확인했다. 실물 휴대폰과 원격 동시 접속 성능을 대신하지 않는다.

## 방법

`scripts/prepare_phase2_browser_benchmark.py`로 `public/preview-phase2-perf.html`을 생성하고 브라우저에서 버튼을 눌렀다. 생성 HTML은 Git과 Vercel 배포에서 제외한다. 빈 RAF 2초 → 실제 엔진 seed 4 봇 → 엔진 종료 → 생성/시작/중단 10회의 순서다. 봇은 실제 `jumpPress`/`jumpRelease`를 사용하며 충돌·시간·점수 규칙을 바꾸지 않는다.

- 빈 RAF: 60 간격, 평균 33.333ms, p95 33.9ms, 최대 34.2ms.
- 페이지는 전체 측정 동안 visible. 이 환경의 기본 RAF 자체가 약 30Hz였으므로 60 FPS 통과로 표현하지 않는다.
- 게임: 3,618 tick / 60.3초, 723점, 코인 12개(+120), 하트 2개, 부활 2회, 최종 COLLISION.
- 실시간 봇의 입력은 브라우저 RAF 간격에 따라 달라져 오프라인 60tick bot의 68.8초 결과와 직접 비교하지 않는다.

## 실제 경계 전후 프레임

각 실제 `onStageChange`/`onRevive` 콜백의 전후 30tick을 표본으로 사용했다. 마지막 60초 경계는 60.3초 게임 종료로 인해 뒤쪽 표본이 일부만 존재한다.

## 반복 생성·중단

10회 모두 resize listener 증가 0, 잔류 RAF 증가 0, stop 이후 resize 호출 없음, stop 이후 tick 진행 없음. 본 게임 엔진 종료 후에도 listener/RAF 잔류는 0이었다.

브라우저의 비표준 `performance.memory` 참고값은 반복 전 9,083,895 bytes, 후 8,533,079 bytes였다. GC 시점을 통제한 heap snapshot 검사가 아니므로 메모리 누수가 전혀 없다고 결론 내리지 않는다. 10회 **완전한 게임 플레이**가 아니라 10회 엔진 시작/중단 수명 주기 검사다. 전체 앱의 반복 화면 전환·이벤트 중복 검사는 별도 회귀 테스트 범위를 따른다.

## 아이콘 시각 확인

별도 로컬 확인 페이지에서 실제 `DinoGameEngine.drawItem`으로 Smile-Light/Heart-Light 원본을 30px에 렌더링했다. 낮·밤 배경 모두 이미지 로드를 확인했고 원본 비율과 충돌 영역을 유지했다. 해당 임시 확인 페이지는 배포하지 않는다.

## 실제 앱 10판 순차 플레이

코드 `f1557b1`, 2026-09-26 12:46:39–12:52:06 KST. 실제 홈 → GameView → 정상 충돌 → 서버 점수 검증 → 결과 → 랭킹 → 홈을 같은 참가자로 10번 실행했다. localhost Python 3.12와 실제 로컬 PostgreSQL을 사용했다. 원격 요청·동시 사용자·부하 참가자 준비는 없다.

- 별도 로컬 쿠키 이름을 사용해 이전 개발 비밀값으로 만든 쿠키와 분리했다. 인증·게임·점수 규칙은 같다. 정상 유효 방문 API로 한 번에 초대권 1장씩 적립했으며 잔액 상한·쿨다운 규칙을 우회하지 않았다.
- 실제 키 입력 핸들러를 사용하는 자동 플레이로 첫 3판은 긴 플레이·부활, 나머지 7판은 약 10초 뒤 점프를 멈추고 자연 충돌하게 했다. 첫 안내 확인 과정에서 측정 도구 대기 시간이 초과된 준비용 1판은 서버에서 정상 완료됐으나 아래 10판에서 제외했다.
- 전체 GameView와 DOM 연출을 그대로 실행했다. RAF·엔진 프레임 처리·전역 listener를 임시 도구로 관측했고 페이지는 내내 전경이었다. 임시 측정 페이지·서버는 확인 후 제거/종료했다.

각 스테이지/부활 콜백 전후 30tick을 관측했다. 스테이지 전환 11회의 구간별 RAF p95는 17.9–18.6ms, 최대 18.8ms, 엔진 처리 최대 2.5ms였다. 부활 5회의 구간별 RAF p95는 18.6–18.7ms, 최대 35.2ms, 엔진 처리 최대 3.0ms였다. 전체 플레이에는 최대 50ms RAF 간격과 54.6ms 엔진 처리 표본이 있으므로 모든 프레임이 매끄럽다고 표현하지 않는다. 앞선 엔진 단독 측정은 다른 시점의 약 30Hz 환경이며 두 측정을 성능 개선 전후로 직접 비교하지 않는다.

10판 모두 홈 복귀 후 잔류 RAF 0·canvas 0·전역 listener 수 기준값과 동일했다. 측정 시간대 브라우저 오류·경고와 미처리 예외는 없었다. 탭의 과거 로그에는 이전 3108 서버 쿠키 불일치 당시 분석 전송 경고가 있으며 측정 시간대에서 제외했다. 참고 heap은 시작 7,877,804 bytes, 종료 7,439,269 bytes, 라운드 종료 표본 최대 8,365,323 bytes였다. 도구 오버헤드와 GC 시점을 통제하지 않아 메모리 누수 부재를 증명하지 않는다.

실제 로컬 DB에서 10판 모두 `FINISHED / VERIFIED / 2.0.0`이며 화면 점수·코인·부활과 일치했다. 각 게임의 서버 시작/완료와 클라이언트 시작/완료 이벤트는 각각 1건이다. 실제 관리자 집계 함수에 해당 시간·유입 채널·직접 유입 참가자 필터를 적용한 결과 승인 10·완료 10·고유 참가자 1·코인 32·하트 5·부활 5·진행 중 0으로 일치했다. 관리자 브라우저 전체 업무 검증은 별도다.

개인 식별값을 제외한 서버 대조 요약은 [phase2-full-app-repeat-summary.json](phase2-full-app-repeat-summary.json)에 보관했다. DOM 원본 내보내기는 브라우저가 지원하지 않아 선택한 결과 필드를 로컬 증거 파일에 옮겼으며 시간 수치는 소수점 첫째 자리로 반올림했다. 실기기·인앱 브라우저·네이티브 공유·원격 동시 부하는 아직 통과로 표시하지 않는다.
