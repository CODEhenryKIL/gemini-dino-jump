# 공룡 점프 — Datadog 장애 감시 도입 기획안

- 작성일: 2026-09-29
- 상태: 2026-09-29 사용자 승인 후 베타 로그 연결·실제 수신 검증 완료. 접속 점검·대시보드·오류 알림과 로그 공백 감시 설정 저장 완료.
- 실제 설정과 검증 기록: [관측 도구 연결 기록](observability-setup.md)
- 대상: Vercel 서버 및 Supabase DB를 사용하는 공룡 점프 웹사이트
- 운영 기간 가정: 7일 이내. 행사 일정과 모니터링 해제 시점은 적용 시 확인한다.
- 권장 구성: Datadog 학생 혜택 + 접속 확인 + 필요한 Vercel 서버 로그 + 장애 알림
- 관련 문서: [GA4 보조 분석 도입 기획안](ga4-integration-plan.md)

## 1. 목적과 역할

장애를 빠르게 발견하고, 영향받는 기능과 원인을 좁힐 수 있도록 한다.

| 도구 | 담당 범위 |
| --- | --- |
| 자체 DB·관리자 통계 | 게임 기록, 게임권·뽑기권, 카카오 전송 확인, 당첨·수령 접수의 정확한 상태 |
| GA4 | 유입 경로, 화면 이동, 퍼널 전환·이탈, 기기·브라우저별 이용 행동 |
| Datadog | 접속 실패, 서버 오류, 응답 지연, 배포 전후 변화, 운영 알림 |
| Supabase 대시보드 | DB 내부 로그, CPU·메모리·연결 수 등 DB 상태 확인 |

Datadog 감시 결과를 게임권 지급·추첨·수령 접수의 판정 근거로 사용하지 않는다. 감시 도입은 서버 증설이나 과부하 방어를 자동으로 수행하는 작업이 아니다.

## 2. 최초 도입 범위

| 대상 | 감시 내용 | 방식 |
| --- | --- | --- |
| 홈 페이지 | 정상 HTTP 응답과 예상 페이지 내용 | 외부 HTTP 접속 확인 |
| 서버·DB 연결 | 서버 응답 및 제한된 읽기 전용 DB 조회 성공 | 상태 확인 API |
| 게임 시작·종료 | 오류율, 처리 시간, DB 연결 실패 | 서버 요청 로그 |
| 복주머니 추첨 | 서버 오류, 처리 지연 | 서버 요청 로그 |
| 카카오 웹훅 | 콜백 처리 실패, 내부 적립·접수 처리 실패 | 요청 로그 및 필요한 처리 결과 로그 |
| 수령 정보 | 저장·최종 접수의 서버 오류 | 개인정보를 제외한 처리 결과 |
| 배포 | 배포 이후 오류·지연 변화 | 배포 버전별 비교 |

HTTP 접속 확인은 브라우저에서 게임 화면이 실제로 렌더링되고 조작되는 것까지 증명하지 않는다. 모바일 화면·게임 동작 확인은 별도 검증으로 남긴다.

### 후속 확장

- 브라우저 오류·긴 화면 처리 작업 분석: 실제 이용자 일부를 대상으로 RUM 적용 검토.
- Python API부터 SQL까지의 상세 추적: 현재 런타임과 호환되는 계측 방식을 확인한 뒤 APM 적용 검토.
- DB 지표 통합: Supabase Metrics API 수집 방식과 수집기 운영 비용 확인 후 검토.
- Supabase 전체 로그 전송: 기본안에서 제외. 필요성과 추가 요금을 확인한 뒤 선택한다.
- 화면 녹화 기능은 초기 도입 범위에 포함하지 않는다.

## 3. 계정과 학생 혜택

1. 사용자 소유 GitHub 계정의 Student Developer Pack 승인 여부를 확인한다.
2. Datadog 학생 혜택을 신청·활성화한다. GitHub 로그인만으로 적용됐다고 판단하지 않는다.
3. 실제 Datadog 계정에 표시된 혜택 시작일·종료일·제품별 무료 한도를 확인한다.
4. 로그 수집·검색 저장·HTTP 테스트·RUM 등 사용할 제품이 각각 포함되는지 확인한다.
5. 혜택이 적용된 Datadog 조직에 공룡 점프를 연결한다.

공식 안내는 2년 무료 및 제품별 사용 한도를 제공한다. 모든 기능을 무제한 무료로 사용할 수 있다는 의미는 아니다. 현재 이 계정의 학생 혜택 활성화 상태와 잔여 한도는 확인하지 않았다.

## 4. Vercel 로그 연결

### 연결 설정

- 기존 Datadog 연결 여부를 확인해 중복 전송을 방지한다.
- Vercel 마켓플레이스의 공식 Datadog 연동을 사용한다.
- 공룡 점프 프로젝트만 선택하고, 실제 서비스 중인 배포 환경·도메인을 확인한다.
- 운영 알림은 본행사 데이터에 한정한다. 배포 환경과 별도로 베타·본행사 구분도 확인한다.
- 사전 검증 로그에는 테스트 환경 표시를 붙이고 운영 알림·지표에서 제외한다.
- 전용 API 키는 서버 비밀 설정에 저장한다. 소스 코드·브라우저 코드·문서에 넣지 않는다.

### 로그 항목

앞서 확인한 코드의 요청 경로·상태 코드·처리 시간·오류 코드·DB 실패 분류를 활용한다. 구현 시 최신 코드와 실제 배포에서 필드가 동일한지 다시 확인한다.

| 필드 | 용도 |
| --- | --- |
| 서비스·환경·행사 구분 | 운영과 테스트 구분 |
| 배포 버전 | 변경 전후 비교 |
| 요청 ID | 동일 요청의 로그 연결 |
| 정규화된 API 경로·메서드 | 게임·추첨·수령 등 기능별 집계 |
| 상태 코드·처리 시간 | 오류율과 응답 속도 계산 |
| 오류 코드·DB 실패 분류 | 연결 실패·대기 초과 등 원인 구분 |
| 처리 결과 | HTTP 성공 응답 이후 내부 처리 실패가 있는 경우 별도 구분 |

- 오류율의 분모는 같은 기능·환경·시간 범위의 전체 요청으로 맞춘다.
- 초기에는 필요한 서버 요청 로그를 정상·실패 모두 수집한다. 표본 수집을 도입하면 누락률과 오류율 계산 방식을 함께 조정한다.
- Vercel의 한 진입 함수로 여러 API가 연결되더라도 실제 API 경로로 구분한다.
- 오류 하나가 플랫폼 로그와 애플리케이션 로그에 각각 남아 중복 집계되지 않도록 집계 기준을 정한다.
- 이미지·정적 파일 접근 로그와 불필요한 디버그 로그는 수집 범위에서 제외한다.
- 게임·추첨 응답 중 Datadog 외부 전송 완료를 기다리지 않는다. 관측 도구 장애가 서비스 응답을 막지 않도록 한다.

## 5. 접속 확인 설계

### 적용 설정 (2026-09-29)

- 확인 대상: 홈 페이지와 서버·DB 상태 확인 API, 총 2개.
- 실행 간격: 각 10분. 학생 혜택의 월 HTTP 실행 한도 10,000회 안에 들도록 조정했다.
- 실행 지역: Seoul (AWS) 1곳.
- 추가 재시도: 0회. 즉시 실패와 다음 정기 실행의 복구를 알림으로 확인한다.
- 정기 실행 횟수: 하루 288회, 5일 1,440회, 30일 8,640회, 31일 8,928회. 수동 실행은 별도다.
- HTTP 테스트 한도는 브라우저 테스트 한도와 구분해 확인한다.

### 상태 확인 API 요구사항

- 기존 API를 먼저 확인하고 재사용 여부를 결정한다.
- 참가자 생성, 게임 시작, 추첨, 게임권 지급, 수령 접수 같은 쓰기 작업을 수행하지 않는다.
- DB 조회는 짧고 가벼운 읽기 전용 쿼리로 제한한다.
- DB가 끊긴 상태에서 캐시된 정상 응답이 돌아오지 않도록 한다.
- 인증 쿠키·개인정보 없이 확인 가능하도록 설계하고 응답에 내부 비밀 정보를 넣지 않는다.
- 행사 종료·예정·일시 중단과 서버 장애를 구분한다.
- 모니터링 요청은 이용자 접속 통계와 구분한다.

이 설정은 적은 수의 정기 상태 확인이며 동시 접속 부하 테스트는 범위에 포함하지 않는다.

## 6. 알림 기준 초안

수치는 정상 운영 기준값을 확보한 뒤 조정한다.

| 항목 | 초기 기준 |
| --- | --- |
| 사이트·DB 연결 불가 | 상태 확인 실패 후 짧은 재시도에서도 실패 |
| 서버 오류 증가 | 동일 기능의 최근 5분 오류 5건 이상이면서 오류율 5% 이상 |
| 응답 지연 | 최근 5분 요청 20건 이상일 때 p95 응답 시간 3초 초과 |
| 카카오·수령 처리 실패 | 정상적인 제한과 구분되는 내부 오류가 짧은 시간에 반복 |
| 로그 수집 문제 | 상태 확인은 성공하고 로그 발생이 예상되는데 지속적으로 데이터가 도착하지 않음 |
| 사용량 경고 | 확인된 무료 한도·예산에 대한 경고 기준 설정 |

`p95`는 요청의 95%가 그 시간 안에 처리됐다는 의미다. 요청이 적을 때는 비율만으로 과도한 경보를 내지 않는다.

- 게임권 부족·정상 중복 차단·사용자 입력 오류·공유 취소는 서버 장애와 구분한다.
- 카카오 웹훅이 없다는 사실만으로 전송 실패를 단정하지 않는다. 취소·미전송·정상 제외 사례가 존재한다.
- 카카오 HTTP 응답 성공과 게임권·뽑기권·수령 접수 처리 성공을 구분한다.
- 알림에는 발생 시각, 영향 기능, 오류 수·분모, 배포 버전, 확인 링크를 넣는다.
- 동일 장애의 반복 알림을 제한하고, 정상 복구 알림을 설정한다.
- 모니터링 자체의 데이터 누락을 정상 상태로 표현하지 않는다.
- 수신 이메일 등 알림 수신처는 설정 전에 확정한다. 개인정보 문의처를 임의로 알림 주소로 사용하지 않는다.

## 7. 대시보드 구성

1. 홈·서버·DB 상태 확인 결과.
2. 기능별 분당 요청 수, 오류율, 응답 시간.
3. DB 연결 실패·대기 초과 횟수.
4. 카카오 웹훅 및 수령 접수 처리 오류.
5. 최근 배포 시점과 버전별 변화.
6. 로그·테스트 사용량 및 예상 비용.

요청 수는 동시 접속자 수와 다르다. DB CPU·메모리·연결 수는 별도 지표 수집을 구성하기 전까지 Supabase 대시보드에서 확인한다.

## 8. 비용 계획

공식 가격 확인 기준일은 2026-09-29이며 실제 활성화 전 계정에 적용되는 요금·혜택·잔여량을 다시 확인한다.

| 항목 | 비용 기준 | 기본안 |
| --- | --- | --- |
| Datadog | 학생 혜택에 포함된 기능·사용 한도 안에서 무료 | 혜택 적용 및 제품별 한도 확인 후 사용 |
| Vercel 운영·로그 전송 | 포함량과 Pro 크레딧을 초과하면 추가 과금. 로그 전송 공개 단가는 GB당 $0.50 | 필요한 서버 로그로 범위 제한 |
| Supabase Log Drains | 연결 하나당 시간당 $0.0822, 월 약 $60. 이벤트 100만 건 단위 $0.20 및 전송량 관련 비용 별도 | 초기에는 사용하지 않음 |
| 기존 Supabase 운영 | 서버 크기, 프로젝트 수, 디스크·전송량 등 기존 설정에 따라 결정 | 현재 사용량 별도 확인 |

### 7일 운영 예시

- Supabase 로그 전송을 정확히 168시간 유지하면 연결 시간 비용은 `$0.0822 × 168 = $13.8096`, 약 **$13.81**이다.
- 로그 이벤트·데이터 전송 비용과 세금 등은 별도다. 일부 시간 사용도 한 시간으로 계산될 수 있다.
- 로그 전송 연결을 만들지 않으면 이 추가 연결 비용은 발생하지 않는다.
- Datadog 학생 혜택은 Vercel·Supabase 청구액을 면제하지 않는다.
- Vercel Pro의 월 $20 사용 크레딧에는 기존 개발·배포 등 다른 사용량도 영향을 준다.
- 7일이라는 기간만으로 초과 요금 여부를 확정하지 않는다. 현재 잔여 한도와 실제 요청·로그량을 확인해야 한다.

### 비용 통제

- 최초 연결 전 무료 혜택, 결제 주기, 잔여 크레딧, 활성 부가 기능을 확인한다.
- 짧은 검증 기간의 실제 로그량과 테스트 횟수로 운영 기간 예상 비용을 계산한다.
- 보관 기간·검색 저장량을 제한하고 사용량 경고를 설정한다.
- 로그 검색 저장 한도는 전체 수집·전송 요금의 차단 장치가 아니다. 수집량과 전송량도 관리한다.
- 비용 대응은 감시 범위·주기·전송 연결 조정부터 검토한다. 게임 사이트 자동 중단은 별도 운영 결정이다.
- 행사 종료 후 수령 접수 기간까지 필요한 감시 범위를 정하고, 불필요한 유료 연결은 해제한다.
- 추가 유료 기능 활성화 전 구체적인 예상 비용을 확인한다. 이 기획안은 유료 가입 승인으로 간주하지 않는다.

## 9. 개인정보와 접근 관리

- 이름·연락처·학교·인증 자료·양식 본문은 Datadog으로 보내지 않는다.
- 쿠키·인증 헤더·API 키·DB 접속 문자열을 로그에 기록하지 않는다.
- URL은 정규화하고 개인별 초대 코드·토큰·불필요한 쿼리 값은 제거한다.
- 기본 플랫폼 로그에도 민감한 값이 없는지 연결 전에 표본을 확인한다.
- 원시 IP 등 불필요한 식별 정보의 수집·보관 범위를 최소화한다.
- 요청 ID 등 개별 값은 로그 조회용으로 사용하고, 지표 차원에는 기능·환경·오류 분류 같은 제한된 값을 사용한다.
- RUM을 추가할 때에는 입력값·URL·브라우저 저장소 수집 범위와 관련 안내를 별도로 검토한다.

## 10. 구현 및 검증 순서

1. 현재 계정·요금·학생 혜택·기존 연결 확인.
2. 최신 서버 로그와 상태 확인 API 점검, 필요한 최소 수정안 준비.
3. 테스트 환경 로그 연결 및 개인정보·중복 집계 확인.
4. 접속 확인, 기능별 대시보드, 장애·복구 알림 구성.
5. 테스트 환경에서 통제된 오류와 복구를 재현해 알림 확인.
6. 모니터링 연결 실패 시 게임·추첨 기능 영향 여부 확인.
7. 실제 수집량과 남은 혜택을 기준으로 비용 예상 정리.
8. 확인된 구성으로 운영 연결 적용, 정상 데이터 수신 확인.
9. 행사 종료 후 필요한 감시 유지·유료 연결 해제 내역 확인.

운영 DB를 끊거나 실제 경품 추첨·게임권 사용을 반복하는 방법으로 장애 테스트를 하지 않는다. 기존 게임 규칙·행사 설정·카카오 지급 로직은 이 작업의 변경 범위가 아니다.
