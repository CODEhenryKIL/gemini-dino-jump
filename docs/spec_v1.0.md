# Team Gemini 공룡 점프 이벤트 개발 정의서 v1.0

- **작성일**: 2026-09-16  
- **문서 목적**: 기획, 디자인, 프론트엔드, 백엔드, 운영 담당자가 동일한 범위로 구현하기 위한 기준.  
- **상태**: 개발 착수용 초안. 사용자 확정 요구와 구현 제안, 출시 전 결정 사항을 구분한다. 이 문서는 구현 완료 보고서가 아니다.

## 1. 서비스 정의와 범위

### 1.1 한 문장 정의
Team Gemini 공식 에셋을 활용한 공룡 점프 게임에서 장애물을 피하며 최고 점수에 도전하고, 즉석 경품과 친구 초대를 통해 Gemini 학생 혜택 페이지 방문과 등록을 유도하는 모바일 중심 이벤트.

### 1.2 목표
- Gemini 학생 혜택에 대한 관심과 실제 등록을 유도한다.
- 점수 경쟁과 개인 추천 링크로 대학생 사이의 확산을 만든다.
- 확정된 예산 안에서 경품을 지급하고 지급 근거를 남긴다.
- 운영 주체, 참여 조건, 결과, 지급 상태를 명확하게 보여준다.
- 등록 전환은 실제 확인 수단이 확보된 경우에만 측정한다. 링크 클릭과 등록 완료는 별도 지표다.

### 1.3 확정 요구 / 구현 제안 / 미정 사항

| 구분 | 내용 |
| :--- | :--- |
| **사용자 확정** | 게임은 공룡 점프 게임 하나만 제공한다. 송편 담기, 카드 뒤집기 등 별도 게임은 구현하지 않는다. |
| **사용자 확정** | 크롬 오프라인 공룡 게임과 같은 직관적인 점프 방식으로 진행한다. |
| **사용자 확정** | 난이도는 총 6스테이지이며 스테이지가 진행될수록 빨라진다. 마지막에는 대부분 오래 버티기 어려울 정도로 어렵게 하고, 충돌할 때까지 플레이한다. |
| **사용자 확정** | 점수 랭킹을 제공한다. |
| **기존 흐름 유지** | 첫 게임 전 회원가입이나 이름, 연락처 입력을 요구하지 않는다. |
| **기존 흐름 유지** | 게임 종료 후 복주머니를 열고 당첨 결과에 따라 Gemini 혜택과 수령 또는 추가 기회를 연결한다. |
| **기존 흐름 유지** | 친구 공유와 개인 추천 링크를 제공한다. 필요한 개인정보는 수령 단계에서 받는다. |
| **이번 문서의 제안** | 6스테이지는 선택형 메뉴가 아니라 한 판 안에서 자동으로 상승한다. |
| **이번 문서의 제안** | 게임권 1장으로 한 판 플레이하고 종료 후 복주머니 1회를 연다. |
| **이번 문서의 제안** | 랭킹은 개인 최고 점수 기준이며 점수에 따른 추가 경품은 초기 범위에 넣지 않는다. |
| **이번 문서의 제안** | 공유 창을 열기만 한 경우에는 보상하지 않고, 초대받은 친구의 유효 플레이가 확인되면 초대자에게 보상한다. |
| **미정** | 실제 Gemini 등록 확인 방법, 경품 구성과 수량, 대학생 확인 방식, 기간, 보상 한도, 수령 기한. |

### 1.4 초기 구현 범위
- **포함**: 모바일 웹, 데스크톱 키보드 조작, 공룡 게임, 6스테이지 자동 난이도, 최고 점수 랭킹, 복주머니, 경품 수령함, 개인 추천 링크, Gemini 혜택 안내, 운영 관리자, 최소 분석 이벤트.
- **제외**: 다중 게임, 멀티플레이 대전, 대학별 팀 순위, 유료 게임권, 현금 충전, 구매형 뽑기, 자체 포인트 지갑, 친구 목록, 사용자 게시판, 공식 Gemini 사이트 내부 추적 코드 삽입.

| **한 판 종료** | 첫 장애물 충돌. 시간 제한이나 6스테이지 클리어 종료 없음 | 확정 취지 반영 |

| **랭킹** | 이벤트 기간 내 참여자별 최고 검증 점수 한 개 | 확정 취지 반영 |
| **랭킹 경품** | 초기에는 없음. 도입 시 지급 기준과 본인 확인을 별도로 확정 | 제안 |
| **경품 확률** | 게임 점수, 난이도, 학교, 공유 횟수와 무관 | 기존 재미 중심 취지 반영 |
| **공유 보상** | 신규 피추천인의 첫 유효 게임 종료 시 초대자 +1장 | 제안 |
| **공유 보상 한도** | 초대자 기준 하루 3장, 행사 전체 10장 | 조정 가능한 제안 |
| **Gemini 보상** | 확인된 최초 등록에 +1장. 재방문이나 재클릭으로 중복 지급하지 않음 | 확인 방식 결정 필요 |
| **운영 시간 기준** | 화면과 일일 보상 리셋은 한국 시간, 서버 저장은 UTC | 제안 |

> **주의**: ‘개인 최고 점수’의 초기 식별 단위는 브라우저에 발급한 익명 참여자다. 쿠키 삭제나 다른 기기 사용을 같은 사람으로 확실히 묶을 수 없다는 한계가 있다. 이 상태에서 ‘실제 사람 기준 1인 1계정 보장’이라고 안내하지 않는다.

## 3. 전체 사용자 흐름

### 3.1 최초 진입
1. 카카오톡, 인스타그램, 학교 커뮤니티 링크로 진입한다.
2. 이벤트명, 운영팀, 참여 대상, 기간, 경품, 주요 수령 조건을 확인한다.
3. 별도 가입 없이 시작 버튼을 누른다.
4. 서버가 익명 참여자와 최초 게임권을 생성한다. 기존 참여자는 잔여권을 재사용한다.
5. 첫 방문에만 짧은 조작 안내를 보여준다.
6. 3초 카운트다운 뒤 공룡 게임을 시작한다.

### 3.2 한 판 진행과 결과
1. 공룡은 자동으로 달린다. 사용자는 탭 또는 키보드로 점프한다.
2. 생존 시간이 늘면서 STAGE 1 → 2 → 3 → 4 → 5 → 6으로 상승한다.
3. 장애물과 충돌하면 즉시 멈춘다.
4. 서버 검증 후 이번 점수, 개인 최고 점수, 현재 순위 또는 검증 상태를 표시한다.
5. 최초 랭킹 공개 시 자동 닉네임을 제안하고 선택적으로 수정하게 한다. 이 입력은 게임이나 뽑기를 막지 않는다.
6. ‘복주머니 열기’로 이동한다. 열기 애니메이션 전에 서버가 추첨 결과를 확정한다.

### 3.3 당첨자
1. 상품 이미지와 상품명, 당첨 상태, 수령 기한을 표시한다.
2. Gemini 등록이 수령 조건으로 확정된 경우 그 상태와 다음 단계를 표시한다.
3. 대학생 여부 등 확정된 참여 조건을 확인한다.
4. 상품 종류에 필요한 정보만 받고 지급을 처리한다.
5. 완료 화면에서 최고 기록 공유와 재도전을 제안한다.

### 3.4 미당첨자
1. 이번 점수와 최고 기록을 유지하면서 미당첨 결과를 표시한다.
2. 확인 가능한 Gemini 보상 기능이 활성화되어 있다면 등록 보상을 먼저 안내한다.
3. 친구 초대를 통해 추가 게임권을 받을 수 있음을 안내한다.
4. 잔여 게임권이 있으면 바로 재도전할 수 있다.

### 3.5 재방문
잔여 게임권, 개인 최고 기록, 아직 열지 않은 복주머니, 진행 중인 상품 수령 상태를 복원한다. 외부 혜택 페이지에서 돌아왔다고 등록 완료로 처리하지 않는다.

## 4. 공룡 점프 게임 상세

### 4.1 기본 조작

| 항목 | 규칙 |
| :--- | :--- |
| **이동** | 공룡은 고정된 가로 위치에서 달리고 배경과 장애물이 왼쪽으로 이동 |
| **모바일** | 게임 영역 탭 또는 하단 점프 버튼 |
| **PC** | Space 또는 ↑ |
| **점프** | 한 번 입력하면 고정된 높이와 체공 시간으로 점프 |
| **공중 입력** | 추가 점프 없음. 마지막 착지 직전 100ms 입력만 버퍼로 보관하는 안 제안 |
| **길게 누르기** | 높이 변경이나 자동 연속 점프 없음 |
| **숙이기** | 초기 범위에 없음 |
| **장애물** | 바닥 장애물만 사용. 점프로 피할 수 없는 높이의 장애물은 생성하지 않음 |
| **충돌** | 체력이나 부활 없이 한 번 충돌하면 종료 |
| **사운드** | 기본 음소거. 사용자가 켤 수 있음 |

> 오리지널 크롬 게임의 소스나 스프라이트를 복사하는 것을 전제로 하지 않는다. 러너 방식은 참고하고, 제공받은 Team Gemini 에셋과 자체 게임 로직으로 구현한다.

### 4.2 총 6스테이지 난이도
- **논리 화면**: 960 × 540 좌표계 사용.
- **속도 단위**: 논리 px/s.

| 스테이지 | 유효 생존 시간 | 이동 속도 | 체감 난이도와 장애물 | 화면 표현 |
| :---: | :---: | :---: | :--- | :--- |
| **1** | 0초 이상 15초 미만 | 280 → 330 | 적응. 낮은 단일 장애물, 넓은 간격 | STAGE 1 / 가볍게 시작! |
| **2** | 15초 이상 30초 미만 | 330 → 390 | 쉬움. 폭과 간격에 작은 변화 | STAGE 2 / 조금 더 빠르게 |
| **3** | 30초 이상 45초 미만 | 390 → 470 | 보통. 폭·높이 혼합, 연속 점프 유도 | STAGE 3 / 집중해 봐! |
| **4** | 45초 이상 60초 미만 | 470 → 560 | 어려움. 간격 축소, 점프 타이밍 정밀화 | STAGE 4 / 이제부터 진짜 |
| **5** | 60초 이상 75초 미만 | 560 → 680 | 매우 어려움. 빠른 혼합 패턴, 짧은 여유 | STAGE 5 / 한계에 도전! |
| **6** | 75초 이후 | 680에서 초당 4씩 증가, 최대 800 | 극한. 촘촘한 통과 가능한 패턴, 정밀 타이밍 요구 | STAGE 6 / 얼마나 더 버틸까? |

- 1~5스테이지는 시작·끝 속도 사이를 선형 보간한다.
- 6스테이지는 105초부터 최대 속도 800을 유지하며 충돌할 때까지 계속된다. 별도 7스테이지, 엔딩, 강제 사망 타이머는 없다.
- 전환 안내는 작은 비차단 배지로 잠깐 표시하고 게임을 멈추거나 버튼을 요구하지 않는다.
- **마지막 스테이지의 목표**: 6스테이지에 도달한 일반 테스트 참가자의 90~95%가 진입 후 15초 안에 충돌하는 것을 초기 밸런스 목표로 잡는다. 이는 측정 결과나 보장된 비율이 아니다. 실기기 플레이 테스트 후 진입 시점, 최고 속도, 간격을 조정한다. 매우 잘하는 소수가 더 오래 살아남을 수 있어야 마지막 생존 시간이 랭킹 차이를 만든다.
- 속도만 올리기보다 장애물 간격과 성공 가능한 점프 시점의 폭을 함께 조정한다. 자동 사망, 무작위 충돌 판정, 갑작스러운 히트박스 확대, 모든 입력으로 피할 수 없는 벽은 쓰지 않는다. 빠른 이동 중 장애물을 건너뛰는 충돌 오류를 막기 위해 연속 충돌 검사(Continuous Collision Detection) 또는 동등한 처리를 적용한다.

### 4.3 장애물 생성과 공정성
- 장애물 간격은 고정 픽셀 난수만으로 정하지 않는다. 현재 속도, 점프 궤적, 장애물 폭, 착지 후 다음 점프 가능 시간을 함께 고려한다.
- **최소 간격 제안값**: 앞 장애물 뒷면이 공룡을 지난 뒤 다음 장애물 앞면이 도착하기까지 스테이지 1~6 순서로 1.15 / 1.05 / 0.95 / 0.85 / 0.75 / 0.65초 이상. 최종값은 자동 시뮬레이션과 실제 조작으로 검증한다.
- 각 패턴에 대해 성공 가능한 점프 입력 구간이 존재해야 한다. 마지막 스테이지는 성공 입력 구간을 약 80~120ms로 좁히는 것을 제안한다. 실제 구간은 물리와 장애물 크기에 따라 검증하며, 저프레임·터치 지연 때문에 성공 자체가 불가능해지면 수치를 완화한다. 앞 스테이지는 이보다 넓은 여유를 준다.
- 화면 오른쪽에 나타난 장애물을 보고 반응할 시간을 보장한다. 화면 크기에 따라 장애물을 미리 보는 거리가 달라지지 않도록 같은 논리 화면을 축소해 표시한다.
- 초반 3초에는 충돌 가능한 장애물을 배치하지 않는다.
- 세션마다 서버 발급 난수 시드를 쓰되 패턴 난도는 동일한 제약으로 제한한다. 유리한 패턴이 최고 점수를 과도하게 좌우하는지 테스트한다.
- 사각형 충돌 영역은 그림의 반짝임과 외곽 여백을 제외한다. 속도나 스테이지에 따라 충돌 영역 자체를 바꾸지 않는다. 디버그 모드에서 영역을 표시해 ‘안 닿았는데 죽는’ 사례를 점검한다.

### 4.4 물리와 시간
- 고정 시간 간격의 시뮬레이션을 사용하고 화면 렌더링과 분리한다. 기준 60 tick/s를 제안한다.
- 프레임당 이동량이 아니라 시뮬레이션 시간으로 위치를 계산해 30/60/120Hz 기기의 속도 차이를 없앤다.
- 점프 체공 시간은 약 0.9초를 시작값으로 잡고 공룡 및 장애물 크기에 맞춰 확정한다. 물리 상수와 충돌 영역은 클라이언트와 검증 서버가 공유한다.
- 점수는 `floor(충돌 전 유효 생존 tick / 60 × 10)`으로 계산한다. 1초당 10점이며 카운트다운과 일시정지 시간은 제외한다.
- 장시간 플레이 로그는 지속적으로 체크포인트로 전송한다. 정상 플레이 시간 상한은 두지 않고, 통신 유예 및 비활성 세션 만료만 별도로 관리한다.

### 4.5 일시정지, 이탈, 통신 장애

| 상황 | 처리 |
| :--- | :--- |
| **앱 전환·탭 숨김** | 즉시 시뮬레이션과 점수 증가 정지. 복귀 시 3초 카운트다운 |
| **자동 일시정지** | 세션당 누적 60초까지 복귀 허용하는 안 제안. 이후 중단으로 처리 |
| **수동 일시정지** | 초기에는 제공하지 않음. 운영상 필요하면 규칙을 추가 |
| **화면 회전·리사이즈** | 논리 좌표 유지. 위험하면 자동 일시정지 후 재개 |
| **짧은 통신 단절** | 로컬 플레이는 최대 15초 유예 후 일시정지. 복구 시 체크포인트 동기화 |
| **유예 초과·새로고침** | 세션을 중단 상태로 정리. 자동 새 게임이나 중복 소비 없음 |
| **결과 저장 응답 유실** | 같은 세션 ID로 재조회·재요청. 재추첨이나 추가 게임권 차감 없음 |
| **서버 시작 전 오류** | 게임권 미차감 또는 예약 해제 |
| **시작 후 확인된 서버 장애** | 운영자가 세션 근거로 1회 보정 지급. 단순 이탈 자동 환급은 하지 않음 |

일시정지를 악용한 랭킹 기록은 검토 대상에 포함한다. 클라이언트 시간과 로그만으로 모든 조작을 막을 수 있다고 보장하지 않는다.

## 5. 랭킹

### 5.1 표시와 정렬

| 항목 | 정의 |
| :--- | :--- |
| **기본 범위** | 이벤트 전체 기간 |
| **정렬** | 검증된 최고 점수 내림차순 → 해당 점수를 기록한 서버 완료 시각 오름차순 → 참여자 ID |
| **동점** | 먼저 기록한 참여자가 위. 화면 안내에도 같은 기준 명시 |
| **목록** | 상위 100명, 20명 단위 더 보기 |
| **내 위치** | 순위권 밖이어도 내 점수와 현재 순위를 별도 카드로 표시 |
| **닉네임** | 자동 닉네임 기본 제공, 선택 수정. 2~12자, 금칙어·연락처 형식 차단 |
| **학교** | 초기에는 수집·표시하지 않음. 대학별 랭킹도 제외 |
| **갱신** | 정상 검증 완료 후 10초 이내 반영 목표. 계산 지연 중 상태 표시 |
| **검토 중** | 개인 화면에 ‘기록 확인 중’. 공개 랭킹과 확정 순위에서 제외 |
| **삭제·탈퇴** | 공개 프로필 비노출과 데이터 처리 요청 경로 제공 |

익명 최고 기록 저장과 공개 노출 동의는 구분한다. 공개 랭킹 참여를 원하지 않는 사용자는 개인 기록과 경품 흐름만 이용할 수 있게 한다. 자동 닉네임이어도 게시 전 노출 항목을 알린다.

### 5.2 점수 검증
1. 서버가 게임 버전, 세션 ID, 시드, 시작 허용 시각을 발급한다.
2. 클라이언트는 점프 입력 tick과 일시정지 구간, 체크포인트를 제출한다.
3. 서버가 같은 물리와 장애물 규칙으로 재생해 충돌 시점과 점수를 계산한다.
4. 서버 생존 시간, 입력 순서, 체크포인트 연속성, 세션 중복 여부를 검사한다.
5. 비현실적인 로그, 반복 자동화 패턴, 다중 동시 실행을 표시해 검토한다.
6. 통과한 기록만 최고 점수 및 공개 랭킹에 반영한다.

> 서버 재생은 단순 점수 숫자 변조를 방지하는 장치다. 봇이 가능한 입력 로그 자체를 생성하는 공격까지 완전히 차단하지는 못한다. 상위 기록 검토와 요청 제한을 함께 사용한다. 추후 랭킹 경품을 도입할 때는 수상자 확인을 강화한다.

## 6. 게임권, 추천, 바이럴

### 6.1 게임권 원장
- 잔여권은 클라이언트 저장값을 신뢰하지 않고 서버 원장으로 계산한다. 발급, 예약, 차감, 예약 해제, 운영 보정의 사유와 원천 ID를 모두 남긴다.
- 세션 시작 시 게임권 1장을 원자적으로 예약하고 실제 시작 승인 시 차감한다. 예약 만료는 30초 제안. 동시 탭에서 같은 1장을 두 번 쓰지 못하게 한다. 한 참여자에게 활성 게임 세션은 하나만 허용한다.

### 6.2 추천 링크와 지급 기준
추천 링크는 우리 이벤트 도메인의 `/invite/{opaque_code}` 형태를 제안한다. 이 코드는 이름, 전화번호 등 개인정보를 담지 않는 임의 토큰이다. Gemini 공식 혜택 URL은 받은 원문을 그대로 사용하며 임의 추적 파라미터나 코드를 삽입하지 않는다.

| 상황 | 처리 |
| :--- | :--- |
| **공유 버튼 클릭** | 공유 시도만 기록. 게임권 미지급 |
| **공유 창 취소** | 보상 없음 |
| **친구 링크 방문** | 추천 관계 후보 저장. 아직 보상 없음 |
| **신규 친구 첫 유효 게임 종료** | 서버 검증 후 초대자 +1장 |
| **친구에게 주는 권한** | 기존 최초 게임권 1장. 초대 링크라고 추가 중복 지급하지 않음 |
| **기존 참여자 방문** | 초대 보상 없음 |
| **중복 초대** | 신규 참여자의 최초 유효 추천인 한 명만 인정. 나중 링크가 덮어쓰지 않음 |
| **A → B → C** | B의 참여는 A에게, C의 참여는 B에게만 직접 보상 |
| **자기 추천** | 동일 참여자 금지. 의심스러운 신규 식별자 반복은 검토 |
| **보상 한도 도달** | 게임은 가능하되 추가 초대 보상 없음. 한도 안내 |

IP만 같다고 같은 사람으로 처리하지 않는다. 학교와 기숙사에서 네트워크를 공유할 수 있다. 익명 상태의 반복 쿠키 생성 악용은 완전 차단이 어려우므로 발급 속도 제한, 의심 요청에 한정한 추가 확인, 수령 단계 중복 확인을 결합한다.
공유 문구는 실제 조건과 일치하게 **"친구가 첫 게임을 완료하면 게임권 +1"**로 쓴다. 단순히 공유하면 바로 +1로 표시하지 않는다.

### 6.3 공유 카드
- 개인 최고 점수, 공룡, 이벤트명, 짧은 도전 문구, 운영팀을 표시한다. 추천인 실명과 수령 정보는 포함하지 않는다. (공유 문구 예: "나 공룡 점프 642점! 내 기록 넘을 수 있어?")
- 기본은 OS 공유 시트를 쓰고 미지원 환경에서는 링크 복사를 제공한다. 카카오 전용 공유 SDK는 연동 조건과 앱 키가 준비된 경우 추가한다. 공유 미리보기 이미지는 공개 가능한 점수만 사용하고 비공개 점수는 기본 이벤트 이미지로 대체한다.

## 7. Gemini 혜택 연결

### 7.1 추적 가능한 행동과 불가능한 추정
자체 사이트에서 혜택 버튼 클릭, 외부 링크 이동 시도, 복귀는 기록할 수 있다. 이 세 행동은 실제 등록 완료 증거가 아니다. Google 계정 로그인이나 학생 확인 자체도 해당 Gemini 플랜 등록 증거로 취급하지 않는다.

### 7.2 개발 구조
등록 확인 방식은 교체 가능한 검증 모듈로 분리한다.

| 상태 | 의미 | 사용자 화면 |
| :---: | :--- | :--- |
| **NOT_STARTED** | 등록 확인 절차 시작 전 | ‘Gemini 학생 혜택 확인하기’ |
| **PENDING** | 증빙 또는 승인 결과 대기 | ‘등록 확인 중’ |
| **VERIFIED** | 허용된 방법으로 확인 완료 | ‘확인 완료’ 및 대상 보상 |
| **REJECTED** | 확인 불가 또는 요건 미충족 | 사유와 재시도·문의 경로 |

`benefit_link_clicked`는 별도 이벤트이며 `VERIFIED` 상태를 바꾸지 않는다. `VERIFIED` 전환의 근거, 담당자 또는 제공자, 처리 시각을 남긴다. 가능한 후보는 승인된 전환 데이터 연동 또는 운영 검수이며 현재 가능한 것으로 확정하지 않는다.

### 7.3 출시 모드
- **게임 검증용 모드**: 실제 경품 없이 게임, 랭킹, 추천, 테스트 복주머니를 검증한다. Gemini 버튼은 혜택 안내 링크로 동작한다.
- **등록 확인 연동 모드**: 확인 수단과 운영 기준이 확정된 뒤 등록 보상 및 등록 조건부 수령을 활성화한다.
- **확인 수단 없이 공개 이벤트를 여는 경우**: 수령 조건과 보상 방식을 운영자가 변경 확정해야 한다. 개발자가 ‘방문=등록’으로 대체하지 않는다.

당첨 화면은 해당 조건이 있으면 "상품 당첨 · 수령 조건 확인 필요"처럼 현재 상태를 명확하게 표시한다. "등록 후 즉시 지급"은 확인과 지급이 실제로 자동 완료되는 상품에만 쓴다.

## 8. 복주머니와 경품 지급

### 8.1 추첨
복주머니는 별도 실력 게임이 아니라 게임 종료 후 보상 공개 인터랙션이다. 선택 능력에 따라 상품이 달라지는 것처럼 연출하지 않는다.
1. 서버 검증을 통과한 세션에 추첨 자격을 1개 부여한다.
2. 사용자가 열기를 누르면 서버가 자격을 확인한다.
3. 설정된 확률표 버전과 남은 재고로 결과를 확정한다.
4. 당첨이면 같은 트랜잭션에서 재고 예약과 수령 건을 생성한다.
5. 확정된 결과를 반환한 뒤 1초 내외 개봉 연출을 재생한다.
6. 재클릭, 응답 유실, 새로고침에도 같은 결과를 반환한다.

### 8.2 확률, 재고, 예산

| 항목 | 구현 기준 |
| :--- | :--- |
| **확률표** | 상품별 확률과 미당첨 확률의 합은 1. 서버 보관 |
| **재고 소진 상품** | 해당 확률 질량은 미당첨으로 이동하는 안 제안. 다른 상품 확률을 자동 증폭하지 않음 |
| **확률 변경** | 운영자 변경 이력과 적용 시각, 새 버전을 남기고 필요한 화면 안내를 갱신 |
| **예산** | 확정 재고와 예약 재고의 비용, 지급 비용을 구분하여 예산 초과 차단 |
| **고가 경품** | 예시일 뿐 삼탠바이미·버즈가 확정된 것으로 표시하지 않음 |
| **경품 소진** | 게임과 랭킹은 유지 가능. ‘경품 종료’를 추첨 이전에 알림 |
| **행사 종료** | 서버 시각 기준 마감. 마감 전 시작한 판은 10분 결과 제출 유예 제안 |

랜덤 추첨은 예산이 전부 소진될 것을 보장하지 않는다. 운영 화면에서 잔여 재고와 참여 추이를 보고 향후 확률을 조정할 수 있으나, 이미 확정된 결과는 변경하지 않는다. 종료 시 남은 경품의 처리 방식은 행사 공지에 별도로 확정한다.

### 8.3 지급 방식

| 상품 | 사용자에게 받는 정보 | 지급 기준 |
| :--- | :--- | :--- |
| **화면 제공 가능한 모바일 쿠폰** | 원칙적으로 연락처 없이 수령함에 코드 표시 | 자격 확인 후 즉시 지급 목표 |
| **문자 발송이 필요한 쿠폰** | 휴대전화번호 | 번호와 발송 상태 확인 후 지급 |
| **배송 상품** | 수령인, 연락처, 주소 | 자격 검수 후 배송. 즉시 발송으로 표현하지 않음 |
| **외부 포인트** | 해당 제공사 연동에 필요한 최소 정보 | 연동 준비 시에만 지원. 자체 포인트 기능은 초기 제외 |

쿠폰 코드, 주소, 연락처는 공개 랭킹이나 분석 도구로 보내지 않는다. 코드 제공 후 새로고침에도 같은 코드를 보여준다. 이미 제공된 쿠폰은 다른 당첨자에게 재할당하지 않는다.

### 8.4 수령 상태와 예외
- **상태 전이**: `RESERVED` → `ELIGIBILITY_PENDING` → `READY` → `ISSUING` → `ISSUED`. 검수 탈락은 `REJECTED`, 미수령 만료는 `EXPIRED`, 외부 지급 실패는 `ISSUE_FAILED`로 분기한다.
- 수령 기한은 당첨 후 72시간을 초안으로 제안한다. 운영 검토 지연 중에는 사용자의 잔여 기한을 정지한다.
- 예약 중에는 재고를 다른 사용자에게 주지 않는다. 만료·탈락은 실제 발급 여부 확인 뒤 반환한다.
- 지급 API 타임아웃은 성공 여부를 제공사 거래 ID로 먼저 확인한다. 무조건 다시 발급하지 않는다.
- 익명 사용자는 쿠키 삭제·다른 브라우저 이동 시 수령함 복원이 보장되지 않는다. 수령 페이지에서 이 점을 알리고, 필요한 경우 수령 단계의 연락처 확인을 통한 복구 경로를 제공한다.
- 대학생 확인은 경품 대상자에게 최소한으로 수행한다. 학교 이메일, 증명 방식 등은 미정이며 전체 사용자에게 학생증 업로드를 선요구하지 않는다.
- 모든 대상자에게 동일한 참여 자격과 중복 수령 규칙을 적용한다. 1인 수령 한도는 출시 전 결정한다.

## 11. 기술 구조와 데이터

### 11.1 구성 제안
모바일 반응형 웹 UI + Canvas 게임 렌더러 + 공유 가능한 순수 게임 로직 + 서버 API + 관계형 DB + 비동기 검증·지급 작업 + 관리자 화면으로 구성한다. 특정 호스팅이나 라이브러리 버전은 이 문서에서 확정하지 않는다.
게임 로직에는 브라우저 DOM 의존성을 넣지 않아 서버 검증에서 동일하게 실행할 수 있게 한다. 랭킹과 재고, 원장은 서버를 기준으로 한다. 읽기가 많은 랭킹은 캐시할 수 있으나 재고와 차감 판단에 지연된 캐시를 사용하지 않는다.

### 11.2 주요 데이터 모델
- **Campaign**: 기간, 상태, 혜택 URL, 보상 규칙, game_version, 안내 버전
- **Participant**: 익명 ID, session credential, 닉네임, 공개 동의, 생성 시각, 상태
- **GameSession**: 참가자, 시드, 버전, 상태, 예약·시작·종료 시각, checkpoint, 점수, 검증 결과
- **GameInputChunk**: session_id, 순번, 입력 tick 배열, pause 로그, 무결성 정보. 순번 중복 금지
- **BestScore**: campaign+participant+game_version 고유, 최고 session_id, score, achieved_at
- **TicketLedger**: 참가자, 종류, 수량, source_type/source_id, 생성 시각. 보상 원천별 중복 금지
- **Referral**: 초대자, 피초대자, 귀속 시각, 완료 세션, 지급 상태. 피초대자별 하나
- **BenefitVerification**: 참가자, 상태, 확인 방식, 근거 참조, 처리자, 상태 변경 이력
- **Draw**: session_id 고유, 확률표 버전, 결과, 생성 시각
- **Prize**: 상품 종류, 총량, 예약량, 발급량, 단가, 확률, 활성 여부
- **Claim**: draw_id 고유, 수령 상태, 기한, 자격 상태, 지급 거래 ID
- **ClaimPrivateData**: claim_id, 필요한 연락·배송 정보. 일반 조회 및 로그와 분리
- **CouponInventory**: 암호화한 코드, 상태, claim_id 고유 연결
- **AdminAudit**: 운영자, 대상, 행위, 변경 전후, 사유, 시각
- **OutboxJob**: 발급·보상 후속 처리, 고유 원천 키, 상태, 재시도 횟수

외부 지급과 DB 트랜잭션을 하나의 원자적 작업으로 가정하지 않는다. DB에는 발급 의도와 고유 거래 키를 기록하고, 후속 작업이 재시도되어도 동일 거래를 조회·확정하게 한다.

### 11.3 API 계약 초안

| 메서드와 경로 | 역할 | 필수 보장 |
| :--- | :--- | :--- |
| `GET /api/campaign` | 행사 상태, 안내, 공개 경품, 기능 활성화 여부 | 비공개 확률 제어값·쿠폰·비밀 키 미노출 |
| `POST /api/participants/anonymous` | 익명 참가자 시작 | 기존 세션 재사용, 발급 속도 제한 |
| `GET /api/me` | 게임권, 최고 기록, 미개봉·수령 건수 | 본인 세션으로만 접근 |
| `POST /api/game-sessions` | 게임권 예약과 시드 발급 | 활성 세션 하나, 중복 예약 방지 |
| `POST /api/game-sessions/{id}/start` | 실제 시작과 차감 | 서버 시각 확정, 동일 요청 멱등 |
| `POST /api/game-sessions/{id}/checkpoints` | 입력·생존 상태 청크 제출 | 순서 및 참여자 검증 |
| `POST /api/game-sessions/{id}/finish` | 종료 제출 및 점수 검증 요청 | 같은 세션 결과 중복 생성 금지 |
| `GET /api/game-sessions/{id}` | 처리 상태와 결과 복구 | 타인 세션 접근 차단 |
| `GET /api/leaderboard` | 공개 상위 기록 및 내 순위 | 비공개 닉네임·개인정보 제외 |
| `PATCH /api/me/profile` | 닉네임과 공개 설정 | 입력 검증, 변경 빈도 제한 |
| `POST /api/draws` | 세션에 귀속된 추첨 | session_id 고유, 재고 원자적 예약 |
| `GET /api/claims` | 내 수령함 | 본인만 접근 |
| `POST /api/claims/{id}/submit` | 필요한 자격·수령 정보 제출 | 상태 검사, 민감 정보 분리 |
| `POST /api/referrals/attribute` | 추천 관계 귀속 | 최초 귀속 고정, 자기 추천 차단 |
| `GET /api/referrals/me` | 추천 링크·보상 내역 | 개인정보 없는 링크 |
| `POST /api/benefit-verifications` | 확정된 확인 절차 접수 | 클릭만으로 승인 금지 |
| `POST /api/events` | 최소 행동 이벤트 | 허용된 스키마만 수신 |

모든 자원은 추측하기 어려운 ID를 쓰되 ID 자체를 권한 확인으로 대신하지 않는다. 차감, 추첨, 지급 요청에는 Idempotency-Key 또는 동등한 원천별 고유 제약을 둔다. 오류 코드는 `NO_TICKET`, `EVENT_CLOSED`, `SESSION_ACTIVE`, `RESULT_PENDING`, `ALREADY_PROCESSED`, `CLAIM_EXPIRED` 등으로 통일한다.

## 12. 운영 관리자

| 기능 | 요구사항 |
| :--- | :--- |
| **행사 제어** | 시작·종료·점검, 신규 게임 중단, 추첨만 중단, 지급만 중단을 구분 |
| **경품 관리** | 재고, 예약, 지급, 잔여 예산 조회와 설정 이력 |
| **게임권** | 참가자 원장 조회, 사유를 남긴 보정. 기존 원장 삭제 금지 |
| **랭킹** | 의심 기록 확인, 공개 제외, 복구, 사유 기록 |
| **자격 확인** | 대학생·Gemini 등록 확인의 대기·승인·반려 처리 |
| **지급** | 실패 조회, 제공사 상태 확인, 안전한 재시도 |
| **초대** | 비정상 추천 패턴, 한도, 지급 이력 확인 |
| **문의** | 수령 실패와 기록 오류를 ID 기준으로 추적 |
| **권한** | 행사 설정 관리자, 검수 담당자, 조회 담당자 분리 |
| **내보내기** | 권한별 필요한 필드만 내보내고 다운로드 이력 기록 |

광범위한 사용자 정보 공개 목록을 만들지 않는다. 배송 담당자는 해당 배송 건에 필요한 정보에만 접근한다. 관리자 로그인 및 변경 기록은 공개 이벤트 로그인과 분리한다.

| **확산** | 추천 방문, 신규 유효 참여, 초대자당 신규 유효 참여 수 | 중복 제거된 익명 기준 명시 |
| **Gemini** | 혜택 클릭률, 확인 접수, VERIFIED 수 | 클릭률을 가입률로 표현하지 않음 |
| **경품** | 추첨 수, 당첨 수, 예약·지급·만료, 지급 비용 | 당첨과 지급 분리 |
| **안정성** | 시작 실패, 결과 저장 실패, 검증 대기, 지급 실패, 응답 시간 | 사용자 이탈과 시스템 실패 분리 |

- **핵심 이벤트**: `landing_view`, `game_start`, `level_reached`, `game_collision`, `game_abort`, `score_verified`, `leaderboard_view`, `draw_open`, `draw_result`, `benefit_link_clicked`, `benefit_verification_completed`, `referral_landed`, `referral_qualified`, `ticket_granted`, `claim_submitted`, `prize_issued`, `share_intent`.
- 서버에서 발생하는 검증·당첨·보상 이벤트는 서버를 원천으로 삼는다. analytics event_id로 중복 제거한다. 주소, 연락처, 증빙 원문, 쿠폰 코드, 세션 인증 토큰은 분석 이벤트에 넣지 않는다.

## 14. 품질 기준과 인수 시나리오

### 14.1 성능과 사용성
- iOS Safari, Android Chrome, 카카오톡·인스타그램 인앱 브라우저에서 진입, 게임, 외부 링크 복귀, 공유 대체 경로를 확인한다.
- 360px 너비 화면에서 주요 버튼과 게임 점수, 수령 폼이 잘리지 않아야 한다.
- 보통의 중급 모바일에서 60fps를 목표로 하며 30fps 환경에서도 게임 시간과 점수가 달라지지 않아야 한다.
- 첫 플레이에 필요한 압축 리소스는 2MB 이내를 초기 목표로 한다. 공식 원본 PNG를 그대로 대량 로드하지 않고 용도에 맞는 크기로 배포한다.
- 주요 API의 p95 1초 이내를 초기 목표로 하되 비동기 점수 검증은 대기 상태를 표시한다.
- 키보드 조작, 버튼 포커스, 대비, 모션 감소, 오류 메시지의 텍스트 안내를 확인한다.

## 15. 제작 산출물과 개발 순서

### 15.1 필요한 산출물
1. 화면 S01~S12의 모바일 디자인과 오류·대기·종료 상태.
2. 공룡 렌더링 자산, 장애물 세트, 배경, 복주머니, 공유 카드.

4. 웹 UI, 게임 엔진, 서버 검증기, API, DB 스키마.
5. 관리자 화면과 보상·지급 작업 처리.
6. 주요 시나리오 테스트, 운영 안내, 출시 설정표.

### 15.2 순서
- **1단계**: 공룡 게임 수직 구현 (탭 점프 → 6스테이지 상승 → 충돌 → 점수, 모바일 실행)
- **2단계**: 익명 세션 · 게임권 · 검증 · 랭킹 (서버 최고 점수와 차감, 중복·변조 검사)
- **3단계**: 복주머니 · 재고 · 수령함 (테스트 상품으로 멱등 추첨·지급 검증)
- **4단계**: 추천 · 공유 · 분석 (실제 신규 유효 참여와 보상 연결)
- **5단계**: Gemini 확인 · 자격 확인 연결 (확정된 방식에 따라 상태와 보상 동작)
- **6단계**: 공식 에셋 · 마이크로카피 적용 (디자인 일관성과 운영 주체·조건 표시)
- **7단계**: 실제 경품 설정 · 통합 검증 (필수 인수 시나리오와 출시 결정 사항 충족)

## 17. 구현 시 유지할 핵심 원칙
1. 게임은 하나다. 6스테이지가 한 판 안에서 이어지고 충돌 전까지 끝나지 않는다.
2. 점수는 경쟁의 기준이고 경품 확률은 점수와 분리한다.
3. 게임 시작에는 개인정보 입력 장벽을 두지 않는다.
4. 랭킹, 게임권, 추천 보상, 경품 결과는 서버가 확정한다.
5. 공유 시도와 실제 친구 참여, 혜택 클릭과 실제 등록을 각각 구분한다.
6. 미정인 외부 연동은 성공한 것처럼 구현하지 않는다.
7. 확정된 결과는 재시도에도 바뀌지 않으며 예산과 재고를 초과하지 않는다.
