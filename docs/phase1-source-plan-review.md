# 제공 기획안 복원 후 1차 대조 검토

검토일: 2026-09-25. 코드 기준: `e84ec67` 작업 브랜치(배포 애플리케이션 코드는 `4fd36f4`). 비교 자료는 `source_user_plan.md`, 1·2·3차 지시서, 정책 결정표, 현재 코드와 기존 테스트다.

최초 검토는 문서 저장·사용자 확정 정정·읽기 전용 코드 검토로 수행했다. 아래 F1–F3 설명과 줄 번호는 보완 전 코드의 발견 기록이다. 이후 사용자 요청으로 `codex/phase1-followup-fixes`에서 세 항목을 보완했고 로컬 검증을 마쳤다. 원격 DB·배포·부하 시험은 변경하지 않았다. [후속 구현·검증 결과](phase1-followup-report.md)를 함께 확인한다.

## 결론

익명 쿠키 복원, 최초 기본권 1장, 유효 초대 방문, 초대권 최대 보유 3장, 참가자당 복주머니 1회, 서버 원장·수동 지급의 큰 흐름은 제공 기획안과 맞는다. 다만 **기존 1차 범위에서 보완할 항목 3개**를 확인했다. 추가 콘텐츠 분류·지표 계약도 새로 제공된 상세 기획을 반영해 확장할 필요가 있다.

기존 200명 시험 성공은 유지되는 사실이다. 부하 시험이 아래의 업무 상태 의미나 집계 정의까지 검증한 것은 아니므로 1차 보고서와 함께 이 검토 결과를 읽는다.

## 1. 1차 보완 항목

### F1. 수령 정보 입력 전에 이미 ‘정보 접수’ 상태가 됨 — P2

- 요구: 당첨, 수령 정보 입력, 운영자 확인·연락·지급을 구분한다.
- 현재: 당첨 시 `claim`을 만들면서 상태를 생략한다. DB 기본값이 `INFORMATION_RECEIVED`여서 연락처가 없는 상태도 ‘정보 접수’가 된다. 실제 제출 때 다시 같은 상태를 저장한다.
- 근거: [생성](../server/operations.py#L390), [DB 기본값](../supabase/migrations/20260925083548_phase1_dino_dev_foundation.sql#L259), [실제 제출](../server/operations.py#L405), [수령함 표시](../public/js/views/prize_view.js#L42).
- 확인 경로: 경품 당첨 → 수령 정보 미입력 → 수령함에 ‘정보 접수’ 배지와 ‘정보 입력’ 버튼이 동시에 표시될 수 있다. 관리자는 연락처에 ‘미접수’를 보면서 상태는 `INFORMATION_RECEIVED`를 보게 된다.
- 영향: 실제 접수 여부와 업무 상태가 어긋난다. `contact_submitted_at`을 쓰는 입력 완료율은 따로 있으므로 모든 수령 지표가 잘못됐다고 확대 해석하지 않는다.
- 보완 방향: 입력 대기 상태를 명시하고 최초 실제 제출 때 정보 접수로 전환한다. 기존 미입력 행의 보정과 사용자/관리자 표시, 미입력 상태 변경 방어를 함께 검토한다.

### F2. Gemini 링크 복사·공유가 초대 공유와 합산됨 — P2

- 요구: Gemini 링크 복사 수·공유 시도 수와 친구 초대 공유를 따로 확인한다.
- 현재: 화면은 `share_attempted`에 `dimensions.source='gemini'`를 기록하지만 집계는 이 구분값을 사용하지 않고 수단·상태만 묶는다. 관리자 Gemini 영역에도 전용 복사·공유 지표가 없다.
- 근거: [Gemini 기록](../public/js/views/benefit_view.js#L39), [합산 집계](../server/metrics.py#L240), [초대 영역 표시](../public/js/admin.js#L285), [Gemini 영역](../public/js/admin.js#L310).
- 확인 예: 같은 기간 초대 링크 복사 1건과 Gemini 링크 복사 1건을 만들면 전체 복사 성공 2건으로 합쳐져 목적별 성과를 볼 수 없다. 원시 이벤트의 구분값은 남아 있으므로 원자료 자체가 소실된 것은 아니다.
- 보완 방향: 공유 목적·수단·상태별 집계와 각각의 이벤트 수/고유 참가자를 제공한다. Gemini 카드와 초대 카드의 수치를 분리하고 동일인이 양쪽을 공유하는 경우를 검사한다.

### F3. Gemini 관측 진행 중과 확정 미클릭을 구분하지 않음 — P2

- 요구: 노출 이후 정해진 관측 기간 내 클릭 여부를 비교하며, 관측이 끝나지 않은 사용자와 확정된 미진행 상태를 구분한다.
- 현재: 클릭은 노출 이후 관측창 안에서 찾지만 모든 노출자를 즉시 분모에 넣고 `노출자 - 클릭자`를 ‘미클릭’으로 표시한다. 최근 노출의 관측 대기 수치는 없다.
- 근거: [노출·클릭 SQL](../server/metrics.py#L117), [미클릭 지표](../server/metrics.py#L333), [기존 시간순서 검사](../tests/test_metrics.py#L63).
- 확인 예: 방금 CTA를 본 사람이 아직 클릭할 시간이 남아 있어도 미클릭 1명으로 집계된다. 실시간 ‘현재까지 미클릭’ 수치로는 해석할 수 있지만, 관측 기간이 완료된 전환율이나 이탈로 읽으면 잘못 판단할 수 있다.
- 보완 방향: 관측 완료 집단과 진행 중 집단을 분리하고, 확정 클릭률·미클릭에는 완료 집단을 사용한다. 실시간 잠정치를 함께 보여준다면 이름과 분모를 명시한다. 같은 참가자의 반복 노출·관측창 경계·0분모를 검사한다.

## 3. 2차·3차에서 처리할 부분

### 2차 화면·게임 완성

- 신뢰·운영 주체·경품 중심 유입/로딩 카피, 공유 카드와 채널별 문구.

- Gemini 실제 콘텐츠 카드, 복사·공유·외부 브라우저 안내. 현재 가이드 버튼은 승인 대기로 비활성화돼 있다.
- 원문 `!image.png`는 텍스트 참조만 제공됐다. 실제 경품 이미지 파일은 이번 첨부에 포함되지 않아 화면 자산으로 확정할 수 없다.

### 운영 전 필수 보호·운영값

- **현재 DRAW 수령 건은 재학생 검증이 완료되지 않아도 지급 완료로 바꿀 수 있다.** 상태 변경과 검증 상태는 저장하지만 지급 전 `VERIFIED`를 강제하지 않는다. [관련 코드](../server/operations.py#L505).
- 이는 현재 합성 Preview의 테스트 흐름이다. 실경품 운영 전에는 자격 확인 상태·연락처 접수·지급 요건을 서버에서 강제해야 한다. 학생증 등 실제 증빙 종류·수집 방식은 D05/D12로 결정한다. `RANKING` 실제 지급은 현재 차단돼 있다.
- 현재 DRAW 수령 폼은 학교를 선택 사항으로 받는다([폼](../public/js/views/prize_view.js#L59)). 실제 수령 양식은 원문의 이름·연락처·학교 수집 요구와 맞춰야 한다. 증빙 방식·개인정보 고지·실제 경품 종류·수량·확률·종료 시각·동점 처리·공식 혜택 문구와 링크는 운영 결정 후 적용한다.
- Notion → Gemini 중간 추적은 원문의 ‘가능하면’과 1차 지시서의 승인 조건에 따라 현재 비활성이다. 공식 URL 및 허용 여부가 정해지기 전에는 실제 경유 전환 구현 완료로 표시하지 않는다.
- 현재 지표는 합성 데이터 전용으로 명시돼 있다. 실제 운영 데이터 제외/포함 규칙과 격리는 3차 운영 전환에서 다시 검증한다.

## 4. 문서 정정·해석

### 쿨다운 — 사용자 재확정 반영 완료

사용자 답변: **“3장이 된 순간부터가 맞아 그거로 반영해줘.”**

- 새 초대 보상으로 초대권 잔액이 3장이 되면 그 순간부터 10시간 추가 적립 대기.
- 기본권 1장은 별도. 대기 중에도 이미 가진 게임권은 사용 가능.
- 누적 지급 3회 제한 없음. 대기 종료 후 새 방문으로 다시 잔액 3장이 되면 새 10시간 시작.
- 대기 중 방문 자동 이월 없음. 장애 환급은 기존 권리 복원이므로 새 쿨다운을 시작하지 않음.
- 현재 서버 [잔액/쿨다운 처리](../server/operations.py#L187)는 이 확정과 일치한다. 문서 저장 때문에 코드 규칙을 바꿀 필요는 없다.
- `source_user_plan.md`, 1차 문서의 원문 제공 상태, 정책 결정표, 2차 쿨다운 UI 규칙, 3차 시험 항목을 정리했다. `00_scope_and_decisions.md`는 첨부 사본으로 보존하며 충돌 시 최신 정책 결정표가 우선한다.

### 원문 자체의 주의점

- 예시 ‘노출 1,000 / 직접 클릭 500 / 가이드 250 / Notion 경유 80 / 미전환 170’은 그대로 계산하면 안 된다. 가이드 클릭은 Gemini 클릭이 아니고 직접·경유 참가자가 겹칠 수 있다. 동일 노출 집단 안의 클릭 합집합으로 계산해야 한다. 현재 Notion 경유는 비활성이다.
- ‘최종 재도전 후 복주머니’와 ‘친구 대기 없이 바로 복주머니’는 상충할 수 있다. 기존 확정대로 첫 정상 완료 후 참가자당 1회 권한을 제공하고, 공유·재도전과 독립적으로 열 수 있는 현재 구현을 유지한다.
- 이벤트 이름이 원문 예시와 다르다고 누락은 아니다. `gemini_cta_viewed/clicked`, `share_attempted`의 의미와 실제 집계를 기준으로 판단했다.
- 원문 줄 번호를 인용한 0차 문서는 예전 문서 배치를 기준으로 하므로 복원 파일의 현재 줄 번호와 동일하다고 가정하지 않는다.
- 첨부의 ‘최초 게임권 몇 장’과 0차의 D01 미정 표시는 기존 대화의 ‘최초 기본권 정확히 1장’ 확정으로 대체된다. 다시 미정으로 되돌리지 않는다.

## 5. 권장 보완 순서

1. F1 수령 상태, F2 공유 목적 분리, F3 관측 진행 중 구분을 각각 수정·회귀 검증한다.
2. 콘텐츠 분류·노출·클릭률·1인당 지표 정의를 계약에 추가한다.
3. 2차 UI·콘텐츠를 이 계약에 연결한다.
4. 실제 공개 전 재학생 검증/지급 조건·운영값을 적용하고 운영 경로를 검증한다.

후속 요청으로 위 1번 F1–F3 구현과 로컬 회귀 검증을 완료했다. 2–4번 추가 계측·2차 화면·실운영 전 검증은 후속 범위로 남아 있으며 이번에 완료했다고 표시하지 않는다.
