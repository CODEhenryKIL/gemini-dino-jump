## 반영 전

1. 브랜치·커밋·코드 검증 결과·migration 파일 해시·설정 버전을 기록한다.
2. 대상 환경과 전용 역할을 확인한다. 비밀값은 출력·문서·Git에 넣지 않는다.
3. 참가자·게임·추첨·수령·원장·재고 건수와 상태별 수량을 집계한다. 개인 연락처를 보고서에 복사하지 않는다.
4. 승인된 백업 경로와 복원 가능 여부를 확인한다. DB dump에는 개인정보가 포함될 수 있으므로 `.local/` 등 비공개 경로·제한 권한에 보관하고 배포 대상에서 제외한다.
5. 회차 migration은 기존 결과를 1회차로 유지한다. 기존 배정·수령·지급을 지우거나 새 풀로 되돌리지 않는다.
6. 본행사 데이터 분리 방식이 정해지기 전에는 기존 베타의 25개 가짜 경품을 실제 77개로 덮어쓰지 않는다.

## 원격 반영 순서

1. 실제 반영 범위·백업·중단 시간을 준비한다. 기존 승인이 충족하는 부분은 재승인받지 않는다.
2. 새 Preview를 먼저 빌드해 두고, 기존 앱의 요청을 처리할 수 있는 호환 migration을 적용한다. 구버전이 교체 직전에 기록한 첫 추첨도 새 앱이 원장을 정산한다. 과거 공유 요청의 목적은 보존한다. 이번 베타는 캠페인을 PAUSED로 바꿔 웹훅을 거절하는 간격을 만들지 않는다. 본행사 전환의 중단 방식은 해당 운영 정책으로 별도 확정한다.
3. 데이터 보존 migration을 적용하고 버전·행 수·제약·권한을 대조한다.
4. 새 API와 UI를 같은 릴리스로 배포한다. 공유 설정과 DB 비밀은 기존 서버 설정을 사용한다.
5. 공개 베타 주소 전환 전 헬스체크·쿠키 복원·기존 결과/수령 조회·목적별 공유를 검사한다.
6. 별도 승인된 격리 데이터로 새 10회 흐름과 재고 정합성을 확인한다. 실제 경품 소진 시험은 자동 실행하지 않는다.
7. 베타 연결 전환 및 결과를 기록한다. 본행사는 운영값·guard·공개 승인이 준비될 때까지 OFF다.

## 장애와 롤백

- 공유 적립 이상: 신규 공유/추첨을 중단하고 share intent, 인증된 웹훅, 게임권·뽑기권 원장, 회차를 대조한다. 같은 요청을 다시 지급하지 않는다.
- 재고 이상: 상품 배정·수령·지급을 분리해 확인한다. 사용자에게 공개된 당첨을 단순 재시도로 변경하지 않는다.
- 배포 오류: 현재 DB와 호환되는 검증 커밋으로 복구한다. **다중 회차가 기록된 DB에 단일 추첨 전제의 이전 코드를 연결하지 않는다.** 우선 쓰기 중단 후 새 schema와 호환되는 수정 배포를 준비한다.
- DB 변경 오류: 파괴적 down migration·전체 reset을 실행하지 않는다. 원인과 전후 건수를 보존한 뒤 보정 migration 또는 승인된 복원을 사용한다.
- 비밀 유출: 전용 접속 비밀만 교체하고 관련 배포를 갱신한다. 로그·Git의 비밀 잔존 여부를 검사하며 다른 앱 자격증명을 임의 변경하지 않는다.
- 앱 배포 롤백은 이미 생성된 당첨·원장·재고를 되돌리지 않는다. 지급 완료 재고를 AVAILABLE로 자동 복원하지 않는다.

## 행사 마감과 수동 지급

1. 확정된 종료 시각·경계 게임 규칙으로 신규 참여를 닫고 마지막 처리 요청을 확인한다.
2. 마감 30초 이후 새 DRAFT 랭킹 스냅샷을 만든다. 순위는 점수 내림차순 → 최고점을 처음 검증·저장한 시각 오름차순 → 참가자 ID다. 동일 점수 재도전은 최초 달성 시각을 바꾸지 않는다.
3. TOP3 후보의 점수·세션·플레이 시간·요약을 확인하고 관리자에서 플레이 검토를 승인 또는 보류한다. 서버 VERIFIED는 물리 규칙의 일치이며 사람 조작의 보증이 아니다. 개인정보 없는 검토 참조와 근거를 남긴다.
4. 세 후보가 모두 검토 승인 상태이고 기록이 바뀌지 않았을 때 FINAL로 확정한다. 미검토·보류·비활성·변경된 후보는 확정할 수 없다. 문제가 있으면 사유를 확인하고 새 스냅샷에서 재검토하며 자동 차순위 선정은 하지 않는다.
5. 랭킹 전용 3개와 복주머니 배정 재고를 각각 대조한다.
6. 담당자 지정 → 대학생 자격·동일인 확인 → 연락 → 실제 전달 → 증거 확인 → 지급 완료로 변경한다. 자격 확인은 플레이 검토와 별개다.
7. 실제 전달이 불명확하면 대기 상태를 유지한다. 버튼 재시도는 추가 발송 지시가 아니다. FINAL 이후 부적격·미응답은 지급 보류 후 운영자가 처리하며 원장 삭제나 임의 재확정으로 수상자를 바꾸지 않는다.
8. 개인정보 정리 절차에 따라 지급일·삭제 기한·완료 기록을 관리한다.

관리자 수령 원장에서 자격 확인을 `확인 완료`로 저장하고 확인 참조를 남긴다. 실제 전달 후 `외부 전달 완료`와 사유를 입력해야 지급 완료로 저장된다. 베타는 `TEST_REF_...`, 본행사는 `REF_...` 참조를 사용하며 개인정보를 사유·참조에 넣지 않는다. 필수값 누락·버전 충돌·지급 확인 철회는 거부한다. 랭킹 지급은 FINAL 수상자·전용 재고와 연결된 요청만 가능하며, 실제 구매·발송은 운영자가 수행한다.

## 본행사 전환 준비 상태

현재 베타에 날짜와 실제 경품 이름만 넣어 본행사를 시작할 수는 없다. 아래 제한은 의도된 베타 보호 장치이며 운영 경로를 준비할 때 함께 검증한다.

| 현재 코드·DB 상태 | 본행사에 필요한 작업 | 먼저 필요한 결정 |
| --- | --- | --- |
| production 런타임·별도 역할·스키마·쿠키 및 manifest/DB guard 일치 검사 구현 | 원격 운영 영역 생성·비밀 연결·실제 값 대조 | 대상 도메인·환경 승인 |
| 기존 `dino_dev`의 캠페인은 테스트 전용, 실경품 OFF 제약 | 운영 데이터 영역과 전용 접속 역할 준비 | 같은 Supabase 재사용. 베타 참여 기록만 초기화하는 범위 확정 |
| 환경별 SQL·조회·쿠키·분석 분리 구현 | 실제 운영 연결과 베타 초기화 범위 대조 | 승인된 새 행사로 시작 |
| 사전 검사·runtime manifest 해시·DB guard 검사 구현 | 승인된 설정을 적재하고 5,000자리/77개+3개 재고 대조 | 누락된 승인·검증 증거 |
| 먼저 달성한 순위·FINAL 스냅샷·분리된 경품·수동 지급 연결 구현 | 후보 플레이 검토 후 FINAL·자격 확인·지급 절차 확인 | 부적격·미응답 예외의 수동 처리 |

새 Supabase 유료 프로젝트 생성은 계획에 포함하지 않는다. 동일 프로젝트 안의 별도 스키마는 DB 서버 자원을 공유한다. 운영 영역·역할과 베타 초기화 순서는 [최종 실행 계획](final-launch-execution-plan.md), 범위 제한 도구는 [베타 초기화 절차](beta-reset-runbook.md)를 따른다.

행사 시간은 2026-09-29 19:00 KST부터 2026-10-03 00:00 KST 미만이다. 새 게임·추첨과 GAME/DRAW 보상은 종료 후 허용하지 않는다. 게임 완료는 종료 경계 전에 요청 본문 전체가 서버에 도착한 경우만 인정한다. 수령 정보는 2026-10-04 00:00 KST 미만에 접수하며 이후 자동 지급·차순위 선정은 하지 않는다.

## 비용·성능 확인

이번 베타 반영에서 새 유료 프로젝트 생성·DB 증설·추가 발송 서비스를 만들지 않았다. 기존 서비스의 배포·요청 사용량은 발생하며 추가 청구액을 0원으로 보장하지 않는다. 실제 Vercel/Supabase 청구·예산 알림과 담당자는 본행사 운영 준비에서 확인한다. 최종 부하 시험은 사용자가 보류했으므로 실행 전 시간·요청·비용 상한을 다시 확인한다.


## 2026-09-29 운영 연결 준비 추가

- 신규 운영영역: 같은 프로젝트의 `dino_prod` / `dino_prod_app`. 본행사는 빈 기록으로 시작하고, 베타 참여 기록은 범위 제한 초기화한다. 기존 앱·공용 인증·관리자·guard·스키마 구조는 유지한다.
- `python scripts/prepare_production.py --schema-output .local/phase3/production-schema.sql`은 SQL 파일만 생성한다. 네트워크·원격 생성·오픈을 수행하지 않는다.
- 원본 migration 파일과 SHA-256 목록은 `config/production-schema-sources.json`에 고정한다. 원본 변경 시 검토 후 목록을 갱신한다.
- 승인된 운영 manifest가 완성되면 서버의 `production-launch-manifest.json` 및 `PRODUCTION_MANIFEST_SHA256`, DB guard가 같은 설정을 가리켜야 한다. 실제 runtime은 `APP_ENV=production`, `VERCEL_ENV=production`, 별도 역할의 transaction pooler를 요구한다.
- 현재 생성·적재 함수는 빈 운영영역만 허용하며, 기존 테이블·재고가 있으면 덮어쓰기를 거부한다. 기본 캠페인은 PAUSED, `event_enabled=false`다.
- 추첨 상품권 77개와 랭킹 3개는 서로 다른 재고 ID를 사용한다. 실제 구매는 아직 전이며, 사용자 결정대로 당첨자 연락처 취합 후 일괄 구매·발송한다. DB 재고 수량은 배정 한도이고 구매 완료의 증명이 아니다.
- 운영 쿠키는 Secure·HttpOnly인 `dj_production_session`으로 베타 `dj_session`과 분리한다.
- 이벤트 시작/종료: 2026-09-29 19:00 ≤ 서버 시각 < 2026-10-03 00:00 KST. 게임 완료 요청은 마감 미만에 서버가 받은 경우만 인정한다.
- 수령 정보 접수: 서버 접수 시각 < 2026-10-04 00:00 KST. 마감 뒤 자동 지급이나 차순위 선정은 하지 않는다.
- 동점은 최고점을 처음 서버에 검증·저장한 시각 순이다. 동일 점수 재도전으로 이 시각이 바뀌지 않는다.
- 마감 30초 뒤 새 스냅샷을 생성하고 후보 플레이 검토 후 확정한다. 이 시간은 마감 전 접수 요청의 처리 대기이며 추가 게임 인정 시간이 아니다. 현재 Vercel maxDuration=30초에 맞춘 기준이므로 실행 제한을 늘릴 때 정산 대기 기준도 검토한다.
- 최종 확정은 랭킹 수령 요청과 3개 재고를 연결한다. 자동 발송하지 않는다. 운영자가 자격·실제 전달·참조 번호를 확인한 뒤 지급 완료 처리한다.
- 운영 검증 참조는 `REF_…`, 베타는 `TEST_REF_…`를 사용한다. 참조 번호에 연락처·증빙 원문을 넣지 않는다.
