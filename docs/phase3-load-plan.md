# 최종 2.1.0 부하 테스트 — 2026-09-29

## 실행 승인과 한도

사용자 요청: “이제 부하 테스트 가자 최대한 빡시게 돌려보자”. 이전 보류를 해제했다.

- 대상: 기존 Vercel 프로젝트의 별도 Preview, 기존 Supabase `dino_dev` 합성 캠페인
- 공개 베타 주소 연결은 유지하고, 본행사 `dino_prod` 경품은 사용하지 않는다.
- 무제한 게임권 OFF, GA4 OFF. 게임·추첨·랭킹·자체 이벤트 서버 API를 검증한다.
- 100명 180초 → 통과 시 200명 동시 시작 30초. 각 단계 종료 대기 최대 90초, 합계 최대 390초.
- 준비 HTTP 조회·실패 요청 포함 최대 7,000회. 자동 재시도 0회.
- 5xx·429·timeout·업무 불일치 발생 시 전체 중단. 실패한 100명 단계 뒤 200명으로 증폭하지 않는다.
- 기존 1·2차 원장·승인 기록은 보존한다. 별도 Phase3 승인 파일과 원장을 사용한다.

## 실제 요청 흐름

새 합성 참가자 조회 → 게임 생성·시작 → 실제 경과시간 대기 → 2.1.0 점수 검증 → 100점 이하 환급 / 고득점 차감 → 복주머니 조회·선택·스크래치 → 랭킹·초대·수령함 조회 → 자체 이벤트 2개 기록.

최대 600회 흐름, 흐름당 11개 API, 사전 조회 2개로 러너 상한은 6,602회다. 별도 준비 조회 2회를 포함해 7,000회 이하로 제한한다. DB에는 합성 참가자 5,000명을 준비해 기존 예상 참여 규모의 테이블을 사용한다. 이는 5,000명 동시 접속 시험을 뜻하지 않는다.

본행사와 같은 5,000칸 비복원 추첨 구조를 합성 경품으로 준비한다. 테스트 전 경품 수량은 기존 77개 기준이다. 사용자 추가 지시인 GS 5천원권 24→10개와 확률 조정은 **부하 테스트 이후** 반영한다. 새 오픈 시각은 **2026-09-29 21:00 KST**, 종료·접수 마감은 기존 확정값을 유지한다.

## 검증 범위의 한계

- API 부하이며 200대 휴대폰의 화면 렌더링·카카오 앱 전송을 재현하지 않는다.
- 카카오 실제 전송 웹훅과 수령정보 제출은 대량 합성 호출하지 않는다. 앞선 실제 전송 증거와 구분한다.
- 100점 이하 게임이 대부분이며 매 100번째 흐름은 실제 seed에서 코인·부활 포함 고득점 경로를 시도한다. 성립하지 않으면 정상 저점 경로로 대체하므로 실제 고득점 완료 수를 사후 DB로 집계한다.
- 오류가 없어도 응답 속도와 처리 완료 비율을 별도로 판정한다. p95 1초 미달이면 목표 미달로 기록한다.
- 신규 유료 서버·프로젝트를 만들지 않는다. 기존 Vercel·Supabase·Datadog 사용량은 발생하며 이번 사용량이 무료라고 단정하지 않는다.

## 첫 실행과 수정 — 19:30 KST

- 100명 단계에서 실제 실행 11.52초, 러너 460회 + 준비 조회 2회 = 462회 요청 후 자동 중단.
- 게임 생성·시작 각 100/100 성공. 게임 완료 73/100 성공, 종료·추첨 등에서 총 39개 503.
- Vercel 로그에서 39개 모두 `database_failure=pool_wait`, 연결 대기 3,001ms 확인.
- 200명 단계는 실행하지 않았다. 실패 증거: `docs/evidence/phase3-load-initial-20260929.json`.
- 원인: 종료 처리의 행사 행 `FOR UPDATE` 잠금이 참가자별 종료 트랜잭션 전체를 순차 처리시켜 연결 슬롯을 점유했다.
- 수정: 게임 종료만 `FOR SHARE`로 변경. 참가자별 세션 잠금 및 관리자 마감·확정의 배타 잠금과 충돌 관계는 유지.
- 추가 사용자 지시: DB 연결 슬롯 대기 3초 → 5초.
- 로컬 실제 PostgreSQL 회귀 검사에서 서로 다른 종료 두 건이 동시 완료되고 관리자 변경은 그동안 대기하는 것을 확인했다.

## 한도 내 1회 수정 후 재검사

첫 실패 보고서·원장은 수정하거나 삭제하지 않는다. 이전 462요청과 실제 실행시간 올림 12초를 새 원장에 승계한다.

- 100명 150초(흐름 간 대기 50초) → 200명 동시 시작 30초, 각 단계 종료 대기 90초.
- 재검사 최대 500개 흐름·5,502 API. 이전 기록을 합쳐 최대 5,964회이며 준비 추가 조회도 총 7,000회에 포함한다.
- 재검사 실행 예약 360초 + 이전 실제 실행 올림 12초 = 372초로 총 실제 부하 390초 이하.
- 이전 증거 파일의 해시와 참가자 사용 위치 100을 묶어 이미 시도한 첫 100명을 재사용하지 않는다.
- 새 수정 배포에만 1회 허용하며 오류 시 중단한다. 세 번째 원격 실행을 자동으로 시작하지 않는다.

## 두 번째 실행 중단 — 하네스 계약 오류

- 수정 배포에서 100명 단계를 다시 시작했고 6.31초 동안 API 356회를 처리했다.
- HTTP 5xx·429·timeout은 없었다. 게임 생성·시작 100건, 완료·추첨 등 도달한 요청도 모두 정상 HTTP 상태였다.
- 자체 이벤트 묶음에서 허용되지 않은 `source=phase3_load`와 `round_number` 차원을 보낸 탓에 `accepted=2` 조건을 만족하지 못해 러너가 중단했다.
- 서버 용량 실패가 아니라 부하 하네스의 이벤트 계약 오류다. 성공 결과로 바꾸거나 삭제하지 않고 `docs/evidence/phase3-load-harness-stop-20260929.json`에 별도 보존한다.
- 수정 내용: `source=home/result`, `channel=phase3_load`로 분리하고 허용되지 않은 `round_number`를 제거했다. 실제 `operations.events_batch` 계약 검사에서 두 이벤트 모두 수락되는 회귀 검사를 추가했다.

## 최종 하네스 교정 실행

두 실패 원본과 원장, 두 코호트 파일을 해시로 묶고 참가자 사용 위치 200부터 시작했다. 이전 요청 818회와 각 실패 실행시간 올림 합계 19초를 새 원장에 승계했다.

- 계획 상한: 새 흐름 500개·API 5,502회, 누적 API 최대 6,320회. 새 실행 예약 360초를 더한 누적 예약은 379초다.
- 실제 결과: 100명 단계에서 150.01초 동안 300개 흐름, 200명 동시 시작 단계에서 21.54초 동안 200개 흐름을 완료했다.
- 최종 실행 API 5,502회, 흐름 500개가 모두 완료됐다. 5xx·429·timeout·예상 밖 실패는 0건이다.
- 세 실행의 실제 경과시간 합계는 189.72초이고, 누적 API는 6,320회다. 승인 상한 390초·7,000회 안이다.
- 최종 실행의 `POST /api/draws` p95는 4,563.88ms, `GET /api/draws/{id}` p95는 3,561.83ms, 스크래치 완료 p95는 3,819.68ms다. 오류 없이 완료했지만 1초 응답 목표는 달성하지 못했다.
- 최종 공개 집계는 `docs/evidence/phase3-load-final-20260929.json`, 해석과 제한은 `docs/phase3-load-report-20260929.md`에 기록한다.

## 결과 해석 제한

- 200명 단계는 동시 시작 30초 계획에서 각 작업자가 한 흐름씩 실행한 burst이며, 200명이 30초 내내 반복 요청한 지속 부하가 아니다.
- API 시험이므로 모바일 UI FPS·입력 지연·화면 전환 끊김을 검증하지 않는다.
- 실제 카카오 전송과 수령정보 쓰기는 포함하지 않는다. 해당 기능은 기존 실전송 증거와 별도로 판단한다.
- 5,000명 동시 접속을 검증한 결과가 아니다. 5,000개 합성 참가자·5,000칸 추첨 구조에서 최대 동시 작업자 200명을 시험한 결과다.
